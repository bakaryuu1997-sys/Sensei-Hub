# Day 27: 速度の頂点 - パフォーマンスチューニングとモニタリング 🏎️

**Day 27** へようこそ。これは、**シニア・データベースアーキテクト** を目指すすべての人にとって最も重要なレッスンです。

1,000件のレコードで正常に動作するデータベースも、1億件に達すると崩壊する可能性があります。10分のクエリと10ミリ秒のクエリの差は、**「チューニング」** スキルにあります。今日は、PostgreSQL エンジンのボンネットを開け、すべてのボルトを締め直しましょう。

---

## 🎯 1. 本日の戦略的目標

1.  **EXPLAIN ANALYZE の解剖:** データベースがどのように「思考」し、実行パスを選択するかを理解します。
2.  **インテリジェントな RAM 設定:** `shared_buffers`、`work_mem`、`effective_cache_size` をマスターします。
3.  **コネクション・プーリング:** 10,000人の同時ユーザーを捌くために `pgBouncer` が必要な理由。
4.  **膨張 (Bloat) と Vacuum の管理:** 不要なデータがデータベースを低速化させるのを防ぎます。
5.  **テーブルパーティショニング:** 数十億行のテーブルを「分割して統治」する戦略。
6.  **モニタリング:** `pg_stat_statements` を使用して「沈黙の殺人者（スロークエリ）」を特定します。

## 🧠 2. 哲学：「シェフと厨房」

データベースを高速にするには、各コンポーネントが調和して動作する必要があります。
- **Shared Buffers (調理台):** 頻繁に使用されるデータが RAM 内に置かれる場所。ここが広いほど、倉庫（ディスク）へ走る回数が減ります。
- **Work Mem (シェフの包丁):** ソートや結合のために各クエリに割り当てられるメモリ。包丁が小さすぎると、シェフは裏庭（ディスク）で作業しなければならず、非常に低速になります。
- **Maintenance Work Mem (清掃トラック):** インデックス作成や Vacuum などのメンテナンス作業用のメモリ。

### ASCII Diagram: データアクセス階層 (I/O コスト)

```text
       [SQL クエリ]
              |
      +-------V-------+
      |  L1/L2 キャッシュ | (0.5 ns) - 超高速
      +-------+-------+
              |
      +-------V-------+
      | SHARED BUFFERS| (10 - 100 ns) - 高速 (RAM内)
      +-------+-------+
              |
      +-------V-------+
      |  OS キャッシュ    | (かなり高速)
      +-------+-------+
              |
      +-------V-------+
      |  SSD / ディスク  | (1 - 10 ms) - 非常に低速 (パフォーマンスの天敵)
      +---------------+

(チューニングの目標：データをできるだけ SHARED BUFFERS に留めること！)
```

## 🛠️ 3. 実戦シナリオ (高度なパフォーマンス分析)

### シナリオ 1：EXPLAIN ANALYZE の解読
クエリの先頭に `EXPLAIN ANALYZE` を付けて実行結果を見てみましょう。

```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

-- 出力例:
-- Index Only Scan using users_email_idx on users (cost=0.42..8.44 rows=1 width=32)
-- Actual time=0.042..0.043 rows=1 loops=1
```

**シニアの解釈：**
- **Index Only Scan:** 完璧です！ テーブル本体に触れることなく、インデックスから直接データを取得できています。
- **Sequential Scan:** 赤信号！ データベースが全行をスキャンしています。すぐにインデックスが必要です。
- **Bitmap Index Scan:** 良好。インデックスからアドレスを先に集め、まとめてデータを取得しています。

### シナリオ 2：メモリ設定の最適化
16GB RAM のサーバーがある場合、デフォルト設定のままにしてはいけません。

```bash
# postgresql.conf 内の設定
shared_buffers = 4GB           # 通常、全 RAM の 25%
work_mem = 64MB                # SORT や JOIN 操作を RAM 内で完結させる
maintenance_work_mem = 512MB   # インデックス作成を高速化
effective_cache_size = 12GB    # OS がキャッシュに使う RAM 量をプランナーに教える
```

## ⚡ 4. シニアの秘密：テーブルの「膨張 (Bloat)」との戦い

PostgreSQL では、行を `UPDATE` しても上書きはされません (MVCC)。代わりに新しい行が作成され、古い行は「デッドタプル（ゴミ）」になります。掃除を怠ると、テーブルサイズが10倍に膨れ上がり、その9割がゴミという状態になります。

**解決策：**
- `autovacuum` が適切に調整され、稼働しているか確認する。
- システムをロックせずにテーブルを整理する `pg_repack` などのツールを活用する。

## 💡 5. スケール戦略：コネクション・プーリング

初心者がやりがちなミスは、アプリを DB に直接接続させることです。Postgres の1接続は約 10MB の RAM を消費します。1000接続あれば、接続を維持するだけで 10GB も消費してしまいます！

> [!IMPORTANT]
> **PGBouncer の活用:**
> PGBouncer は「門番」の役割を果たします。アプリからの 1000 の接続を受け付けつつ、実際のデータベースへの接続は 50 本程度に絞り込みます。これらを高速に再利用することで、DB サーバーが新しい接続処理で CPU を浪費するのを防ぎます。
