# Day 23: タイムマシン - バックアップ、リカバリ、そして高可用性 🛡️

データベースエンジニアの世界には、有名な格言があります。 **「エンジニアには2つのタイプしかいない。データをバックアップしている者と、まだデータを失ったことがない者だ……今のところは。」**

システムがランサムウェアに暗号化されたり、データセンターが火災に見舞われたりすることを想像してみてください。もし強固なバックアップとリカバリ戦略がなければ、会社は数時間で消滅してしまうかもしれません。今日は、単にデータをコピーする方法ではなく、**「生存のためのアーキテクチャ」** を構築する方法を学びます。

---

## 🎯 1. 本日の戦略的目標

1.  **RTO と RPO を極める:** クライアントと信頼性について交渉するための2つの重要な指標。
2.  **論理バックアップ (pg_dump):** データを SQL ファイルとして出力。小〜中規模 DB に適した柔軟な手法。
3.  **物理バックアップ (pg_basebackup):** テラバイト級の巨大なデータベースのために、バイナリファイルを直接コピー。
4.  **継続的アーカイブ (WAL):** トランザクションログを継続的に記録し、ミリ秒単位の過去に復元。
5.  **ストリーミング・レプリケーション:** メインサーバー停止時に即座に切り替わる「プライマリ・スタンバイ」構成。
6.  **3-2-1 ルール:** バックアップ保存のための業界標準の黄金律。

---

## 🧠 2. 哲学：RTO と RPO - あなたのデータにはいくらの価値があるか？

コードを書く前に、この2つの概念を理解する必要があります。これらがあなたのアーキテクチャのコスト（高いか安いか）を決定します。
- **RPO (目標復旧時点):** 「どれだけのデータ紛失を許容できるか？」。RPO = 0 なら同期レプリケーションが必要です。RPO = 24時間なら、夜間のバックアップで十分です。
- **RTO (目標復旧時間):** 「最大ダウンタイムはどれくらいか？」。RTO = 5分なら、高可用性 (HA) が必要です。RTO = 1日なら、バックアップファイルからゆっくり復元できます。

### ASCII Diagram: 災害復旧 (DR) アーキテクチャ

```text
       [ユーザーのリクエスト]
              |
              V
      +-----------------+
      |  プライマリサーバー | (本番稼働)
      | (Read / Write)  |
      +-----------------+
        /             \
       /               \ (1) ストリーミング・レプリケーション (リアルタイム)
      /                 \
     V                   V
+-----------------+   +------------------+
|  WAL アーカイブ  |   |  スタンバイサーバー | (冗長化)

+-----------------+   +------------------+
     |                       |
     | (2) ポイントインタイム  | (3) 高可用性 (HA)
     |     リカバリ (PITR)   |     フェイルオーバー
     V                       V
+----------------------------------------+
|           災害復旧システム               |
+----------------------------------------+
```

## 🛠️ 3. 実戦シナリオ (高度なハンズオン)

### シナリオ 1：論理バックアップ (100GB 以下の DB 向け)
`pg_dump` はデータを SQL ファイルとして抽出します。利点は、異なる PostgreSQL バージョンや、異なる種類の DB にもリストアできることです。

```bash
# 4つのスレッドで並列実行し、バックアップを高速化
pg_dump -U postgres -d production_db -F c -j 4 -f backup_full_$(date +%Y%m%d).dump

# データのリストア（復元）：
# -c: ロード前に既存データを削除
# -j: 4スレッド並列でリストア実行（RTO を劇的に短縮）
pg_restore -U postgres -d restore_db -j 4 -c backup_full_20260513.dump
```

### シナリオ 2：物理バックアップ (巨大な DB 向け)
数テラバイト規模の DB の場合、`pg_dump` では一日中かかってしまいます。そこで `pg_basebackup` を使います。

```bash
# バイナリデータファイルをバックアップサーバーへ直接コピー
pg_basebackup -h 10.0.0.1 -D /var/lib/postgresql/backup_data -U replication_user -P -v
```

## ⚡ 4. シニアの秘密：ポイントインタイムリカバリ (PITR)

これは、シニアとジュニアを分けるスキルです。ハッカーが **14:00:05** にデータを削除したとします。あなたは **12:00:00** のベースバックアップと、12時から14時までの全 WAL ログを持っています。

**PITR の復元プロセス：**
1. 12時の物理バックアップ (Base Backup) をリストアします。
2. `recovery.signal` ファイルと `recovery_target_time` を設定します。
3. 停止時間を指定： `'2026-05-13 14:00:04'`。
4. DB を起動すると、すべての操作が「再現 (Replay)」され、ハッカーが削除ボタンを押す「1秒前」で正確に停止します。

## 💡 5. 生存戦略：3-2-1 ルール

単一のデバイスを信じてはいけません。

> [!IMPORTANT]
> **バックアップの 3-2-1 ルール：**
> - **3つのコピー：** (1つの本番 ＋ 2つのバックアップ)。
> - **2つの異なるメディア：** (例：1つはサーバーディスク、1つは S3 などのクラウドストレージ)。
> - **1つのオフサイト：** (ランサムウェア対策として、1つのコピーは地理的に離れた場所、またはネットワークから切り離された場所に置く)。

---

## 📊 6. バックアップ戦略の比較

| 指標 | pg_dump (論理) | pg_basebackup (物理) | ストリーミング・レプリケーション |
| :--- | :--- | :--- | :--- |
| **バックアップ速度** | 低速 (データ走査) | 非常に高速 (ファイルコピー) | 継続的 (リアルタイム) |
| **復元速度** | 低速 (インデックス再構築) | 非常に高速 (コピーのみ) | 即時 (フェイルオーバー) |
| **ストレージ容量** | 小 (SQLのみ) | 大 (DBサイズと同等) | 非常に大 (2台分) |
| **RPO** | 定期的 (24h/1h) | 定期的 | ほぼゼロ |
