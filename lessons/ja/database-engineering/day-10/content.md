# Day 10: データ・アーキテクトの生死を分かつ一撃 (更新・削除：UPDATE / DELETE) 💥

これまでの2つのレッスンでは、`SELECT` 文を使って「選択的な読み取り」の練習をしてきました。データを読み取るだけなら、会社のハードドライブを壊すことはないので、自由に網を投げることができました。（コピーを取り出すだけで、原本はそのまま残るからです）。

**しかし今日は、不注意な開発者にとって最も恐ろしい局面を迎えます。**

私たちは、既存の引き出しに新しい値を書き込む（**UPDATE**）こと、そしてファイルを焼却炉に投げ捨てる（**DELETE**）という、直接的な変更の領域に踏み込みます。

あなたのデータベース・キャリアの生存をかけた門門へようこそ： **「外科手術の極意 - 極限の注意を払ったデータ操作」**。

## 🧠 2. 哲学：なぜ UPDATE の筆は燃えやすいのか

あなたが大手物流会社（ヤマト運輸や佐川急便のような）のIT担当者だと想像してください。ある顧客「タムさん（UID: 121）」の配送注文にエラーがありました。配送料が本来2,000円であるべきところ、誤って200円と入力されてしまいました。

マネージャーが叫びます： _「急げ！ SQLツールを立ち上げて、`shipping_orders` テーブルの200円を2,000円に修正してくれ。ドライバーが損をする前に！」_

もしあなたが無謀なデベロッパーなら、SQLをWord文書のように、クリックしてタイプするだけのものだと思うでしょう。**それは間違いです。**

### SQLの厳格さの欠如は会社を殺す（「WHERE忘れ」の事例）

```ascii
[ 盲目的な更新の危険性 (顧客価格テーブル) ]
100万件の配送注文が入ったデータベース (テーブル: shipping_orders)
   +----+--------------------+--------------+
   | ID | 顧客名              | 配送料 (円)   |
   +----+--------------------+--------------+
   | 01 | タムさん（標的）     |      200     | [ <--- 目標：この行だけを更新する ]
   | 02 | レーさん            |      600     |
   | 03 | フンさん            |    1,000     |
   | .. | (残り100万件)       |              |
   +----+--------------------+--------------+

(致命的なコマンド): UPDATE shipping_orders SET shipping_fee = 2000;
  |
  | 盲目的なSQLロボットはフィルター（WHERE）を受け取らず、ディスクへ突進する！
  V
   +----+--------------------+--------------+
   | 01 | タムさん（標的）     |    2,000     | (修正完了！ 成功か？)
   | 02 | レーさん            |    2,000     | (ちょっと待て！ 彼女は600円だったはずだ！)
   | 03 | フンさん            |    2,000     | (なんてことだ... 全員の配送料が2,000円になった！！)
   +----+--------------------+--------------+
   => 数億行のテーブルの全行が2,000円になった！
   => 結果：顧客の猛抗議、損害賠償、そしてあなたの解雇！
```

**これを肝に銘じてください：** 本番環境で `UPDATE` や `DELETE` を使うとき、コマンドの最後に `WHERE id = ...` が見えるまで、心臓の鼓動を止めてはいけません。

## 💻 3. 実戦トレーニング（SupabaseでのSQL練習）

`products`（製品）テーブルがあり、`id`、`product_name`、`price`、`is_in_stock`（在庫あり）のカラムがあると仮定します。

### ステップ1：安全な注入 (UPDATE コマンド)

`id = 56` のナイキシューズが10,000円で登録されていますが、25,000円に更新する必要があります。また、ちょうど在庫が切れました。

```sql
-- ID 56 への精密な狙い撃ち：
UPDATE products
SET price = 25000,
    is_in_stock = false
WHERE id = 56;

-- 「WHERE id = 56」が見えて初めて、一息つくことができます！
-- SQLはこう返します：「1 Row Updated.」 データベースは安全です。
```

複数のカラムを一度に更新するために **カンマ (`,`)** を使っていることに注目してください。クリーンで効率的です。

### ステップ2：最終浄化 (DELETE コマンド)

あなたのアプリがハッカーのスクリプト攻撃を受け、数千の偽の「クローン」アカウントが作成されました。管理者は、即座に削除すべき特定のクローン `id = 900` を特定しました。

```sql
-- 焼却コマンド (DELETE FROM):
DELETE FROM users
WHERE id = 900;

-- 結果：行 ID 900 は消滅しました。検索インデックスはよりクリーンで高速になります。
```

### ステップ3：一括ストライク (IN 演算子)

もしハッカーが5つの特定のアカウント（ID: 900, 1022, 5003）を作成した場合はどうでしょうか？ DELETEコマンドを3回実行するのは非効率です。**IN** の網を使いましょう！

```sql
DELETE FROM users
WHERE id IN (900, 1022, 5003);
-- ロボットは3つのターゲットすべてを集め、一つのトランザクションで焼き払います。
-- 高速で低レイテンシです！
```

## 💡 4. シニアの秘密：論理削除 (なぜテック企業は本当の意味で削除しないのか)

あなたがGoogleや大手銀行のCTO（最高技術責任者）の面接を受けていると想像してください。彼らはこう尋ねます： _「顧客がキャンセルしたから注文を削除したい場合、アプリはSQLの 'DELETE' コマンドを使うべきですか？」_

もしあなたが「はい、`DELETE` を使います」と答えたら、不採用になるかもしれません。

**現実：** プロのテック企業は、物理的な取引履歴をディスクから削除することはほとんどありません。もし削除してしまい、後で顧客が請求に異議を唱えたり、警察が詐欺事件の証拠を必要としたりした場合、「削除された」データは永遠に失われ、会社は法的に無防備になってしまいます。

### 技術：論理削除 (Soft Delete)

`DELETE` の代わりに、隠しカラム `is_deleted`（BOOLEAN型、デフォルト `false`）を追加します。
レコードを「削除」するには、バックエンドで **UPDATE** を使って「秘密のマスキング」を実行します：

```sql
-- 破壊する代わりに、レコードを隠す：
UPDATE orders
SET is_deleted = TRUE
WHERE id = 502;
```

**魔法の仕組み：**
*   **顧客** の画面からは注文が消えます。アプリが `SELECT * FROM orders WHERE is_deleted = FALSE` を実行しているからです。
*   **会社** には、監査、訴訟、データ分析のための元のデータが残っています。これはデータの整合性を守るための、数百万ドル規模の価値がある最適化です！
