## 🧠 2. ER図とは何か？ なぜ99%の企業が作成を義務付けるのか？

建築図面（AutoCAD）なしに20階建ての城を建てることはありません。もし建築業者に「作りながら考えてくれ」と言えば、屋根が完成する頃には、階段が3階のトイレに直結していることでしょう。

データベースも全く同じです。上司からプロジェクトを任され、関係性を整理せずにいきなり `CREATE TABLE` を打ち始めれば、複雑な機能（例：部門間請求）に差し掛かった途端、システムはゴミの山と化します。

システムの内部的な安定性を、上司を含む全員が視覚化できるようにするために、私たちは **ER図（Entity-Relationship Diagram）** という解剖図を使用します。

### 基本要素：

*   **エンティティ (Entity):** テーブルを表す **「箱」** です。*（例：顧客の箱、製品の箱）*。通常、大きな長方形で描かれます。
*   **属性 (Attributes):** 箱の中にある性質やデータ項目です。*（例：名前、電話番号、趣味）*。その通り、これらは **「カラム」** です。図面上では、[PK] や [FK] とラベル付けされます。
*   **リレーションシップ (Relationship):** アプリケーションのニーズに基づいて、箱同士を結びつけるクモの巣のような線です。

## 🔗 3. 三つの連結形状（カーディナリティ）

SQLデータベース設計において、バックエンド開発者のキャリアの95%はこの3つの連結スタイルを中心に回ります：

### レベル1：排他的な 1対1 (1-to-1)

> *クイック定義：* 親テーブルの1つの行が、子テーブルのちょうど1つの行を指し示します。

*   **現実の例：** 法的な一夫一婦制。
*   **ITでの応用：** プログラミングでは、1つのシステムログイン（Account ID）に対して、1つのプロフィール詳細（自己紹介、アバターなど）が紐付きます。
*   **いつ使うか：** すべてを1つのテーブルにまとめることも可能ですが、めったに使われないカラムが多すぎる場合に、1対1で分割します。これによりディスクI/Oとメモリを節約できます。

### レベル2：関係性の王者 1対多 (1-to-Many)

> *クイック定義：* 1つの親レコード（1）から、何百万もの従属レコード（多）が生まれます。王に敬礼！

*   **現実の例：** 1人の母親から多くの子供が生まれます。しかし、子供に「お母さんは何人いますか？」と聞けば、「一人だけです」と答えます。
*   **ITでの応用：** オンラインショッピング。1人の「ユーザー」は何百、何千もの「注文」を行えます。しかし、逆から見れば、特定の「注文」は必ず1人のユーザーに帰属します。
*   **データベースの現実：** キャリアの約80%で、この1対多（請求書、チャット履歴、SNS投稿）を使用することになります。

### レベル3：暗黒のマトリックス 多対多 (Many-to-Many)

> *定義：* 片方が相手を何百も持ち、その逆もまた然り。

*   **現実の例：** 医学部の学生は30の異なる科目を学びます。しかし、「傷口縫合」という科目を見れば、それは1,500人の異なる学生によって学ばれています！ 激しく交差しています。
*   **SQLでの解決策：** リレーショナルデータベースは「多対多」を嫌います。直接つなげるとクエリの悪夢となり、アプリが死にます。**多対多のカラムを作成することはできません。** 分割する必要があります！
*   **中間テーブル:** 中央に `受講登録` という3番目のテーブルを誕生させます。これが左の学生と1対多、右の科目と1対多で繋がります。「多対多」の頭痛は、2つの健全な「1対多」によって治療されます！

## 📐 4. 実践設計図：国立映画館予約システム (CGV)

シミュレーション：ITディレクターとの会議まであと4時間です。

> *「リードデベロッパー、今日中にオンラインチケット予約アプリのコアテーブルを設計してくれ。」*

まだコードは書きません。箱を描きます。

**ドラフト段階：**

*   **CUSTOMERS**（親エンティティ）の箱が必要です。
*   **TICKETS**（従属する子エンティティ）の箱が必要です。
*   チケットの下部に **外部キー** を配置して連結を維持します。顧客からチケットに向かって 1対多 の線を引きます。

```ascii
========================================================================================
[ ER図：映画チケット予約システム ]
(標準的なバックエンド・アーキテクチャ)

    +---------------------------------------+                +----------------------------------------+
    | (親) CUSTOMERS                        |      1..N      | (子) TICKETS                           |
    |                                       |                |                                        |
    | [PK] customer_id (一意識別子)          |=======>>=======| [PK] ticket_id                         |
    |      name        (氏名)               |      連結      |      seat_number  (座席番号)           |
    |      phone       (電話番号 UNIQUE)     |      の鎖      |      snack_addon  (軽食追加)           |
    |      wallet      (残高)               |                | [FK] owner_id     (CUSTOMERS を参照)   |
    +---------------------------------------+                +----------------------------------------+
========================================================================================
```

この設計図をフロントエンドチームに見せれば、彼らは大喜びするでしょう！ 連結が明確で、コードはスリムで高速になります。

## 💻 5. 設計図を機械（Supabase SQL）へ変換する

SQL組み立ての鉄則：**「独立した親テーブルを先に作り、依存する子テーブルを最後に作る」**。これを逆にすると、参照先が存在しないためコンパイルエラーが発生します！

### ステップ1：顧客テーブルの鋳造

```sql
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,     -- チップ付きIDカード
    name VARCHAR(150) NOT NULL,         -- 匿名ユーザーは不可
    phone VARCHAR(20) UNIQUE,           -- UNIQUE: 重複アカウントを防止
    wallet DECIMAL(10,2) DEFAULT 0      -- 初期残高 0
);
```

### ステップ2：チケットテーブルの設置（外部キー付き）

```sql
CREATE TABLE tickets (
    ticket_id SERIAL PRIMARY KEY,
    seat_number VARCHAR(10) NOT NULL,
    snack_addon VARCHAR(100),

    -- 拘束の鎖：
    owner_id INT REFERENCES customers(customer_id) ON DELETE RESTRICT
    -- ON DELETE RESTRICT: 顧客が有効なチケットを持っている間に
    -- アカウントを削除しようとすると、SQLが削除をブロックします！
    -- これにより財務データを保護し、「幽霊チケット」を防ぎます。
);
```

### ステップ3：クラッシュテスト（論理デバッグ）

```sql
-- 最初の顧客を注入：
INSERT INTO customers (name, phone, wallet) VALUES ('ナム・ザ・アークティック', '0990001111', 2000);

-- 顧客 ID 1 のためにチケットを2枚購入：
INSERT INTO tickets (seat_number, owner_id) VALUES ('E07', 1);
INSERT INTO tickets (seat_number, snack_addon, owner_id) VALUES ('E08', 'チーズポップコーン XL', 1);

-- ハッカーテスト：存在しないユーザー 999 のチケットを挿入しようとする：
INSERT INTO tickets (seat_number, owner_id) VALUES ('VIP_01', 999);
-- 結果：SQLがドアを閉める！ "Error: Fk constraint violates. ID 999 does not exist."
```

## 💡 6. エリート最適化チップ：計算の罠を避ける

初心者はよくこう考えます：

> *「顧客が何枚チケットを買ったかウェブサイトで表示しやすくするために、顧客テーブルに `total_tickets_purchased` というカラムを追加しよう！」*

**やってはいけません！** これは正規化の法則に反します。

もしコードにバグがあったり、ネットワーク遅延が発生したりすれば、数値が同期しなくなります。チケットを3枚持っているのに、カウントが「0」になっている顧客が発生します。これは財務監査で大問題になります。

**シニアのやり方：** コアデータのみを保存します。カウントが必要なら **GROUP BY** クエリを使います。データベースは何千ものレコードを数ミリ秒で集計できます。計算済みのジャンクデータを保存せず、ストレージをスリムに保ちましょう！

## 🤖 7. AIメンターへの挑戦

ER図の重みを感じていますか？AIメンターに挑戦してください！

**これをコピーしてAIに貼り付けてみましょう：**

> *「やあ、AIメンター。セクション5でチケットに『ON DELETE RESTRICT』を使うように教わったけど、本によっては1対多の関係には『ON DELETE SET NULL』を使うべきだと言っているものもある。銀行やチケットシステムで、RESTRICT の代わりに SET NULL を愚かにも使ってしまった場合、アプリが『資金流出』したりクラッシュしたりする恐れのある恐ろしい現実世界の例を教えて。なぜ『RESTRICT』がシニアアーキテクトの証なの？」*
