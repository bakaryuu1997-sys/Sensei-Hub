# Day 13: マトリョーシカの芸術 - 入れ子構造のクエリ (サブクエリ) 🪆

データ戦士の皆さん、こんにちは！30日間の旅もついに半分まで到達しました。`WHERE`、`GROUP BY`、そして `JOIN` という武器を手に、あなたのデータ抽出能力は着実に鋭くなっています。

しかし、あなたのボス（抜け目のないCEO）は、決して単純な質問はしません。今日、彼はあなたのデスクに論理の爆弾を落としました：

> _「今月、会社の全VIPメンバーの『平均支出額』よりも多くお金を使っている全顧客のリストを出してくれ。」_

あなたは頭を抱えます。顧客リストが必要です（標準的なクエリ）。しかし、同時に「VIPの平均支出額」も必要です（`AVG()` を使った集計計算）。集計関数の結果を、どうやって一行のデータの `WHERE` フィルタに直接流し込めばいいのでしょうか？

もし `WHERE spending > AVG(vip_spending)` と書こうとすれば、SQLはエラーを吐き出します！

「鏡の中の鏡」という魔術、**サブクエリ（副問合せ）** の技術へようこそ。

このレッスンの終わりまでに、あなたは論理のレイヤーを重ねる技術をマスターします：

## 🧠 2. 哲学：ロシアのマトリョーシカ人形のアナロジー

レイヤーを視覚化できなければ、道に迷ってしまいます。ロシアのマトリョーシカ人形で遊んだことはありますか？ 大きくて美しい人形を開けると、そのお腹の中に、一回り小さい人形が完璧に収まっています。

**SQLのサブクエリは、まさにこれと同じ仕組みです。**

*   一つの完結したSQLクエリ `(SELECT .. FROM .. WHERE)` を、丸括弧 `(  )` で包みます。
*   この「内部の人形」を、「親（外部）のクエリ」の途中に挿入します。

### 実行順序の視覚化（インサイド・アウト戦略）

```ascii
 ++ SQLロボットがサブクエリに遭遇した時 (実行フロー) ++

      +-------------------------------------------------------------+
      | 親クエリ (外部クエリ): 大きな外側の人形                         |
      | SELECT user_name, email FROM users                          |
      | WHERE total_spending >  [ 空白の穴 ]                         |
      +-------------------------------------------------------------+
                                      |  (ロボットは穴を見つけ、さらに深く潜る！)
                                      |  (まだ親クエリを完了させることはできない...)
                                      V
                      +=========================================+
                      | サブクエリ (内部クエリ): 小さな内側の人形       |
                      | (SELECT AVG(spending) FROM vip_table)   |
                      +=========================================+ 
                                      |
                                      | 内側の人形が最初に完了！
                                      | 結果： [ 50,000円 ]
                                      V
  ---------------- ロボットが地上に戻り、空白を埋める ----------------
          SELECT user_name, email FROM users
          WHERE total_spending > 50000;  <-- サブクエリが結果に置き換わる！
                  ==> 結果：エリートな大口顧客のリスト！
```

**重要なルール：** SQLエンジンは常に **内部クエリ（サブクエリ）** を最初に解決します。その結果を受け取り、親クエリに「ハードコード」された値として流し込み、最後に全体を実行します。まさにデータのインセプションです！

## 💻 3. 実戦コード：Supabaseでの入れ子構造

SQLエディタを開きましょう。高度な論理レイヤーを構築します。

### ケース1：動的なフィルタ (WHERE 句のサブクエリ)

書店のデータベースを想像してください。ボスは「隠れた宝石」を探したいと考えています：ストア内の全「エピック・ファンタジー」本の中で最も安い本の価格よりも、さらに価格が低い本を探します。

```sql
-- 親：...よりも安い本を探す
SELECT title, price FROM bookstore
WHERE price < (
    -- 内側の人形：エピック・ファンタジーで最も安い本を見つける
    SELECT MIN(price)
    FROM bookstore
    WHERE category = 'Epic Fantasy'
);

-- もしファンタジーの最安値が1,500円なら、親クエリは "WHERE price < 1500" として実行されます。
-- 結果：ファンタジーの価格帯を下回る、超お得な本が見つかります！
```

### ケース2：比較カラム (SELECT 句のサブクエリ)

本のテーブルを表示し、各価格の隣に、ストアで **「最も高い本」** との価格差をリアルタイムで表示したい場合はどうすればいいでしょうか？

```sql
SELECT
    title,
    price,
    -- 入れ子のカラム：最大価格との差をリアルタイムで計算
    (SELECT MAX(price) FROM bookstore) - price AS gap_from_luxury
FROM bookstore;

-- 結果：価格差を示す美しい仮想カラムが得られます。
-- これは、動的なビジネスレポートを作成する際に非常に強力な手法です！
```

## 💡 4. シニアの警告：「相関サブクエリ」の惨劇

シニアアーキテクトとして、あなたは「N+1問題によるパフォーマンス死」を避けなければなりません。

**相関サブクエリ（Correlated Subquery）** と呼ばれる危険なタイプのサブクエリがあります。これは、内部クエリが実行のために外部クエリの値を必要とする場合です。

**恐怖のシナリオ：**
*   もし外部クエリが100万行あるとします。
*   SQLロボットは、**内部のサブクエリ全体を100万回再実行**しなければなりません（各行に対して1回）。
*   サーバーのCPUは100%に達し、APIはタイムアウト（エラー504）を起こし、アプリはクラッシュします。

**解決策（5万円の価値があるヒント）：** もし相関サブクエリを書いている自分に気づいたら、すぐに止めてください！ それを **JOIN** に変換しましょう。データベースは高速なバイナリアルゴリズムを使って JOIN を処理するように最適化されています。大規模なデータセットにおいて、JOIN はサブクエリよりも **50倍高速** なことがよくあります。
