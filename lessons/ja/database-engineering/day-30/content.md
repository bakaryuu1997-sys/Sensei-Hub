# Day 30: グランドアーキテクト - 数百万ユーザー向けのシステム設計 🏆

おめでとうございます！SQLに戸惑っていた開発者から、30日間を経てついに**データベースマスター**への道を歩み切りました。

この「卒業の夜」に、新しい理論を学ぶことはありません。代わりに、あなたは**シニアデータベースアーキテクト**として、「100万ドル規模」の課題に挑みます：**1億件の商品と1日100万件の注文を抱えるECプラットフォームのデータインフラ設計**です。

これまでの29日間で得たすべての知恵を絞り出し、持続可能なデータ帝国を築き上げましょう。

## 🏛️ I. 課題の概要：メガスケールの挑戦

設計するシステムは、以下の過酷な要件を満たす必要があります：
1.  **膨大なデータ量：** 1億件の商品と、数千種類の動的な属性（色、サイズ、構成など）。
2.  **超高並列処理：** フラッシュセール時に**秒間50万リクエスト**を処理。
3.  **データ整合性：** 在庫の「オーバーセリング（売り越し）」は一切許容されません。
4.  **AI機能：** ユーザーの好みや「雰囲気」に基づいたインテリジェントな商品推奨。
5.  **リアルタイム分析：** 経営陣向けに秒単位で更新される売上レポート。

## 🏛️ III. 詳細設計戦略

### 1. スマートな商品ストレージ (Hybrid Schema)
*   **リレーショナル構造：** 商品ID、名称、価格、ブランドを正規化された形式で保存し、整合性を確保します。
*   **JSONB (Day 22)：** すべての動的な属性を保存します。
*   **インデックス：** JSONB列に**GINインデックス**を作成し、ミリ秒単位での属性フィルタリングを実現します。
*   **メモリ最適化：** 注文ステータスなどの固定値には文字列ではなく **Enum型** を使用し、ディスク容量を節約しパフォーマンスを向上させます。

### 2. スケーリング戦略：分割統治 (Sharding & Partitioning)
1億件の商品を扱う場合、単一のテーブルではパフォーマンスの限界に達します。
*   **テーブルパーティショニング (Day 24)：** `orders`テーブルを月ごとにパーティショニングします。これにより、今月の注文クエリが数十億件の履歴データをスキャンする必要がなくなります。
```sql
-- アーキテクトのためのパーティショニング例
CREATE TABLE orders (
    order_id SERIAL,
    user_id INT,
    order_date TIMESTAMP NOT NULL,
    total_amount DECIMAL
) PARTITION BY RANGE (order_date);

-- 2026年5月のパーティション作成
CREATE TABLE orders_2026_05 PARTITION OF orders
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');
```
*   **シャーディングキーの選定：** これは死活問題となる決定です。
    *   **良：** `user_id`（ユーザーデータが各ノードに均等に分散される）。
    *   **悪：** `region_id`（特定の地域が他の地域より遥かにアクティブな場合、そのノードだけがクラッシュし、他はアイドル状態になる「ホットスポット」問題が発生します）。

## 🛠️ IV. ハードウェアとOSのチューニング（アーキテクトの秘策）

マスターシステムはデフォルト設定では動作しません。OSのチューニングが必要です：
*   **カーネル最適化：** `vm.swappiness = 1` を設定し、PostgresがRAMの内容をディスクにスワップするのを防ぎます。
*   **Huge Pages：** この機能を有効にして、大規模なメモリ管理を効率化します。
*   **ストレージ：** 最高のIOPS（秒間入出力操作数）を実現するために、**NVMe SSD** と **RAID 10** の構成を必須とします。

---

## 🔒 V. セキュリティの要塞化

*   **行単位セキュリティ (RLS - Day 27)：** アプリのコードにロジックバグがあっても、ユーザーAがユーザーBの注文を絶対に見られないようにします。
*   **データマスキング：** PCI-DSS規格に準拠するため、ログ内のクレジットカード番号などを自動的にマスクします。
*   **監査ログ：** `pgaudit` を使用して、機密性の高いアクション（顧客のウォレット残高を誰が閲覧したかなど）をすべて記録します。

---

## 🚀 VI. ゼロダウンタイム・マイグレーション戦略

Webサイトを停止せずに100億行のデータを移動する方法：
1.  **CDC (Change Data Capture)：** Debeziumなどのツールを使用して、旧DBから新DBへリアルタイムにすべての変更を複製します。
2.  **段階的な切り替え（Phased Cut-over）：** ユーザーの1%を新しいシステムに移動し、問題がなければ10%、50%、100%と増やしていきます。

---

## 🧩 VII. 未来へ：AIとベクトル検索

システムには「知能」が必要です。
*   **pgvector：** 商品のベクトル埋め込み（Vector Embeddings）を保存します。
*   **推奨エンジン：** `<->`（コサイン距離）演算子を使用して、ユーザーが現在閲覧している商品と最も類似度の高い上位10商品を瞬時に見つけ出します。これがAmazonの推奨機能の仕組みです！
