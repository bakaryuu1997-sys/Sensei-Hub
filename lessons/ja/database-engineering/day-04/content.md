# Day 04: データ型 - データの構成材料を分類する 🛠️

偉大なるサーバー（Supabase）はすでに従順に稼働しています。これから、ストレージにおけるあらゆるトラブルの根源、**「データ型（Data Types）」**に踏み込みます。

家を建てるのと同じように、乾燥した木材を保管するのと、液体のガソリンを保管するのでは、全く異なる扱いが必要です。データベースにおいて、薄いガラスでできたキャビネットに鉄ののこぎりを無理やり押し込めば、衝撃が加わったときに悲惨な結果を招きます。

データ型は、サーバー内の各「チェスト（列/カラム）」にラベルを貼り、システムに対して「間違った種類の物を入れさせない」ために存在します。

---

## 🎯 1. 本日の核心的な学習目標

この非常に生き生きとしたレッスンを通じて、あなたは以下のことを脳に刻み込みます：

1.  **4つの構成の柱を掴む：** どんなプログラミング言語でも必ず遭遇する、4つの究極のデータ型グループ（文字列、数値、日付/時刻、論理値）を明らかにします。
2.  **仮想RAM割り当て戦略：** 空の「ビニール袋」（`VARCHAR`）と「巨大なブラックホールバッグ」（`TEXT`）の違いを理解し、ストレージ効率の思考を養います。
3.  **スキーマの可視化：** 電子請求書がデータベースのルールの下でどのように構成されているかを見抜きます。
4.  **ライブコードの執筆：** データを定義し、エラーなくスムーズに動作するテーブルを作成するための構文を自ら書き上げます。

紹介はこれくらいにしましょう。型を間違えるということは、サーバーのRAMを悲鳴を上げさせるということです！さあ、行きましょう！

## 🧠 2. 本質：生産ラインの分類ビン

データベースを、巨大な物流倉庫にある小包仕分け機だと想像してください。
ベルトコンベアは絶えず動いています。NodeJS開発者が小包を投げ入れます。ロボット警察（PostgreSQL管理システム）が各ビンの番をし、すべての小包を検査します：

*   この小包はレンガ（純粋な数値）だ。**レンガ用ビン**へ投げ入れろ。
*   この小包はラブレター（長いテキスト/文字列）だ。**レタートレイ**へ投げ入れろ。
*   この小包は時計（日付と時刻）だ。
    もしコーダーが**ガソリンの瓶**を**レタートレイ**に投げ入れたら、警察はその小包をウェブクライアントの顔に投げ返し、重いエラーを報告します：`Syntax Error: Type Mismatch`（構文エラー：型の不一致）。何も保存されません！

SQLには、アーキテクチャの柱に対応する、明確に定義された4つのデータ型グループがあります：

### 📜 グループ1：柔らかな文字列ロジック (STRING LOGIC)

顧客名、配送先住所、記事のタイトル、Facebookのアバターリンクなどを保存するために使用されます。

*   **VARCHAR(50)** (Variable Character): 直訳すると「可変長文字」。文字を入れる箱だが、最大50スロットまで伸縮自在という意味です。非常にスペース効率が良いです。テキストが短ければ、箱も小さくなります。ユーザー名、メールアドレス、電話番号（先頭に0があるため）に最適です。
*   **TEXT** (無制限のコンテンツ): 「制限なしのプラスチック包装、10ページの論文でも何でも放り込め！」という意味です。これを乱用すると**RAMの災難**を招きます。ブログ記事の本文など、長い説明文に使用してください。短いIDコードなどに使ってはいけません。長いテキストのインデックス作成や検索は、マシンをハングアップさせる原因になります！

### 🔢 グループ2：数学的コア (NUMBER CORE)

このグループには数値のみを投入します。その「秘術」は、数学関数（`加算、減算、乗算、SUM、AVG`）が使えることです。

*   **INTEGER (INT)**: 整数を表します。正、負、または0で、小数はありません（`1`, `100`, `-9`, `10,000,200`）。スコア、購入数、TikTokビデオの「いいね」の数に最適です。
*   **DECIMAL(10, 2) または NUMERIC**: 金融や通貨の価値のチャンピオンです。`10` は全体の桁数、`2` は小数点以下の桁数を表します。例：`残高から 1,450,900.50 セントを引き出す`。銀行業務で計算に `FLOAT` を使うと、プロとしての「刑務所」行きです。なぜなら、`FLOAT` は科学的な「浮動」小数点用で、時間の経過とともにわずかだが壊滅的な誤差（セント単位の紛失）を引き起こすからです！

### ⏳ グループ3：時間の刻印 (DATE / TIMESTAMP)

取引時間をスタンプし、逃さないようにするマシン。日付範囲での検索に非常に貴重です！

*   **DATE**: 年 - 月 - 日 のみを保持します (`1997-03-25`)。正確な出生時間まで気にする必要のない誕生日の保存などに使います。
*   **TIMESTAMP / TIMESTAMPTZ**: 日付からミリ秒、タイムゾーンまでをすべて保持します (`2026-03-04 15:30:20.100+09`)。監査証跡（ハッカーが何時何分何秒にお金を引き出したかを正確に確認する）に不可欠です。

### 💡 グループ4：白黒の切り替え (BOOLEAN)

コンピュータのバイナリ（0 vs 1）の神聖なシンプルさです。

*   `TRUE`（真）または `FALSE`（偽）の2つの値のみを保存します。サーバーへの負荷が最も低い型です。
*   例：`is_vip: TRUE`, `is_paid: FALSE`。ネットワーククエリを極限まで高速化・軽量化します。

## 🏛️ 3. 請求書をデータベースで視覚化する

この知識を使って、iPhoneの注文表示を再現してみましょう：

```ascii
================================================================================
|                    Apple iPhone 購入請求書 (テーブル名: ORDERS)              |
================================================================================
| データベース列ラベル          | 構造化データ型                               |
|-------------------------------|----------------------------------------------|
| 注文ID: 1                    | ( SERIAL / BIGINT ) [自動インクリメント]    |
| 顧客名: 田中 太郎             | ( VARCHAR(150) )                             |
| 合計金額: $1,999.50          | ( DECIMAL(10, 2) )                           |
| 請求時間: 午前 8:00          | ( TIMESTAMP )                                |
| 配送済みか: まだ             | ( BOOLEAN False )                            |
================================================================================
```

もし一つの変数が間違っていたら（例えばフォームから `金額: "後で払う"` と送られてきたら）、PostgreSQLは鉄の定規を振り回し、`Value Mismatch`（値の不一致）エラーを投げ返します。平和は保たれるのです！

## 💻 4. 実践：テーブルを鍛造する

上のスキーマを Supabase SQL Editor でコードにしてみましょう！

**1. 取引テーブルを開設する。**

```sql
-- 注文分類テーブルを作成する（伝説の CREATE TABLE コマンド）
CREATE TABLE tiki_orders (
    id SERIAL PRIMARY KEY,              -- SERIAL: 自動的に 1, 2, 3... と増える魔法
    customer_name VARCHAR(50) NOT NULL, -- 空であってはならない (NOT NULL)
    total_price DECIMAL(10, 2),         -- 正確な金額（小数あり）を保存
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- DEFAULT: サーバーの現在時刻を取得
    is_delivered BOOLEAN DEFAULT false  -- 新しい注文が生まれた時はデフォルトで false
);
```

**2. 最初の粘土をマシンに投入する：**
挿入コマンド (`INSERT INTO`) を使います：

```sql
-- 最初のユーザーオブジェクトをビンに投入する
INSERT INTO tiki_orders (customer_name, total_price)
VALUES ('田中さん', 3500.50);

-- 魔法：ID、created_at、is_delivered を指定していないことに注目してください。
-- それでも、レコードにはそれらが表示されます！なぜでしょうか？
-- CREATEコマンドで書いた DEFAULT 宣言があるからです！
-- マシンが自動的に (1)、現在の時刻、そして (FALSE) を埋めてくれます。
-- 効率的でクリーンです！
```

**3. 内容を検査する：**

```sql
SELECT * FROM tiki_orders;
```

ドーン！！！ クールでクリーンな青いテーブルが目の前に現れます。

## 💡 5. 100万ドル級の最適化ヒント（コスト削減）

昨日はアスタリスク（*）の話でした。今日はRAMの抑制についてです。PostgreSQLの道は「狭さ」にあります：**「適合する最小の形式を選べ」**。

*   **初心者の悪い癖：** データ型を過剰に大きく設定すること。*「顧客名が詩のように長いかもしれないから... `customer_name TEXT` にしておこう」*、あるいは何でもかんでも `VARCHAR(255)` を使うこと。
*   **収益を損なう災難：** インデックス（高速検索メカニズム）が巨大なテキストをスキャンしなければならない場合、ディスクI/OとRAMを浪費します。たとえテキストが20〜50文字であっても、列が巨大に定義されていると、DBが大きくなるにつれて検索が遅くなります。
*   **シニアエンジニアの秘密：** 電話番号は一貫して10〜15桁程度です。`VARCHAR(15)` を使います。暗号化されたパスワードハッシュは通常固定長です。`VARCHAR(60)` を使います。列のサイズを絞ることで、サーバーはスリムで高速なままであり、大規模になっても検索は瞬時に行われます！
