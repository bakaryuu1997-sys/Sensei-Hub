# Day 29: データの復活とディザスタリカバリ (PITR, RTO & RPO) 🛡️

**Day 29**へようこそ。データベースエンジニアの世界には、有名な格言があります：*「世の中には2種類の人間がいる。データを失ったことがある人間と、これからデータを失う人間だ。」* 

今日は、どちらのグループにも属さない方法を学びます。わずか数コマンドで数百万ドルの損失を救う、**「死からの復活」**が可能なシステムを構築する方法を学びます。このレッスンは、普通の開発者と**データベースマスター**を分ける重要な境界線となります。

---

## 🏛️ I. 戦略的マインドセット：RTO vs RPO

コードに触れる前に、ビジネスの言語を理解する必要があります。災害が発生したとき、CEOが気にするのは以下の2つの数字だけです：

### 1. RPO (Recovery Point Objective) - 「どれだけ失うか？」
*   **定義：** 障害発生時点からさかのぼって、どれだけの時間のデータを失っても許容できるかという指標（目標復旧時点）。
*   **シナリオ：** 毎日深夜0時にバックアップを取り、翌日の午後11時にサーバーがクラッシュした場合。そのバックアップしかない場合、RPOは23時間となり、丸一日分の注文データを失うことになります！
*   **マスターの目標：** RPO < 1分（継続的アーカイブを使用）。

### 2. RTO (Recovery Time Objective) - 「復旧にどれくらいかかるか？」
*   **定義：** システムが停止してから復旧するまでにかかる時間の許容値（目標復旧時間）。
*   **シナリオ：** 午前9時にサーバーがクラッシュし、復旧が完了したのが午後1時だった場合。RTOは4時間です。この4時間、会社は収益を上げられません。
*   **マスターの目標：** RTO < 5分（高可用性構成と自動フェイルオーバーを使用）。

## 🏛️ II. 3-2-1 バックアップ戦略（国際標準）

単一のバックアップを決して信用してはいけません。データベースマスターは常にこのルールに従います：
1.  **3つのコピー：**（オリジナルデータ + 2つのバックアップ）。
2.  **2つの異なるメディア：**（例：サーバーのSSD + Amazon S3/Google Cloud Storageなどのクラウドストレージ）。
3.  **1つのオフサイトコピー：** 少なくとも1つのコピーは、完全に異なる地理的リージョン（例：サーバーはシンガポール、バックアップは米国）に保存する必要があります。

## 🚀 III. ポイントインタイムリカバリ (PITR)：タイムマシン

PITRは、データベースを過去の特定の瞬間（ミリ秒単位）に正確に復元できる技術です。これを実現するには、**WAL（ログ先行書き込み）**を理解する必要があります。

### 1. 継続的アーカイブの構成（非常に重要）
`postgresql.conf`を開き、Postgresが変更ログを安全なストレージに継続的にプッシュできるように以下のパラメータを設定します：

```ini
# --- WALアーカイブの構成 ---

# レプリケーションとバックアップに必要なログレベル
wal_level = replica

# アーカイブモードを有効にする
archive_mode = on

# WALファイル（.wal）を安全なアーカイブ場所にプッシュするコマンド
# %p：ソースファイルのパス、%f：ファイル名
archive_command = 'cp %p /mnt/server/archive_logs/%f'

# 60秒ごとにログファイルを強制的に閉じる（RPOを60秒に短縮）
archive_timeout = 60
```

### 2. 「開発者がテーブルを削除してしまった」ときの復旧手順
**午前10:15:30**に、誰かが誤って `DROP TABLE customers` を実行したとします。

**ステップ1：サーバーを直ちに停止します。**
**ステップ2：最新のベースバックアップをリストアします。**
**ステップ3：データディレクトリに `recovery.signal` ファイルを作成します。**
**ステップ4：`postgresql.conf` で復旧パラメータを構成します：**

```ini
# アーカイブからログファイルを取得するためのコマンド
restore_command = 'cp /mnt/server/archive_logs/%f %p'

# 黄金の瞬間：災害が発生するちょうど1秒前に復元する
recovery_target_time = '2026-05-13 10:15:29'

# 復旧後のアクション：'promote' を指定してサーバーをリクエスト受付可能状態にする
recovery_target_action = 'promote'
```
**ステップ5：Postgresを再起動します。** システムは自動的にすべてのログを「再生」し、10:15:29で正確に停止します。`customers` テーブルが戻ってきました！

## 🏛️ IV. 主要なバックアップツールの比較

| ツール | メカニズム | メリット | デメリット |
| :--- | :--- | :--- | :--- |
| **pg_dump** | 論理バックアップ (SQL) | 可読性が高い、バージョンに依存しない。 | 大規模DBでは遅い、PITR非対応。 |
| **pg_basebackup** | 物理バックアップ (Binary) | 高速、PITR対応。 | 同じPostgresバージョンに復元する必要がある。 |
| **pgBackRest** | **（推奨）** | 圧縮、並列転送、S3/Azure対応。 | 構成がやや複雑。 |
| **WAL-G** | クラウドネイティブ | クラウド/Kubernetes環境に最適化。 | Goやクラウドの知識が必要。 |

## 🔬 V. 実践ラボ：現実世界の復旧シナリオ

ローカルマシンで試せるシミュレーションラボです：

### ステップ1：サンプルデータと初期バックアップの作成
```sql
-- 機密テーブルの作成
CREATE TABLE secret_vault (
    id SERIAL PRIMARY KEY,
    data TEXT,
    created_at TIMESTAMP DEFAULT now()
);

-- 「死守すべき」データの挿入
INSERT INTO secret_vault (data) VALUES ('金庫コード: 1234'), ('VIP顧客データ');

-- [ここで pg_basebackup を使用して物理バックアップを実行]
-- pg_basebackup -D /tmp/backup_full -P -v
```

### ステップ2：バックアップ後のデータ挿入（これはWALに残ります）
```sql
INSERT INTO secret_vault (data) VALUES ('午前9時の新しいトランザクション');
INSERT INTO secret_vault (data) VALUES ('午前10時の新しいトランザクション');
```

### ステップ3：災害発生（午前10:05）
```sql
-- エンジニアが誤ってデータを消去
DROP TABLE secret_vault;
```

### ステップ4：復活（PITR）の実行
1. データベースを停止します。
2. 現在の `data` ディレクトリを削除します。
3. `/tmp/backup_full` を `data` ディレクトリに展開します。
4. `recovery.signal` ファイルを作成します。
5. `recovery_target_time = '2026-05-13 10:04:59'` を構成します。
6. 再起動して確認します：`SELECT * FROM secret_vault;` 
=> 結果：午前9時と10時のデータが含まれた状態でテーブルが戻っています！

## 🏛️ VI. 高可用性 (HA)：決して死なないシステム

バックアップは災害後の復旧のためのものですが、**HA**はそもそもシステム停止を防ぐためのものです。

### 1. レプリケーション
*   **同期レプリケーション：** PrimaryはSlaveの書き込み完了を待ってからアプリに成功を返します。（絶対的な安全だが低速）。
*   **非同期レプリケーション：** Primaryは書き込み後に即座に完了し、Slaveは後で更新されます。（高速だが、数ミリ秒のデータ紛失のリスクあり）。

### 2. Patroniによる自動フェイルオーバー
**Patroni**はPostgresのためのスマートなマネージャーです。
*   Primaryの健全性を継続的にチェックします。
*   Primaryがダウンした場合、PatroniはEtcd/Consulと連携してSlaveの中から新しいPrimaryを選出します。
*   プロセス全体が自動的に行われ、30秒以内に完了します。

## 📚 VII. マスターDBA用語集

*   **WAL (Write-Ahead Log)：** ディスクに保存する前にすべての変更を記録する日記。
*   **LSN (Log Sequence Number)：** WALログ内のすべての位置を指す一意の識別子。
*   **チェックポイント：** PostgresがRAMからディスクにすべてのデータをフラッシュするプロセス。
*   **タイムラインID：** データ履歴の特定の「分岐」を指す一意の識別子。
*   **ベースバックアップ：** ある時点でのデータベースの完全な物理コピー。

## ⚠️ VIII. よくある落とし穴（DBAの知恵）

1.  **WALファイルのクリーンアップ忘れ：** `archive_command` は継続的に実行され、ディスクをすぐに埋めてしまいます。`pgbackrest` などのツールを使用して、古いバックアップを自動的に削除してください。
2.  **リストアの未テスト：** バックアップ成功100%は、リストアできることを意味しません。毎月リストアテストを行ってください。
3.  **同じRAIDへのバックアップ：** RAIDカードが故障すると、オリジナルとバックアップの両方を失います。
4.  **権限：** バックアップファイルの権限は0600である必要があります。公開されると、ハッカーはデータベースに入ることなくデータを盗むことができます。
