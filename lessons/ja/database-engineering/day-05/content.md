# Day 05: Table, Column ＆ Row - データの「家」を建てる 🏛️

あなたは今、「建設許可証」（PostgreSQL）を手に入れ、「建設資材」（データ型）の選び方も分かりました。今日は、実際にクワとシャベルを手に取り、基礎を掘り、地球上のあらゆるリレーショナルデータベース（SQL）の最も神聖で根源的な3つの概念である **Table（テーブル）**、**Column（列/カラム）**、**Row（行/レコード）** を使って家の骨組みを立ち上げます。

この骨組み作りの段階で設計を一つでも間違えれば、1年後にアプリケーションが数百万人の顧客を抱えて本番稼働したとき、システム全体が修復不可能なほど崩壊することになります。

## 🎯 1. 本日の作戦目標

このレッスンの終わりには、あなたの脳は以下の知識バッテリーで満たされているはずです：

1.  **明確な区別：** 「家庭用薬箱」の例えを通じて、テーブル、カラム、レコードの機能と役割を正しく定義できるようになります。
2.  **基礎打ちの技術（DDL）：** テーブル作成コマンド（`CREATE TABLE`）を習得し、構造的なフレームワークを理解します。
3.  **鉄筋注入の技術（DML）：** データ挿入コマンド（`INSERT INTO`）を習得し、空のキャビネットを価値ある宝庫に変えます。
4.  **最適化された設計思考：** サーバーのRAMを浪費させる「肥大化したスキーマ（Bloated Schema）」という病を回避する方法を知ります。

## 🧠 2. 本質：「薬箱」の理論

多くの大学教授は、Excelの構造を使ってテーブル、行、列を説明しようとします。しかし、それはDay 1で打ち砕いた「Excelの死の罠」との混同を招きやすいです。
私たちは、物理的かつ幾何学的で非常に分かりやすい例を使います：**病院の薬棚**です。

あなたの `general_hospital` データベース全体が、非常に広く空っぽの保管室だと想像してください。

### レベル1：テーブル (Table) - 独立したキャビネット
（NoSQLのダンボール箱方式のように）床に物を散らかさないために、あなたは**独立した木製キャビネット**を計測して購入します。
各引き出し（Drawer）には明確なラベルが貼られています：

*   引き出し1：**目薬**専用（テーブル `eye_drops`）。
*   引き出し2：**胃腸薬**専用（テーブル `stomach_meds`）。

**鉄の掟：** あなたは明確に定義します。絶対に目薬の引き出しに胃腸薬を混ぜてはいけません。間違えれば、患者が失明するかもしれません！データベースにおいて、この概念は**エンティティの分離（Entity Isolation）**と呼ばれます。`users` という名前のテーブルには、絶対に `products` の情報を保存してはいけません。

### レベル2：カラム (Column) - 構造の宣言ラベル
目薬の引き出しを引くと、中の仕切りに3つの強制的なラベルが貼られており、看護師は薬を入れる前に必ずこれに従わなければなりません：

*   **仕切り1（薬名）：** 文字のみを受け付ける（VARCHAR）。
*   **仕切り2（使用期限）：** 日付でなければならない（DATE）。
*   **仕切り3（価格）：** 金額でなければならない（DECIMAL）。

データベースにおいて、**カラム（列）**とはこれらの規則のことです。それは、そのテーブルに入れられるすべてのものの「構造」を形作ります。それは入れ物そのものではなく、**「入れ物の枠組み（スキーマの基礎）」**なのです。

### レベル3：レコード (Row / Record) - 実際の薬のシート
今、診療所から看護師がやってきて、昨日12ドルで購入した2026年期限の「パナドール・エクストラ」のシートを渡してくれました。
あなたの手にあるその実物のパナドールには、枠組みが要求する3つの情報がすべて含まれています：

1.  名前 = "パナドール・エクストラ"
2.  期限 = "2026-01-01"
3.  価格 = 12.00

看護師は喜んでこのシートを薬棚の引き出しに入れます。おめでとうございます！あなたは今、**1行のデータ（1 ROW / 1 RECORD - 実在するハードデータの存在）**を手に入れました。

薬のシート1枚が1つの「行（Row）」と呼ばれます。
100万人の顧客を抱える倉庫は、100万行のレコードを持つ倉庫です。データベースはカラムを眺めるだけでなく、レコード（行）によって生きているのです！

```ascii
[テーブル: 風邪薬カタログ]

<<<< ここはカラム（列）エリア - 建築的な骨組み >>>>
+--------------+------------------+-----------------+-------------------+
| ID (INT)     | 薬名 (VAR)        | 期限 (DATE)     | 在庫あり (BOOL)   |
+--------------+------------------+-----------------+-------------------+
| 1            | パナドールX      | 2026-01-01      | TRUE (在庫あり)   | <─ 実際の薬シート (ROW 1)
| 2            | ティフィーパック | 2024-12-10      | FALSE (在庫なし)  | <─ 実際の薬シート (ROW 2)
| 3            | デコルゲン感冒薬 | 2027-04-15      | TRUE (在庫あり)   | <─ 実際の薬シート (ROW 3)
+--------------+------------------+-----------------+-------------------+
```

## 💻 3. SQL実践：電子雑誌の構築
今日は、ハイテク雑誌（VergeやWiredのようなもの）のリードアーキテクトの役割を担います。SQLを使って記事を保存するためのデータベースを構築する必要があります。

*(ちょっとした秘密：開発者は、テーブルの枠組みを書くことを **DDL**（データ定義言語）、データを注入することを **DML**（データ操作言語）と呼びます。これらを覚えておくと上司を感心させられるかもしれません！)*

**ステップ1：基礎の作成 (CREATE TABLE - DDLコマンド)**
SupabaseのSQL Editorにアクセスし、以下を入力してください！

```sql
CREATE TABLE articles (
    -- カラム1: 記事ID（究極の識別子）
    id SERIAL PRIMARY KEY,
    -- カラム2: タイトルは必須、空であってはならない (NOT NULL)
    title VARCHAR(300) NOT NULL,
    -- カラム3: 無制限のコンテンツ、文字があることを強制する
    body_content TEXT NOT NULL,
    -- カラム4: ペンネーム（RAMを節約するために短い文字列）
    author_alias VARCHAR(50),
    -- カラム5: 公開済みか下書きか？ - デフォルトは False (下書き)
    is_published BOOLEAN DEFAULT false,
    -- カラム6: 生成時間を記録 - DEFAULT: サーバーの現在時刻
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**Run** を押してください！基礎がデータベースの地殻に打ち込まれました。

**ステップ2：空のキャビネットに記事を流し込む (INSERT INTO - DMLコマンド)**

```sql
INSERT INTO articles (title, body_content, author_alias)
VALUES (
    '初心者のためのデータベース爆速習得術',
    '私たちは、プロジェクトの予算を劇的に節約するために、高速な行ロック（Row Locking）アーキテクチャを採用しました...',
    'コードの達人ナム'
);

-- is_published や created_at に値を挿入する必要はありません！
-- ステップ1で書いた DEFAULT 宣言によって自動的に処理されます。
```

**ステップ3：結果を確認する：**

```sql
-- 存在するデータ構造をすべて表示するコマンド
SELECT id, title, is_published, created_at FROM articles;
```

ロボットが完璧に整理されたコレクションを返してくれます。IDは1、`is_published` は False。すべてが完璧です！

## 💡 4. エリートエンジニアの最適化ヒント（核心的な哲学）

これらの概念を侮ってはいけません。エリートエンジニアを悩ませる「**Bloated Schema**（肥大化したスキーマ）」という言葉を知っていますか？

エリートシステム設計の不文律：

> **「列（カラム）は高価な金である！行（レコード）は道端に落ちている安いキャンディである。」**

*   AmazonやNetflixのようなアプリがあるとします。そのアプリには1億**行（レコード）**の顧客データが含まれています。1億行あっても、データベースは電光石火の速さで動作します。
*   **しかし！！** もしあなたのテーブル（例えば `users` キャビネット）が愚かにも**横に150個のカラム**を持つように設計されていたら（名前、年齢、電話番号、趣味、車の種類、ペットの名前、元カノのウエストサイズ...すべてを詰め込もうとした場合）、すべてのデータベースアーキテクトは恐怖で叫ぶでしょう。
*   問題は、わずか数個のデータを探すためだけに、このように横に長くて肥大化した行をスキャンすることが、RAMやディスクI/Oに非常に大きな負荷をかけることです。データベースは苦しみ、窒息します。

**生存のためのヒント：**
中心となる `users` テーブルは、できるだけスリムで最小限に保ってください。もし追加の、二次的な詳細（趣味、犯罪歴など）がある場合は、**それらを別のテーブルに分けてください**（例： `user_details_extra`）。そして関連付け用の列（外部キー - 明日学びます）を使用します。冗長性を徹底的に排除することで、美しく密度の高い建築的なメッシュが出来上がります！
