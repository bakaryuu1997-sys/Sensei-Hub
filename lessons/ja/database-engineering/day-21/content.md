# Day 21: 見えない自動化ツール - データベース・トリガー 🔫

Day 21 へようこそ！ 昨日は、関数とプロシージャを使ってデータベース内部にロジックを記述する方法を学びました。今日はさらに一歩進んで、**「自動化」** を学びます。

**トリガー (Trigger)** とは、特定のイベント（INSERT, UPDATE, DELETE）を「監視」し、それが発生したときに関数を自動的に実行するデータベースオブジェクトです。バックエンドから呼び出す必要はありません。データベースが自ら「反応」するのです。

---

## 🎯 1. 本日の戦略的目標

1.  **トリガーの基本：** 「イベント・条件・アクション」のループ構造を理解します。
2.  **監査ログ (Audit Logging):** セキュリティとコンプライアンスのために、すべてのデータ変更を記録します。
3.  **自動計算：** 合計値やステータスフラグを自動的に同期させます。
4.  **パフォーマンスの警告：** トリガーがシステムを低速化させる「隠れた罠」になるケースを学びます。

---

## 🧠 2. 哲学：データの「防犯カメラ」

**トリガー**を、**「特殊なAIを搭載した防犯カメラ」** だと考えてみてください。

- **標準的な関数：** 写真を撮るために、あなたがボタンを押す必要があります。
- **トリガー：** カメラが動き（データの変更）を検知すると、あなたが何もしなくても自動的にイベントを記録し、アラームを鳴らし、カウンターを更新します。

```ascii
[ データベース・トリガーのワークフロー ]

       ユーザーの操作 (SQL コマンド)
           |
           |   1. 注文 (orders) を INSERT
           V
  +-----------------------------------+
  |      トリガーの門番 (監視中)       |
  |  (BEFORE または AFTER をチェック)  |
  +-----------------------------------+
           |
           |   2. イベント検知！
           V
  +-----------------------------------+
  |      トリガー関数が発動           |
  |  - 変更前のデータをログに記録     |
  |  - 顧客の合計残高を更新           |
  |  - 通知を送信                     |
  +-----------------------------------+
           |
           |   3. アクション完了
           V
       データベースが永久に更新される
```

## 💻 3. 実戦 SQL：監査ログを作成する

プロフェッショナルなアプリケーションには、必ず **「監査ログ (Audit Log)」** が必要です。ユーザーの残高が変わったとき、「誰が？ いつ？ 変更前の値は何だったか？」を知る必要があります。

### ステップ 1：監査用テーブルの作成
```sql
CREATE TABLE balance_audit_log (
    id SERIAL PRIMARY KEY,
    user_id INT,
    old_balance NUMERIC,
    new_balance NUMERIC,
    changed_at TIMESTAMP DEFAULT NOW()
);
```

### ステップ 2：トリガー関数の作成
```sql
CREATE OR REPLACE FUNCTION log_balance_changes()
RETURNS TRIGGER AS $$
BEGIN
    -- 残高が実際に変更された場合のみ記録する
    IF OLD.balance IS DISTINCT FROM NEW.balance THEN
        INSERT INTO balance_audit_log(user_id, old_balance, new_balance)
        VALUES (OLD.id, OLD.balance, NEW.balance);
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

### ステップ 3：テーブルにトリガーを設定する
```sql
CREATE TRIGGER trigger_balance_audit
AFTER UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION log_balance_changes();
```

これで、`UPDATE users SET balance = ...` を実行するたびに、データベースが自動的に履歴を `balance_audit_log` に記録します。Node.js 側に一行もコードを追加する必要はありません！

## 💡 4. シニアの秘密：トリガーの副作用（ステルス・トラップ）

トリガーは強力ですが、危険も伴います。1行のインサートのたびに5つの他のテーブルを更新するトリガーがある場合、1万行の一括インサートを行うとデータベースは **「ギブアップ」** してしまいます。

**CTOからの警告：**
- **不可視性：** トリガーは「見えない」ロジックです。バグが発生した際、バックエンド開発者にとって、DB内部で「魔法のように」変更が起きているため、デバッグが非常に困難になります。
- **再帰：** 「トリガーの無限ループ」に注意してください（トリガーAがテーブルBを更新し、それがトリガーBを呼び出し、またテーブルAを更新する……）。これはサーバーを一瞬でクラッシュさせます。

**鉄則：** トリガーは **監査 (Auditing)** や **整合性の維持** に使用し、ロジックは可能な限りシンプルかつ高速に保ってください。
