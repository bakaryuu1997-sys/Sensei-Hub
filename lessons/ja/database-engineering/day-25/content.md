# Day 25: 専属ボディーガード - 行レベルセキュリティ (RLS) 🛡️

**Day 25** へようこそ。今日は PostgreSQL の最も強力な機能の一つであり、SaaS (Software as a Service) 開発において圧倒的な優位性をもたらす秘密兵器、**行レベルセキュリティ (RLS)** について探究します。

Slack や Jira のようなアプリを構築していると想像してください。数千の企業（テナント）が一つのデータベースを共有しています。
- **危険な方法:** バックエンドコードに頼って、すべてのクエリに `WHERE company_id = 123` を追加します。もしジュニア開発者がレポートページでこの条件を一つでも書き忘れれば、企業 A のデータが企業 B に漏洩します。これはレベル1のセキュリティ大惨事です。
- **シニアアーキテクトの方法:** RLS を設定します。データベースは **カーネルレベル** でフィルタリングを強制します。バックエンドは単に `SELECT * FROM orders` と書くだけでよく、データベースはログインユーザーの企業に属する行だけを自動的に返します。

## 🎯 1. 本日の戦略的目標

1.  **RLS の実行メカニズム:** PostgreSQL がクエリに「密かに」フィルタリング条件を注入する仕組みを理解します。
2.  **Permissive (許容) vs Restrictive (制限) ポリシー:** 「開いたドア」と「厳格なゲート」ポリシーの違いを理解します。
3.  **SaaS マルチテナントのマインドセット:** 階層的な権限設計 (User < Manager < Admin)。
4.  **セッション変数のマスター:** `current_setting()` を使用した柔軟な RLS カスタマイズ。
5.  **パフォーマンス・ベンチマーク:** RLS はシステムを遅くするか？ ポリシーの最適化方法。
6.  **RLS と外部キー:** ユーザーが参照テーブルを見る権限がない場合でも、データの整合性を確保する方法。

## 🧠 2. 哲学：「身元のレンズ」

データテーブルを、数千人の取引を記録した巨大な台帳だと考えてください。

- **RLS なし:** 台帳を開いた人は誰でも、すべてのページを見ることができます。
- **RLS あり:** 台帳は特殊な「あぶり出し」のインクで書かれています。各ユーザーには専用のフィルター眼鏡が渡されます。ユーザー A が本を見ると、自分の取引だけが浮き上がり、他の行は白紙のままに見えます。

### ASCII Diagram: SaaS における RLS アーキテクチャ

```text
       [バックエンドアプリ] -> "SELECT * FROM transactions;"
              |
              V
  +---------------------------------------+
  |      POSTGRESQL クエリ・リライター      |
  | (ユーザー 'org_id_789' を識別)         |
  +---------------------------------------+
              |
              | [ポリシーを自動注入]
              V
  "SELECT * FROM transactions WHERE org_id = 'org_id_789';"
              |
              V
  +---------------------------------------+
  |           ストレージエンジン            |
  | (インデックス内の一致する行のみをスキャン) |
  +---------------------------------------+
              |
              V
       [安全な結果を返却]
```

## 🛠️ 3. 実戦シナリオ (高度な実装)

### ステップ 1：有効化と基本設定
```sql
CREATE TABLE projects (
    id SERIAL PRIMARY KEY,
    name TEXT,
    team_id UUID NOT NULL,
    is_public BOOLEAN DEFAULT false
);

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
```

### ステップ 2：階層的なアクセス権限
以下の要件を実装します：
1. Public プロジェクトは誰でも閲覧可能。
2. チームメンバーは自分のチームの Private プロジェクトを閲覧可能。

```sql
-- 公開プロジェクト用ポリシー (Permissive)
CREATE POLICY "Public projects are visible to everyone" 
ON projects FOR SELECT 
USING (is_public = true);

-- チームメンバー用ポリシー (Permissive)
-- auth.uid() は Supabase の関数で、現在のユーザー ID を取得します
CREATE POLICY "Team members can view private projects" 
ON projects FOR SELECT 
USING (
    auth.uid() IN (
        SELECT user_id FROM team_members WHERE team_id = projects.team_id
    )
);
```

## ⚡ 4. シニアの秘密：ポリシーのパフォーマンス最適化

> [!CAUTION]
> **パフォーマンスの罠:** ポリシー内に複雑なネストされた `SELECT` (サブクエリ) がある場合、PostgreSQL はメインテーブルの **すべての行** に対してそのサブクエリを実行する可能性があります。
> 結果：100万行のテーブルが100万回のサブクエリを誘発し、サーバーがクラッシュします！

**アーキテクトの解決策：**
1. **JWT クレームの利用:** `team_members` テーブルをクエリする代わりに、ログイン時に JWT トークンの中に `team_id` を含めます。PostgreSQL はテーブル結合なしで JWT から極めて高速に読み取れます。
2. **権限の非正規化:** 必要に応じて、行自体の JSONB カラムに権限情報を保存します。
3. **インデックスは必須:** ポリシーの `USING` 句で使用されるカラムには必ずインデックスを貼ってください。

## 💡 5. プロフェッショナルな RLS デバッグ

なぜユーザーにデータが見えすぎるのか、あるいは全く見えないのか？

```sql
-- SQL エディタ内でユーザーの身元をシミュレートしてポリシーをテスト
BEGIN;
SET LOCAL role = 'authenticated';
SET LOCAL "request.jwt.claims" = '{"sub": "user_uuid_here"}';

-- テストクエリの実行
SELECT * FROM projects;

ROLLBACK;
```
