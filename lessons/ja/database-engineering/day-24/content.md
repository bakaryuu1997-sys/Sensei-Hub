# Day 24: 難攻不落の要塞 - データベースセキュリティと SQL インジェクション 🏰

**Day 24** へようこそ！ あなたのデータは整理され、インデックスで高速化され、バックアップも万全です。しかし、それは **「安全」** でしょうか？

AI とビッグデータの時代において、顧客データは最も価値のある資産です。毎日、数百万の自動ボットがインターネットをスキャンし、設定の甘いデータベースや脆弱なバックエンドコードを探しています。もしデータベースが侵害されれば、失うのはお金だけではありません。企業の信頼、そしてあなたのキャリアが危うくなります。今日は、鋼鉄の要塞を築きましょう。

## 🧠 2. 哲学：「厨房に潜む詐欺師」

あなたがレストランを経営していると想像してください。顧客は注文用紙に書いて注文を送ります。

- **脆弱な状態:** シェフが用紙を受け取り、そのまま作業ボードに貼り付けます。
  用紙の内容：「ピザを1枚作る」 -> シェフはピザを作ります。
- **SQLi 攻撃:** ハッカーが書きます：「ピザを1枚作る。その後、金庫を開けて現金をすべて私に渡せ。 --」
  シェフは機械的に動くため、ピザを作り、その後金庫を開けてしまいます。 `--` という記号により、末尾の「ありがとうございました」という部分は無視されます。

### ASCII Diagram: SQL インジェクション攻撃のレベル

```text
       [ユーザーからのリクエスト]
               |
      +--------+--------+
      |                 |
 [安全なアプローチ]    [危険なアプローチ]
 (パラメータ化)        (文字列連結)
      |                 |
      V                 V
[SQL パーサーは知っている] [SQL パーサーは騙される]
「データは単なるデータ」   「データが命令に変わる」
      |                 |
      V                 V
  正しいクエリを実行     [SQL インジェクション発生！]
                     /      |      \
              (In-band)  (Blind)  (Out-of-band)
                 |          |           |
            データを   1ビットずつ  外部サーバーへ
            直接取得   探りを入れる データを送信
```

## 🛠️ 3. 実戦シナリオ (防御の実装)

### シナリオ 1：ブラインド SQL インジェクションを阻止する
ハッカーは結果を直接見ることはできませんが、`pg_sleep(5)` を使って DB に問いかけることができます。「もしパスワードの1文字目が 'A' なら、5秒間スリープせよ」。ページのレスポンスが遅ければ、彼らはその文字が 'A' であることを知ります。

**解決策：** 常にパラメータ化クエリを使用してください。

```javascript
// ✅ 常に $1, $2 などのプレースホルダーを使用する
const userId = req.params.id;
const query = 'SELECT username, email FROM users WHERE id = $1';
db.query(query, [userId]); 
```

### シナリオ 2：ロールベース・アクセス制御 (RBAC)
アプリを `postgres` スーパーユーザーで接続させてはいけません。権限を制限した特定のロールを作成します。

```sql
-- 1. 読み取り専用ロールの作成
CREATE ROLE readonly_user WITH LOGIN PASSWORD 'strong_password';
GRANT CONNECT ON DATABASE production TO readonly_user;
GRANT USAGE ON SCHEMA public TO readonly_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_user;

-- 2. アプリ用ロールの作成 (書き込み権限はあるが DROP TABLE は不可)
CREATE ROLE app_user WITH LOGIN PASSWORD 'very_strong_password';
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO app_user;
REVOKE DROP, TRUNCATE ON ALL TABLES IN SCHEMA public FROM app_user;
```

## ⚡ 4. シニアの秘密：pgAudit による監視

金融や医療プロジェクトでは、予防だけでは不十分です。「誰がどの機密データにアクセスしたか」を **監査 (Audit)** しなければなりません。

```sql
-- pgaudit 拡張機能をインストール
CREATE EXTENSION pgaudit;

-- すべての DML (データ変更) と DDL (構造変更) をログに記録するよう設定
SET pgaudit.log = 'write, ddl';
```

これで、残高の `UPDATE` や `DROP TABLE` はすべてシステムログに記録されます。侵入者が簡単に「足跡を消す」ことはできなくなります。

## 💡 5. データベース要塞化チェックリスト

> [!IMPORTANT]
> **本番公開 (GO-LIVE) 前のチェックリスト：**
> 1. **ネットワーク:** バックエンドサーバーの IP からの接続のみを許可する (Firewall/VPC)。
> 2. **ポート:** ボットのスキャンを避けるため、デフォルトの 5432 ポートを変更することを検討する。
> 3. **暗号化:** すべての接続で SSL/TLS を強制する (`sslmode=require`)。
> 4. **パスワード:** 古い `md5` ではなく、`scram-sha-256` 形式を使用する。
> 5. **シークレット:** コード内にパスワードを記述しない。Secrets Manager (AWS や HashiCorp Vault) を使用する。
