## 🧠 2. アーキテクチャ：配車サービスの3層エコシステム

私たちのデータベースには、1対多（1-to-Many）の関係でつながった三つの「キャビネット（テーブル）」があります。

*   **キャビネット1 (drivers):** ハンドルを握るヒーローたちの個人情報を保存します。
*   **キャビネット2 (rides):** リクエストされたすべての配車記録。`driver_id` を通じて `drivers` にリンクされます。
*   **キャビネット3 (payments):** 回収された代金の記録。`ride_id` を通じて `rides` にリンクされます。（重要：キャンセルや失敗により、すべての配車に支払いがあるわけではありません！）

### ER図（エンティティ関係図）

```ascii
 ++ ビジネス・インテリジェンス・スキーマ - 配車サービスのコア ++

   [ テーブル: drivers ] 1 ---------------- N [ テーブル: rides ] 1 ---------------- N [ テーブル: payments ]
   [PK] id                                 [PK] id                             [PK] id
        driver_name                             customer_name                       amount_usd
        city                               [FK] driver_id (アンカー)                payment_status
                                                is_completed (完了フラグ)      [FK] ride_id (アンカー)

  (ロジック：一人のドライバーは多くの配車を担当する。一つの配車には複数の支払い試行がある場合がある。
   支払いのない「ゴースト配車」も存在する。)
```

## 💻 3. ミッション：「エリート・ドライバー」分析レポート

**CEOからのタスク：**
> _「CTO、'Saigon' 市のレポートが必要だ。完了した配車から合計で『5,000ドル以上』を稼いだ全ドライバーの名前を見たい。もしドライバーが存在するがまだ稼いでいない場合は、合計を '$0' と表示してくれ。稼ぎが多いドライバーが一番上にくるようにソートしてくれ！」_

これを解決するには、**JOIN**、**GROUP BY**、**SUM**、**COALESCE**、**HAVING**、そして **ORDER BY** を一つのエレガントな一撃で組み合わせる必要があります。

### 実戦 SQL コード：

```sql
SELECT
    d.driver_name,
    d.city,
    -- 安全装置：SUMがNULL（支払いなし）の場合、0に置き換える
    COALESCE(SUM(p.amount_usd), 0) AS total_earnings
FROM drivers AS d
-- 結合の連鎖：Drivers -> Rides -> Payments をつなぐ
LEFT JOIN rides AS r ON d.id = r.driver_id
LEFT JOIN payments AS p ON r.id = p.ride_id

-- フィルタ1：生データレベル（集計前）
WHERE d.city = 'Saigon'
  AND r.is_completed = TRUE
  AND p.payment_status = 'COMPLETED'

-- 集計：ドライバー固有の識別子でグループ化
GROUP BY d.id, d.driver_name, d.city

-- フィルタ2：集計レベル（計算後）
HAVING SUM(p.amount_usd) > 5000

-- 最終仕上げ：稼ぎの多い順にソート
ORDER BY total_earnings DESC;
```

**なぜこれがシニアレベルなのか：** これを一つのクエリで行うことで、データベースエンジンがメモリ使用量を最適化します。もしこれを Node.js で100万行に対して行おうとすれば、サーバーはメモリ不足でクラッシュするでしょう。データベースならミリ秒単位で処理できます。

## 💡 4. CTOの秘密：マスター・レプリカ (504タイムアウトの防止)

会社が1,000万ユーザーに成長すると、大きな問題にぶつかります： **「レポートによるデッドロック」** です。

上記のような巨大なBIレポートを実行すると、SQLロボットは大量のCPUとディスクI/Oを占有します。同時に顧客が配車を予約しようとすると、データベースが「レポート計算で忙しすぎる」ため、その `INSERT` コマンドがブロックされる可能性があります。これが、悪名高い **504 Gateway Timeout** の原因です。

**解決策：リードレプリカ（Read-Only Replicas）。**

ハイエンドな企業は二つのデータベースサーバーを設置します：
1.  **マスターDB：** すべての「書き込み」（新規配車、新規支払い）を処理します。高速でスリムに保たれます。
2.  **リードレプリカ：** マスターのリアルタイムな「クローン」です。**すべてのBIレポートやマーケティングのクエリはこちらに送信されます。**

たとえレプリカでレポートに30秒かかったとしても、マスターDBは顧客のために100%高速でレスポンスを返し続けることができます。これが、決してダウンしない「ワールドクラス」のシステムを構築する方法です。
