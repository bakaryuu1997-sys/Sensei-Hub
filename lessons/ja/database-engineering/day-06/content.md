# Day 06: 主キー ＆ 外部キー - 永遠の絆を紡ぐ鎖 🔗

昨日のDay 05では、木板を削って「キャビネット（テーブル）」を作成しました。
キャビネットが一つしかないうちは、すべてが順調に見えました。しかし、ソフトウェアエンジニアリングの世界において、たった一つのテーブルしか持たないアプリケーションを書くことは決してありません。

基本的なLazadaやShopee（ECアプリ）であっても、顧客キャビネット（Users）、製品キャビネット（Products）、注文キャビネット（Orders）、レビューキャビネット（Reviews）が必要です。
もしこれらのキャビネットがハードドライブ上で互いに独立してバラバラに存在していたら、それは「価値のない混乱」と呼ばれます。顧客は自分がどの注文を持っていて、どれを支払えばいいのか、どうやって知ればいいのでしょうか？

**だからこそ、データベースにはシステム全体に命を吹き込む統一概念が必要なのです：それが「リレーショナル（関係性）」データベースです。**

このリレーショナルな力は、このコースで最も重要な二つの知的な絆、**主キー（Primary Key - PK）** と **外部キー（Foreign Key - FK）** にかかっています。

---

## 🎯 1. 本日の鋭い学習目標

強力な「キー（鍵）」の領域に足を踏み入れるにあたり、あなたは以下の強力な力を手にすることになります：

1.  **位置特定の真髄（主キー）：** 名前や年齢が不明であっても、データベースが何百万もの「ゴミ」のような行の中から特定のオブジェクトを完璧に特定できる理由を理解します。
2.  **主従関係の連結技術（外部キー）：** 補助的なテーブルを、巨大な「親の骨」に生物学的に連結させ、「孤児データ（Orphan Data）」の災難を防ぐメカニズムを学びます。
3.  **SQL実戦の儀式：** 命を繋ぎ合わせるコードを実行し、不正なリンクを挿入しようとした際にデータベースから受ける「拒絶」を体験します。

同盟を起動させましょう！

## 🧠 2. 宿命的な哲学：生と死を分かつIDカード

現実世界のロジックをSQLの構造設計に持ち込んでみましょう：

### 第一の柱：存在の識別子（主キー - PK）

あなたの名前が「1992年生まれ、東京在住の田中太郎」であることは重要ではありません。人間にとって、私たちはあなたを見て、視覚的に認識します。しかし、「霊的に欠陥のある」マシンにとって、文字を読むのは疲れる作業であり、画像（特に同じ年齢、同じ出身地の田中太郎が何十人もいる場合）を比較するのは困難です。

RDBMSの脳は、一つの壊れない線を好みます：**「一意の、ICチップ付きのマイナンバーを割り当てること」**。

例：ナムさんは `ID: 001`、ランさんは `ID: 002` です。名前を変えようが、髪を赤く染めようが、別の街に引っ越そうが、そのIDは一生ついて回ります。
**データベースにおいて：** それは車のナンバープレートのようなものです。それは1つの行（Row）の永遠のステータスを維持し続け、静かに座っています。もしある日、アプリがレコードを探す必要があれば、バイナリインデックス化されたIDで検索する方が、テキストの海をフィルタリングするよりも何十億倍も速いのです！

### 第二の柱：従属的なリンク（外部キー - FK）

「リレーショナル」な力が宿るのは、あるテーブルが自分の親の「元のPK」を自分の中に持っているときです。

分かりやすい例：あなた（顧客UID 001）がジムの受付に行き、入会手続きをします。受付係は、3ヶ月分のジムパスのために3枚の請求書を発行します。データベースの世界では、`orders` テーブルに3つの注文行（Row）がプリントされます。
これら3枚の請求書が「あなた（顧客 001）」のものであることを証明するために、すべての請求書にあなたの名前や電話番号をいちいち書き直す必要はありません。請求書の隅に **「所有者ID: 001」** というコードを刻み込むだけでいいのです！

*その刻まれた番号がFKです。それは親のPK（001）のへそに深く噛み付いています！* それらが二人をロックします。コードはUIDを辿って所有者を見つけるだけです。クリーンで効率的、そして冗長なデータもありません！

## 💻 3. 実戦コード：絆を紡ぐ（SQLキーの儀式）

今日は、単にセメントを流し込むだけでなく、構造的なフックをセットアップするため、これまでよりも技術的な記述が重くなります。Supabaseでジム会員アプリを作ってみましょう！

**>> ステップ1：まず親となるマスターテーブルを作成する（必須の独立性）：**

```sql
CREATE TABLE gym_members (
    -- 主キー (PRIMARY KEY): 一意のアイデンティティを保証し、自動的に増加する
    id SERIAL PRIMARY KEY,
    member_name VARCHAR(250) NOT NULL
);
```

**>> ステップ2：子のテーブルに連結フックを打ち込む（従属する注文）：**

```sql
CREATE TABLE training_bills (
    id SERIAL PRIMARY KEY,           -- 各請求書には独自のIDがある
    item_name VARCHAR(50),
    owner_id INT REFERENCES gym_members(id) ON DELETE CASCADE

    -- <<< アーキテクトよ、奇跡はこの上の行にある >>>
    -- REFERENCES コマンドは、「X線リンク」を (gym_members) テーブルの (id) カラムに直接向けます。
    -- ON DELETE CASCADE: 「自動焦土作戦」ポリシー。もし親（所有者）がジムを辞めて
    -- そのレコードが削除された場合、その子の請求書はすべてマシンによって自動的に消去されます。
    -- 「孤児」のようなゴミは残されません！
);
```

**>> ステップ3：セキュリティシステムの起動（データベースの壁のテスト）**
クラッシュテストをシミュレートしてみましょう。

まず、親を注入します：

```sql
INSERT INTO gym_members (member_name) VALUES ('超人ナム・ジムマー');
-- システムはこの会員に ID: 1 を割り当てます
```

さて、ハッカーやバグのあるクライアントが、存在しないユーザー（例：ユーザーID 99）に対して請求書を作成しようとしたとします。

```sql
INSERT INTO training_bills (item_name, owner_id) VALUES ('巨大プロテインコンボ', 99);
```

**ドーン！！ 💥 結果はどうなる？**
PostgreSQLロボットは不正なリンクを捕まえ、クライアントにエラーを投げ返します：`SQL Error: insert or update on table "training_bills" violates foreign key constraint. Key (owner_id)=(99) is not present in table "gym_members".`

データベースの守護天使は、ゴミがディスクに触れる前にそれを浄化しました！これにより、ずさんな開発者によって引き起こされる論理バグの90%が防がれます。SQLは究極の檻なのです！

## 💡 4. 最高峰の最適化の秘密：コスト削減の整数ルール

一部のスタートアップは、「ID番号よりも覚えやすいから」という理由で、**メールアドレス**を外部キー（FK）や主キー（PK）として使おうとします。
**絶対に間違いです！これはパフォーマンスを破壊します！**

メールアドレスは `VARCHAR` 文字列です。JOINや検索の際にCPUやRAMを介してテキストを移動させるのは、床の上で重い絨毯を引きずるようなものです。CPUサイクルを浪費し、クエリを遅延させます。

**最適化の極致：** PKとFKのリンクには、常に **整数ID（バイナリインデックス化された数値）** を使用してください！サーバーは、AWSなどのクラウド予算を浪費することなく、光の速さ（1ミリ秒）で数値を処理します。Day 1から、アーキテクチャを堅牢かつスリムに保ちましょう！
