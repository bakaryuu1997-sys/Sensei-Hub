# Day 12: 空白領域の走査 (左外部結合・右外部結合：LEFT & RIGHT JOIN) 🔗

昨日、あなたは `INNER JOIN`（内部結合）という武器を手にし、完璧なマッチングの技術を学びました。あなたのデータベースは、「顧客A」と「請求書B」をスナップさせて、完全な収益レポートを作成する方法を知っています。

**しかし、ビジネスの世界はそれほど完璧ではありません！**

マーケティング・ディレクターが机を叩いてこう叫んだと想像してください。
> _「もう収益レポートなんていらない。今日は、サイトに登録したけれど『一度も商品を購入したことがない』すべての顧客を見つけ出してくれ。営業チームに電話して、なぜ成約に至っていないのか理由を突き止める必要があるんだ！」_

このタスクに古い `INNER JOIN` の斧を投げつけても、SQLロボットは...何も返してくれません。なぜなら、`INNER JOIN` は「カップル」しか表示しないからです。顧客が何も購入していなければ、注文テーブルにレコードは存在せず、`INNER JOIN` は単にその顧客をビューから削除してしまいます。

「包括的」な接続の魔法へようこそ： **LEFT JOIN & RIGHT JOIN (外部結合/Outer Join)。**

## 🧠 2. 哲学：左側テーブルの「セーフティネット」

`users`（ユーザー）テーブルを **作戦基地**（左テーブル）、`orders`（注文）テーブルを **行動記録**（右テーブル）と考えてください。

`INNER JOIN` では、行動がなければユーザーは無視されます。
**LEFT JOIN** では、SQLロボットにこう命じます： _「左側の全員を連れてこい。注文があればそれを付けろ。もし注文がなければ、捨てずにおけ。ただ注文のスロットに『空っぽ』のステッカーを貼っておくだけでいい。」_

データベースの世界でその「空っぽのステッカー」は、**NULL** と呼ばれます。

### LEFT JOIN の視覚化（「包括的」なマップ）

```ascii
 ++ データベースの状態 - LEFT JOIN 実行前 ++

  (左テーブル: users)                         (右テーブル: orders)
   +ID_PK+ | ユーザー名                        +ID_PK+ | [FK_USER_ID] | 金額
   --1-----| アリス (忠実な顧客)               --102---| [   1   ]    | 5,000円
   --2-----| ボブ (ウィンドウショッピング)     (ボブはまだ注文がありません！)
   --3-----| チャーリー (爆買い顧客)           --103---| [   3   ]    | 50,000円

 ================ ロボットが実行： LEFT JOIN orders ON u.id = o.user_id ================
 |                                                                                    |
 V      + 結果：誰も取り残されない（注文のない顧客も含めて） +                            V

   +USER_ID+ | ユーザー名        +++++ ORDER_ID + 金額
   --1-------| アリス            +++++ [102]    | 5,000円   <== 一致が見つかりました！
   --2-------| ボブ              +++++ [ NULL ] | [ NULL ]  <== 黄金の虚無！ボブがリストに残ります！
   --3-------| チャーリー        +++++ [103]    | 50,000円  <== 一致が見つかりました！

   => なぜこれが強力なのか？ ボブが見えるからです！ 彼は存在し、かつ活動していないことが分かります。
```

**ところで、RIGHT JOIN は？**
技術的には同じことを行いますが、右側のテーブルを保護します。しかし、開発者の99%は `LEFT JOIN` だけを使います。なぜなら、人間は左から右へ読むからです。右テーブルを保護する必要がある場合は、コード内のテーブルの順序を入れ替えて `LEFT JOIN` を使えばいいだけです。 **コードの可読性を保つために、LEFT JOIN を使い続けましょう。**

## 💻 3. 実戦コード：Supabaseでゴースト顧客を狩る

マーケティング・ディレクターを助けて、眠っている顧客を見つけ出しましょう。

### ステップ1：包括的なビュー

まず、全員とその注文状況を見てみましょう：

```sql
SELECT
    u.id,
    u.user_name,
    o.total_amount
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id;
-- 結果：購入者には実際の金額が表示され、未購入者には "NULL" が表示されます。
```

### ステップ2：スナイパーショット（休眠ユーザーの特定）

何も購入していない人だけを営業チームにリストアップするには、右テーブルの主キーに対して特定の `WHERE` フィルタを使います。

```sql
SELECT
    u.id,
    u.user_name,
    u.email
FROM users AS u
LEFT JOIN orders AS o
ON u.id = o.user_id
-- 重要なフィルタ：右側が欠落している行のみを表示
WHERE o.id IS NULL;

-- 注意： "= NULL" ではなく "IS NULL" を使います。
-- SQLにおいて、NULLは値ではなく「何もない状態」です。何もないものと「等しい」ことはできません。
```

## 💡 4. シニアの罠：COUNT(*) VS. COUNT(列名) の惨劇

シニアレベルに到達するには、`LEFT JOIN` 後の **集計関数** に注意を払わなければなりません。

各顧客が何件の注文を持っているか数えたいとします。
*   **危険なコード：** `SELECT u.user_name, COUNT(*) FROM users u LEFT JOIN orders o... GROUP BY u.user_name`
    *   *結果：* ボブ（注文数0）の注文数が **1** と表示されます。なぜ？ `COUNT(*)` は「行」そのものを数えるからです。ボブは LEFT JOIN によって保持されているため、行は存在してしまいます。
*   **正しいコード：** `SELECT u.user_name, COUNT(o.id) FROM users u LEFT JOIN orders o... GROUP BY u.user_name`
    *   *結果：* ボブの注文数は正しく **0** と表示されます。なぜ？ `COUNT(カラム名)` は `NULL` 値を無視するからです。ボブの `o.id` は NULL なので、ロボットはそれをスキップします。

**NULLのニュアンスを理解しているかどうかが、ジュニアプログラマーとデータアーキテクトを分ける境界線です。**
