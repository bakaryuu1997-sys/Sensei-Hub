# Day 28: コネクションプーリングとPgBouncer - ボトルネックの解消 ⚡

**Day 28**へようこそ。大規模なコンサートチケットの販売など、非常にトラフィックの多いイベントを運営していると想像してください。

10万人のユーザーが全く同じ瞬間に「購入」ボタンをクリックします。アプリケーションは爆発し、突然、PostgreSQLデータベースが致命的なエラーをスローします：
> `FATAL: sorry, too many clients already`

トランザクションが停止し、顧客は不満を感じて去っていきます。CEOからは説明を求められるでしょう。その原因は、データベースが弱いからではなく、あまりにも多くの接続が同時に開かれたためにシステムが「窒息」してしまったからです。今日は、数百万ユーザー規模のシステムの背後にある秘密である**コネクションプーリング**と、その救世主である**PgBouncer**をマスターします。

---

## 🎣 1. イントロダクション：直接接続が「サイレントキラー」である理由

アプリケーション（NodeJS、Go、Pythonなど）がPostgreSQLへの接続を開くたびに、単にパケットを送信するだけではありません。データベースは一連の重いタスクを実行する必要があります：

1. **TCPハンドシェイク（3段階）：** ネットワークを介した物理的なリンクの確立。
2. **SSL/TLSネゴシエーション：** ハッカーがデータを傍受できないように暗号化を確立。
3. **認証：** IDの確認（ユーザー名/パスワード/ロール）。
4. **バックエンドプロセスの生成：** これが最も重い部分です。PostgreSQLは、その特定の接続を処理するために、オペレーティングシステムで新しいプロセスを「フォーク（生成）」する必要があります。
   *   各プロセスは即座に約**2MB〜10MBのRAM**を消費します。
   *   1,000件の接続があると、SQLコマンドを1つも実行する前に、単に「待機状態」を維持するためだけに**10GBのRAM**を失うことになります！

RAMが枯渇すると、OSは**OOM Killer**を起動し、PostgreSQLプロセスを強制終了します。システムはクラッシュします！

## 🏛️ 2. コア理論：コネクションプーリングの技術

すべてのユーザーに専用のタクシーを提供するのではなく（コストがかかり、交通渋滞の原因になります）、**シャトルバス（コネクションプール）**を使用します。

### 🧩 ASCIIダイアグラム：PgBouncer経由のデータフロー

```text
[ アプリケーション側 ]           [ PGBOUNCER - ゲートキーパー ]          [ データベース側 ]
      (App)                         (ミドルウェア)                       (PostgreSQL)

Req 1 \                                                               /-- Conn 1 (Ready)
Req 2 --(仮想接続)--> [ コネクションプール ] --(物理接続)--> [ Postgres ]
Req 3 /                 [ (接続の再利用)   ]                       \-- Conn 2 (Ready)
...                     [                ]                         (少数のパイプを維持)
Req 10,000 /            [                ]                         (RAMを節約)

原理：Appからの10,000リクエストに対して、Postgresへの物理的な接続は100程度で済みます。
PgBouncerは、処理が終わった接続をすぐに奪い取り、待機している次のリクエストに渡します。
```

### 📊 マスターすべき3つのプーリングモード

| モード | 仕組み | メリット/デメリット |
| :--- | :--- | :--- |
| **Session Mode** | ログインからログアウトまで接続を維持します。 | 最も安全ですが、最も無駄が多いです。1万ユーザーの問題は解決しません。 |
| **Transaction Mode** | **（推奨）** 1つのトランザクション（`BEGIN` -> `COMMIT`）の間だけ接続を維持します。 | Webアプリに最適。100の物理接続で1万ユーザーを処理可能。 |
| **Statement Mode** | 各SQLステートメントの後に接続を解放します。 | 非常に高いパフォーマンスですが、トランザクションをサポートしません（ECサイトでは危険）。 |

## 🛠️ 3. 戦場での実践：プロのようにPgBouncerを構成する

LinuxサーバーにPgBouncerをインストールする場合、`pgbouncer.ini`ファイルが魔法の場所になります。以下のパラメータに注目してください：

```ini
[databases]
# 実際のデータベースへのパス
mydb = host=127.0.0.1 port=5432 dbname=real_db

[pgbouncer]
listen_port = 6432
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt

# パフォーマンスのためのゴールデンパラメータ:
max_client_conn = 10000    ; 1万件の仮想クライアント接続を許可
default_pool_size = 50     ; Postgresへの物理接続は50件のみ開く
reserve_pool_size = 10     ; メインプールが混雑したときのために10件を予約
pool_mode = transaction    ; Webアプリにとって最も重要なモード
```

### ⚠️ 注意：Prisma/TypeORMにおけるプリペアドステートメント
現代のORMは、プリペアドステートメント（事前コンパイルされたSQL）を使用することがよくあります。`Transaction Mode`では、PgBouncerが頻繁に接続を切り替えるため、以下のエラーが発生することがあります：
> `ERROR: prepared statement "s1" already exists`

**解決策：** 
1. 接続文字列に `?pgbouncer=true` を追加します。
2. または、Prismaを `binaryTargets` を使用するように構成するか、ステートメントキャッシュを無効にします。

## 🔍 4. ディープダイブ：プーラーの健全性の監視

マスターとして、「勘」で管理してはいけません。以下のコマンドを使用して、システムの状態を確認してください：

```sql
-- 'pgbouncer' という名前の仮想データベースに接続
psql -p 6432 pgbouncer

-- プールの統計を表示
SHOW POOLS;
```

**注目すべき主要なメトリクス：**
*   **cl_active:** 接続を保持しているアプリインスタンスの数。これが `max_client_conn` に達すると、新しいクライアントはタイムアウトします。
*   **sv_active:** 実際に実行されている物理的な接続の数。 
*   **cl_waiting:** **危険なメトリクス。** これが0より大きい場合、クライアントがパイプを待っていることを意味します。すぐに `default_pool_size` を増やす必要があります！

## 💡 5. 比較：PgBouncer vs Supavisor vs Odyssey

2026年、私たちにはより多くの選択肢があります：
*   **PgBouncer:** クラシックで軽量（シングルスレッド）、非常に安定しています。
*   **Odyssey (Yandex製):** マルチスレッドで、マルチコアCPUでのパフォーマンスが向上しています。
*   **Supavisor (Supabase製):** Elixirで記述されており、驚異的なスケーラビリティを持ち、数百万の接続をスムーズに管理します。
