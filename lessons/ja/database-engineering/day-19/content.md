# Day 19: 幽霊テーブル - ビューとマテリアライズドビュー 🖼️

昨日は、システムクラッシュからデータを守るための **「トランザクション」** をマスターしました。今日は、**開発の生産性とレポートのパフォーマンス**に焦点を当てます。

プロジェクトが成長するにつれて、SQLクエリは「怪物」のように巨大化していきます。たとえば、「月次売上レポート」を見たいだけなのに、毎回5つのテーブルを結合し、複雑な計算を書かなければならないとしたらどうでしょう？ それは非常に疲れ、タイポ（打ち間違い）の原因になり、メンテナンスも困難になります。

シニア・アーキテクトは、この複雑さを隠すために **「ビュー (View)」** を使います。ビューとは、実際のテーブルのように振る舞いますが、中身は保存された「クエリ」そのものである「幽霊テーブル」です。

---

## 🎯 1. 本日の戦略的目標

1.  **標準ビュー (Standard VIEW):** 複雑なクエリのための仮想的な「ショートカット」を作成します。
2.  **マテリアライズドビュー (MATERIALIZED VIEW):** クエリ結果をディスクに保存し、爆速のレポートを実現します。
3.  **ビュー vs テーブル:** メモリと速度のトレードオフを理解します。
4.  **リフレッシュ戦略:** マテリアライズドビューのデータを最新に保つ方法を学びます。

---

## 🧠 2. 哲学：「保存されたカメラアングル」

**ビュー**を、複雑な3Dの世界における **「保存されたカメラアングル」** だと考えてみてください。
- **テーブル**は、部屋の中にある実際のオブジェクト（モノ）です。
- あなたがビューを通して見るたびに、データベースは保存されたクエリに基づいてそのシーンを「再描画」します。 **追加のストレージ容量はゼロ** ですが、計算には時間がかかります。

一方、**マテリアライズドビュー**は、そのシーンを撮った **「写真」** です。
- ディスク上に物理的な容量を消費します。
- 写真はすでに撮られているので、見るのは **一瞬（高速）** です。
- ただし、部屋のオブジェクトが動いても（データが変更されても）、写真を撮り直す（リフレッシュ）までは、写真は古いままです。

```ascii
[ データベース・パフォーマンス・アーキテクチャ ]

  +------------+      +------------+      +------------+
  | テーブル A  | +--+ | テーブル B  | +--+ | テーブル C  |
  +------------+      +------------+      +------------+
        |                    |                  |
        +---------- 巨大な結合クエリ -----------------+
                             |
         +-------------------V-------------------+
         |             ビュー (ロジック)           |
         | (見るたびにその場で計算される)        |
         +---------------------------------------+
                             |
         +-------------------V-------------------+
         |   マテリアライズドビュー (物理保存)    |
         |  (保存済み結果。爆速読み込み！ 🚀)    |
         +---------------------------------------+
```

## 💻 3. 実戦 SQL：Supabase でビューを作成する

### シナリオ：「VIP売上」のショートカット
毎回 `orders`、`customers`、`products` を結合する代わりに、ビューを作りましょう。

```sql
-- 1. 標準ビュー (仮想) の作成
CREATE VIEW view_vip_orders AS
SELECT 
    o.id AS order_id,
    c.full_name AS customer,
    p.name AS product,
    o.amount
FROM orders o
JOIN customers c ON o.customer_id = c.id
JOIN products p ON o.product_id = p.id
WHERE o.amount > 1000;

-- これで、普通のテーブルのようにクエリできます！
SELECT * FROM view_vip_orders WHERE customer = 'Bakaryuu';
```

### シナリオ：「CEOへの重たいレポート」（マテリアライズド）
レポートの実行に10秒かかる場合、標準ビューでは解決しません。マテリアライズドビューが必要です。

```sql
-- 2. マテリアライズドビュー (物理) の作成
CREATE MATERIALIZED VIEW mv_monthly_revenue AS
SELECT 
    date_trunc('month', created_at) AS month,
    SUM(amount) AS total_revenue
FROM orders
GROUP BY 1;

-- 読み込みは「爆速」です：
SELECT * FROM mv_monthly_revenue;

-- データを最新にする（手動リフレッシュ）：
REFRESH MATERIALIZED VIEW mv_monthly_revenue;
```

## 💡 4. シニアの秘密：ビューによるセキュリティ

ビューはパフォーマンスのためだけではありません。強力な **「セキュリティの武器」** でもあります。
たとえば、パスワードのハッシュや住所など機密情報を含む `users` テーブルがあるとします。マーケティングチームには「名前」と「メール」だけを見せたいが、他は見せたくない場合……。

**解決策：** マーケティングチームに `users` テーブルへのアクセス権を与えてはいけません。代わりに、名前とメールだけを選択する `marketing_user_list` というビューを作成し、そのビューにのみアクセス権を与えます。これで、彼らがどんなに頑張ってもパスワードを見ることはできなくなります！
