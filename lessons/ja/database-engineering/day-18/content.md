# Day 18: データのファイアウォール - トランザクションとACID 🛡️

**Day 18** へようこそ。

今日は、絶対的な「信頼」についてのレッスンです。顧客が「支払う」ボタンをクリックしたとき、彼らはあなたのシステムに全幅の信頼を寄せています。トランザクション（Transaction）とは、ネットワークエラーやサーバーのクラッシュに関わらず、その信頼を維持し続けるための技術的な傑作です。シニアアーキテクトとして、この保護メカニズムを「原子（アトミック）」レベルで理解する必要があります。

---

## 🎯 1. 戦略的ビジョン
- データの整合性を守る **ACID** の4本の柱をマスターする。
- **MVCC** の深層を理解する（なぜSELECTはUPDATEをブロックしないのか？）。
- 並行データ競合を処理するための **Isolation（分離）** レベルを使い分ける。
- 信頼性の高いリカバリ（Recovery）メカニズムを備えた、回復力のあるシステムを設計する。
- 実務における悲観的ロックと楽観的ロックの使い分けを理解する。
- 高並行環境におけるデッドロック回避技術をマスターする。

---

## 🏛️ 2. ACIDの解剖：信頼の4原則

### 2.1 Atomicity（原子性）
「全か無か（All or nothing）」。送金処理が10ステップあり、9ステップ目で失敗した場合（例：接続遮断）、それまでの8ステップはすべて取り消され（Rollback）なければなりません。データベースは「中途半端」な状態を決して認めません。

### 2.2 Consistency（一貫性）
データベースがある有効な状態から別の有効な状態へと遷移することを保証します。COMMIT前にすべての制約（外部キー、チェック制約、トリガー）が満たされていなければなりません。処理後のデータは定義されたすべての業務ルールに従っている必要があります。

### 2.3 Isolation（分離性）
並行して実行されるトランザクション同士が、互いの中間的な「一時データ」を見ることができないようにします。これはDBエンジンにおいて最も難しく、かつパフォーマンスに影響を与える部分です。要件に応じて、速度のために分離性を妥協することもあります。

### 2.4 Durability（永続性）
一度コミットされたデータは、ディスクに安全に保存されなければなりません。直後にサーバーの電源が落ちても、先行書き込みログ（WAL - Write Ahead Logging）のおかげでデータは保護されます。

---

## 🔬 3. MVCCメカニズム (MULTI-VERSION CONCURRENCY CONTROL)

Postgresは、テーブル全体のロック（Locking）ではなく、**MVCC** を採用しています。UPDATEのたびに既存の行を上書きするのではなく、その行の新しいバージョンを作成します。
- **xmin**: この行バージョンを作成したトランザクションID。
- **xmax**: この行バージョンを削除または更新したトランザクションID。xmax = 0 であれば、その行は現在有効です。

**哲学:** 「読み取り（Reader）は書き込み（Writer）をブロックせず、書き込みは読み取りをブロックしない」。これにより、ロックによるシステム停止を回避し、数千の同時クエリを処理できます。

---

## ⚡ 4. 分離レベルと異常現象

1. **Read Committed (デフォルト)**: コミット済みのデータのみを読み取ります。ダーティリードを防止しますが、非再現リードは発生する可能性があります。
2. **Repeatable Read**: トランザクション内で同じ行を2回読み取った際、必ず同じ結果が得られることを保証します。非再現リードとファントムリードを防止します。
3. **Serializable**: 最高レベル。トランザクションが1つずつ順番に（直列に）実行されたかのような結果をシミュレートします。複雑な **Write Skew（書き込みスキュー）** を防止します。

## 🏗️ 5. 実戦プロジェクト：電子マネーの安全な送金

```sql
-- 安全な送金処理の例
BEGIN;

-- 1. 行をロックして、他の誰にも編集させない（悲観的ロック）
SELECT balance FROM accounts WHERE user_id = 'Alice' FOR UPDATE;

-- 2. アプリケーション層での残高チェック
-- IF balance < 100 THEN ROLLBACK;

-- 3. 残高の更新
UPDATE accounts SET balance = balance - 100 WHERE user_id = 'Alice';
UPDATE accounts SET balance = balance + 100 WHERE user_id = 'Bob';

-- 4. 完了
COMMIT;
```

## 🛠️ 6. よくある落とし穴とアンチパターン

1. **ロールバックの失念 (Forgotten Rollback)**: アプリ側でエラーが発生したのにROLLBACKを呼ばないこと。「Idle in transaction」状態が続き、リソースを占有し続けます。
2. **長時間のトランザクション**: トランザクションを開いたまま外部APIを呼び出すこと。APIが遅いと、DBロックが保持され続け、システム全体の渋滞を招きます。
3. **暗黙のトランザクション**: トランザクションの開始と終了を制御せず、DBが1文ごとに自動コミットすること。パフォーマンスが著しく低下します。

## 🚨 7. ケーススタディ：Z銀行での「書き込みスキュー」による損失

**背景:**
Z銀行には「顧客の2つの普通預金口座の合計残高がマイナスになってはならない」というルールがありました。
顧客は口座Aに100ドル、口座Bに50ドル持っています（合計150ドル）。
2つの100ドルの引き出しリクエストが同時に発生しました。
- トランザクション1：口座Aから100ドル引き出し。
- トランザクション2：口座Bから100ドル引き出し。

**結果:**
`Repeatable Read` レベルでは、両方のトランザクションが開始時に合計残高を確認し、150ドルあると判断します。両方のリクエストが承認され、COMMITされます。結果：口座A = 0ドル、口座B = -50ドル。合計は -50ドルとなり、銀行のルールに違反しました。

**アーキテクトの教訓:**
複数の行にまたがる状態に依存するロジックの場合、`SERIALIZABLE` レベルを使用するか、関連するすべての行に対して明示的に `FOR UPDATE` でロックをかける必要があります。

## 🧠 8. インタビュー対策：シニアアーキテクト・レベル

**質問1: Postgresはデッドロックをどのように処理しますか？**
*回答:* Postgresには「Deadlock Detector」というバックグラウンドプロセスがあります。2つのトランザクションが互いのロックを循環的に待ち合っていることを検知すると、一方（通常は新しいほう）を強制的にエラーにしてロールバックさせ、システムを解放します。

**質問2: Vacuumにおける「xmin」と「xmax」の役割は？**
*回答:* 行が削除されると、その行のxmaxに削除したトランザクションIDが記録されます。物理的にはすぐ消えず、古いトランザクションがすべて終わるまで残ります。その後、VACUUMプロセスがこれらのマーカーを見て「不要なタプル（Dead tuples）」を掃除し、領域を再利用します。

## 📂 10. アーキテクチャ決定記録 (ADR)

| 決定事項 | 根拠 | 影響 |
| :--- | :--- | :--- |
| **悲観的ロックの採用** | 金融上の競合を絶対的に排除するため。 | キューイングが発生し、レイテンシが増加する可能性がある。 |
| **楽観的ロックの採用** | 競合の少ないシステムでの効率化。 | アプリ側でリトライロジックを自前実装する必要がある。 |
| **WALの使用** | 停電時などのデータ安全性を確保するため。 | ログファイル用の追加ディスク容量が必要。 |

## 🎓 11. マスタリング・クイズ（厳選5問）

1. 問1: PostgreSQLが `xmin` と `xmax` を使う理由は何ですか？
   - 回答: MVCCを実装するためです。同じ行の複数のバージョンを管理することで、読み取り側がロックを必要とせず、並列性能を向上させます。
2. 問2: ダーティリードとは何ですか？なぜ危険なのですか？
   - 回答: コミットされていないデータを読み取ることです。そのデータが後にロールバックされる可能性があるため、業務ロジックが誤った判断を下すリスクがあります。
3. 問3: 書き込みスキュー（Write Skew）現象を解決する確実な方法は？
   - 回答: `SERIALIZABLE` 分離レベルを使用するか、`FOR UPDATE` を使用して能動的にデータをロックすることです。
4. 問4: なぜ長時間実行されるトランザクションを避けるべきなのですか？
   - 回答: リソースロックを長時間保持し、VACUUMによる掃除を妨げるため、DBの肥大化（Bloat）とシステム全体の低下を招くからです。
5. 問5: WAL (Write Ahead Log) の目的は何ですか？
   - 回答: 実際のデータファイルに書き込む前に、変更内容をログに記録すること。これにより、クラッシュ後の完全なデータ復旧が可能になります。

## 🛠️ 12. 用語集 (GLOSSARY)

- **ACID**: 原子性、一貫性、分離性、永続性の4原則。
- **MVCC**: 多版型同時実行制御。
- **Deadlock**: 2つのプロセスが互いのロックを待ち続けて動けなくなる状態。
- **WAL**: 先行書き込みログ。
- **Pessimistic Locking**: 先にロックし、後で処理する手法（悲観的）。
- **Optimistic Locking**: 処理を先に行い、コミット時に競合をチェックする手法（楽観的）。
