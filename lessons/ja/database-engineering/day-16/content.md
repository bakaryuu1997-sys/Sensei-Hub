# Day 16: インデックス Part 1 - B-Tree と超高速検索 ⚡

**Day 16** へようこそ。

今日は、PostgreSQLの「脳」を解剖し、10億行の中から1つのレコードをわずか数ミリ秒で見つける仕組みを理解します。インデックスは魔法ではありません。高度なデータ構造と数学の結晶です。B-Treeを理解することは、データベースがハードディスクとどのように通信するか（Disk I/O）を理解することと同義です。

---

## 🎯 1. 戦略的ビジョン
- ディスク上のB-Treeの物理構造（ページレイアウト）をマスターする。
- Seq Scan、Index Scan、Index Only Scanの使い分けを理解する。
- 書き込み操作に対するインデックスの「重いコスト」を理解する。
- クエリ設計時に「インデックス・ファースト」の思考を持つ。
- `EXPLAIN ANALYZE` を駆使して、オプティマイザの判断を読み解く。

---

## 🔬 2. ソースコード解読：ページ構造

Postgresでは、すべてのインデックスファイルは8KBの固定「ページ」に分割されています。これはOSがディスクからRAMに読み込む最小単位です。ページの読み込みは、データベースにおいて最もコストの高いI/O処理です。

```c
/* インデックスページを管理するためのPostgreSQLソースコード構造 */
typedef struct BTPageOpaqueData {
    BlockNumber btpo_prev;    /* 左側の兄弟ページへのポインタ */
    BlockNumber btpo_next;    /* 右側の兄弟ページへのポインタ */
    uint32      btpo_level;   /* 高さ: 0 = リーフ, >0 = 内部ノード */
    uint16      btpo_flags;   /* フラグ: ルート、リーフ、ハーフデッドなど */
    BTCycleId   btpo_cycleid; /* Vacuumプロセス中の保護用 */
} BTPageOpaqueData;
```

B-Treeの本質は、ツリーを常に**平衡（Balanced）**に保つことです。データが100万行でも10億行でも、ルートからリーフまで読み込むページの数（ツリーの深さ）は非常に小さく保たれます（通常わずか3〜4階層）。

---

## 🏛️ 3. なぜ B-TREE なのか？（ハードディスクの物理学）

PostgresがバイナリツリーではなくB-Treeを使用するのは、**ファンアウト（Fan-out）**（各ノードあたりの子分岐数）が非常に大きいためです。
- **バイナリツリー**: 10億行の場合、約30階層必要。各階層でディスク読み込みが発生し、遅すぎる！
- **B-Tree**: ファンアウトが数百あれば、10億行でもわずか3階層程度。わずか3回のディスク読み込みで済むため、極めて高速です。

---

## ⚡ 4. 実戦的なクエリシナリオ

1. **Sequential Scan (順次スキャン)**: 行を1つずつ読み込みます。テーブルが非常に小さい場合や、全データの大部分（例：80%以上）を取得する場合、オプティマイザはこれを選択します。順次I/OはランダムI/Oよりも速いためです。
2. **Index Scan**: インデックスを使用してTID（タプルID）を見つけ、ヒープ（メインテーブル）にジャンプしてデータを取得します。最も一般的な方法です。
3. **Index Only Scan**: インデックスからすべての情報を取得し、ヒープへのアクセスを省略します。I/Oコストを50〜80%削減できます。
4. **Bitmap Index Scan**: 複数のインデックスを組み合わせます。インデックスをスキャンしてTIDをRAMに集め、ディスク位置順にソートしてからヒープを一度に読み込むことで、ディスクヘッドの動きを最適化します。

---

## 🛠️ 5. よくある落とし穴とアンチパターン

1. **インデックスの過剰作成 (Index Overkill)**: すべての列にインデックスを張ること。結果として、INSERT/UPDATEのたびに数十のB-Treeを更新しなければならず、書き込みが極端に遅くなります。
2. **低カーディナリティ列へのインデックス**: 「性別」や「ステータス」（値が2〜3種類）などの列へのインデックス。オプティマイザはほぼ確実にSeq Scanを選択するため、無意味です。
3. **WHERE句での関数使用**: `WHERE YEAR(created_at) = 2023`。これは `created_at` のインデックスを無効化します。`WHERE created_at >= '2023-01-01' AND created_at < '2024-01-01'` と書くべきです。

---

## ⚠️ 6. ページ分割 (Page Splits)：速度の副作用

満杯のインデックスページにデータを挿入すると、Postgresは**ページ分割**を行い、データの50%を新しいページに移動させます。これにより書き込みコストが増加し、インデックスの断片化が発生します。
**アーキテクトの解決策:** 書き込みの多いテーブルでは `FILLFACTOR = 85` 程度を設定し、各ページにあらかじめ空き領域を確保しておきます。

---

## 🚨 7. ケーススタディ：UUID v4 が書き込み性能を破壊した話

**背景:**
ある決済システムで、`UUID v4`（完全ランダム）を主キーとして使用していました。テーブルが1億レコードに達したとき、INSERT速度が 5,000 req/s から 200 req/s まで急落しました。

**原因:**
UUID v4 はランダムであるため、新しいレコードはB-Treeのランダムな位置に挿入されます。これにより、DBはディスクからランダムなページをロードせざるを得ず（キャッシュミスが多発）、ツリー全体でページ分割が連鎖しました。SSDであってもランダム書き込みのオーバーヘッドに耐えられませんでした。

**アーキテクトの教訓:**
可能な限り、順序性のあるID（`bigserial` や、タイムスタンプが先頭にある `UUID v7`）を優先してください。これにより、新しいデータは常にツリーの「右端」に挿入され、キャッシュ効率が最大化し、ページ分割が最小限に抑えられます。

## 🧠 8. インタビュー対策：シニアアーキテクト・レベル

**質問1: なぜ `ORDER BY` でインデックスが使われないことがあるのですか？**
*回答:* インデックスのソート方向（ASC/DESC）が違う場合や、複合インデックスの先頭列が指定されていない場合です。また、オプティマイザが「インデックスをランダムに読むより、全スキャンしてRAMでソートしたほうが速い」と判断した場合もスキップされます。

**質問2: Postgresにおける「クラスタ化インデックス」を説明してください。**
*回答:* PostgresにはSQL ServerやMySQLのような自動的なクラスタ化インデックスはありません。ヒープ内のデータは挿入順に並んでいます。`CLUSTER` コマンドで特定のインデックスに従ってヒープを並べ替えることはできますが、その後の更新で順序は崩れるため、手動での再実行が必要です。

## 🏗️ 10. 実戦プロジェクト：1000万ユーザのクエリ最適化

1. **現状**: `email` での検索に2秒かかる（Seq Scan）。
2. **解決策1**: `CREATE INDEX idx_email ON users(email);` -> 10msに短縮。
3. **解決策2**: `CREATE INDEX idx_email_id ON users(email) INCLUDE (id, name);` -> `Index Only Scan` を達成し、CPUとディスクI/O負荷を劇的に削減。

## 🎓 12. マスタリング・クイズ（厳選5問）

1. 問1: なぜディスクストレージにはバイナリツリーよりB-Treeが適しているのですか？
   - 回答: ファンアウトが大きいためツリーの高さが低く抑えられ、システムのボトルネックであるディスク読み込み（Disk I/O）の回数を最小限にできるからです。
2. 問2: DBがIndex ScanよりSeq Scanを優先するのはどのような時ですか？
   - 回答: 取得するデータ量が全データの20%を超える場合や、テーブル自体が極めて小さい場合です。
3. 問3: `Index Only Scan` が成立するための条件は？
   - 回答: 必要なすべての列がインデックスに含まれており、かつVisibility Mapによってデータが「クリーン」であると確認できる場合です。
4. 問4: 大量の挿入が発生するシステムでページ分割を抑えるには？
   - 回答: `FILLFACTOR` を100未満（70〜80等）に設定し、主キーに順序性を持たせることです。
5. 問5: UUID v4 がB-Treeインデックスに悪影響を与える理由は？
   - 回答: ランダム性によってデータが分散し、キャッシュミスを誘発して高コストなランダムI/Oを強制するため、書き込み性能が著しく低下します。

## 🛠️ 13. 用語集 (GLOSSARY)

- **Fan-out (ファンアウト)**: 1ノードあたりの最大分岐数。
- **TID (Tuple ID)**: レコードの物理アドレス（ブロック番号、オフセット番号）。
- **Random I/O**: ディスクの不連続な位置へのアクセス。
- **Index Bloat (肥大化)**: 削除されたデータが再利用されず、インデックス内に生じる無駄な空間。
- **Cardinality (カーディナリティ)**: 値の種類の多さ。
- **Visibility Map**: ページ内のデータが全トランザクションから見える状態か（クリーンか）を示すマップ。
