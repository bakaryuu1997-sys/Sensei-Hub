# 🪝 THE HOOK: 「消えた画像と 404 エラーの謎」

あなたが、大手ニュースサイトのために WordPress システムを構築していると想像してください。100 万人の同時アクセスに耐えられる素晴らしいオートスケーリングを設定しました。しかし、致命的な問題が発生します。編集者が新しい写真を記事にアップロードしたとき、その写真は編集者が接続していた「その一台」のサーバー（EC2）のハードディスクにしか保存されません。

オートスケーリングで作成された他の数千台のサーバーにアクセスした読者には、画像が「404 Not Found」エラーで表示されます。なぜなら、彼らがアクセスしたサーバーにはその写真が存在しないからです。

これが**共有ストレージ（Shared Storage）**の課題です。クラウドの世界では、適切な「ストレージ」を選択しないと、ウェブサイトが正しく動作しないだけでなく、請求額が 10 倍に跳ね上がることもあります。

今日は、ストレージの 3 つの「帝国」を深く掘り下げます。**EBS**（専用ハードディスク）、**EFS**（Linux 用共有ディスク）、そして **FSx**（Windows や Lustre 用の特殊なソリューション）です。

# 🎭 ANALOGY: 現代的なオフィスビル

これらのストレージの種類を理解するために、**現代的なオフィスビル**を想像してみましょう。

### 💻 1. Amazon EBS: 個人のノート PC
各従業員（EC2）は自分のノート PC を持っています。
- **超高速**: ハードディスクが本体に内蔵されている。
- **占有**: 一人のユーザーだけが使用する。別の PC に移すには「抜き差し（Detach/Attach）」が必要。
- **制限**: 同じオフィス内（1 つの AZ）でしか使えない。

### 📁 2. Amazon EFS: 全社共有のネットワークドライブ (NAS)
EFS は、会社全体の共有フォルダ（Z ドライブなど）のようなものです。
- **無制限の共有**: 数千人の従業員が同時に同じファイルを開き、編集できる。
- **自動拡張**: 容量不足を心配する必要がない。
- **高い耐久性**: データはすべての階（マルチ AZ）に保管されている。

### 🏢 3. Amazon FSx: 特殊な金庫
Windows を使う経理部門用（FSx for Windows）や、ロケットデータの解析を行う科学者用（FSx for Lustre）など、特定のニーズに応える「重量級の金庫」です。

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. Amazon EBS (Elastic Block Store)
- **gp3 (汎用 SSD)**: 標準的なタイプで、価格と性能のバランスが良い。
- **io2 (プロビジョンド IOPS SSD)**: 絶対的な I/O 安定性が必要な大規模データベース用。
- **Snapshots**: 「写真」を撮るようにバックアップし、S3 に増分保存されます。

### 2. Amazon EFS (Elastic File System)
- **Multi-AZ**: 少なくとも 3 つの AZ にデータが保存され、可用性は EBS を凌駕します。
- **ストレージクラス**: 標準クラスと **EFS-IA**（低頻度アクセス）を使い分け、古いファイルのコストを最大 90% 削減できます。

### 3. Amazon FSx & Storage Gateway
- **FSx for Windows**: SMB プロトコルと Active Directory を完璧にサポート。
- **FSx for Lustre**: ハイパフォーマンスコンピューティング（HPC）用。
- **AWS Storage Gateway**: あなたのオフィス（オンプレミス）とクラウド（S3/EBS）を繋ぐ架け橋。

### 4. 2026 年最新アップデート: インテリジェントストレージ 🚀
- **Amazon Q in EBS Optimization**: 2026 年、AI が `VolumeQueueLength` を自動監視し、「このディスクがボトルネックになっています。今すぐ io2 にアップグレードしましょう」とアドバイスをくれます。
- **EFS Archive クラス**: 2026 年の画期的な進化。S3 Glacier に近い低価格でファイルデータを保存でき、数秒でアクセス可能です。
- **Hybrid Cloud Link (2026)**: Storage Gateway が AI と統合され、従業員が次に使うファイルを予測。オフィスのサーバーに自動で「キャッシュ」し、ネットワーク遅延をゼロにします。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実務シチュエーション：** 「10 台の EC2（オートスケーリング）が、500GB の共有画像フォルダにアクセスする必要があります。1 つの AZ がダウンしてもデータが生き残るようにするには、何を選びますか？」

**マスターアーキテクトの回答例：**
「**Amazon EFS** を選択します。EFS は数千台のサーバーからの同時アクセス（Shared Access）をサポートしており、標準で **Multi-AZ** 構成だからです。1 つのデータセンターがダウンしても、他の AZ のサーバーから画像にアクセスし続けられます。また、500GB のデータを最適化するため、**ライフサイクル管理** を有効にして古い画像を **EFS Archive (2026)** に自動移行し、コストを最大 95% 削減します。」

# 🔦 CASE STUDY: Adobe と数千人のデザイナーのための共有ストレージ

**背景:** Adobe Creative Cloud は、数百万人のデザイナーが同時に作業する巨大なプラットフォームです。課題は、数千台の EC2 サーバーで動作するアプリケーションが、競合や遅延なく同じアセット（写真、動画）にアクセスできるようにすることでした。

**課題:** EBS は数千台のサーバーで共有できず、S3 はデザインアプリ特有の細かいファイルシステム操作（上書き保存など）をスムーズに行うのが困難でした。

**AWS ストレージによる解決策（2026 年基準）:**
1.  **Linux 環境への Amazon EFS 導入**: Adobe は共有リソースの保存に EFS を採用。**Elastic Throughput** 機能により、ピーク時に数千人のデザイナーが一斉にビデオをレンダリングしても、手動設定なしで自動的に速度が向上します。
2.  **8K 動画処理のための FSx for Lustre**: 超高速な処理が必要なタスクには FSx for Lustre を使用。数百 GB/s の速度でデータを処理し、8K 動画のレンダリングを一瞬で終わらせます。
3.  **EFS Archive によるコスト最適化**: 1 年以上前のプロジェクトは自動的に **EFS Archive** クラスへ移動。コストを 95% 削減しつつ、デザイナーがたまにファイルを開く際も数秒で準備が整います。

**BrSE への教訓:** 日本のレガシーシステムをクラウドへ移行する際、顧客はオンプレミスと全く同じディレクトリ構造を求めることがよくあります。**EFS** は、アプリケーションコードを修正することなく、従来の NAS を置き換えるための最高のソリューションです。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — EBS Multi-Attach と EFS を混同しない**: EBS Multi-Attach は、最大 16 台の（Nitro 世代の）サーバーが 1 つの AZ 内の 1 つのディスクに接続できる機能です。一方、**EFS** は数千台のサーバーが複数の AZ をまたいで接続できます。柔軟性を求めるなら EFS です。

> **Tip 2 — EFS のパフォーマンスモード**: 数百万の小さなファイル（PHP/Node.js のソースコードなど）を扱うなら **General Purpose**。ビッグデータ処理などには **Max I/O**。モードを間違えるとアプリの速度が 50% 低下することがあります。

> **Tip 3 — EFS のセキュリティグループを忘れるな**: 接続できない原因の 9 割は、EFS のセキュリティグループで **TCP 2049** ポートを EC2 に対して開け忘れていることです。デバッグ時はまずここを確認しましょう。

> **Tip 4 — Windows なら迷わず FSx**: Microsoft AD との深い統合や SMB プロトコルが必要な場合、FSx が唯一の選択肢です。EC2 でファイルサーバーを自作するのではなく、バックアップやパッチ適用を AWS に任せられる FSx を使いましょう。
