# 🪝 THE HOOK: 「金融グループの CISO（最高情報セキュリティ責任者）として」

あなたが大手金融グループの CISO だと想像してください。会社は 500 もの AWS アカウントを運用しています。ある朝、インターン生が不注意で、クレジットカード情報を含むデータベースへのアクセスを全開放（0.0.0.0/0）するセキュリティグループを作成したことを発見しました。

あなたは冷や汗をかきます。どうすればこれを二度と起こさないようにできるでしょうか？
- 毎日 500 アカウントをチェックすることは不可能です。
- 開発者のプロジェクトを遅らせないために、彼らの Admin 権限を完全に剥奪することもできません。
- あなたが必要としているのは、たとえルートユーザーであっても、危険な操作を禁止する究極の「輪（制約）」です。

**Day 37: Advanced Identity & Access Management** へようこそ。今日は、たとえ愚かなミスがあっても突破できない、多層防御システムを構築します。

# 🎭 ANALOGY: 国際空港のセキュリティに例える IAM

IAM のセキュリティシステムは、国際空港の警備に似ています：

### 🎫 1. IAM ポリシー - 航空券
- どの座席（リソース）に座れるか、どんな機内食（アクション）を食べられるかが書かれています。しかし、航空券だけでは飛行機に乗れません。

### 🛂 2. Permissions Boundary - パスポート
- 「最大限の境界」です。パスポートに「ASEAN 諸国のみ」とあれば、航空券に「米国行き（IAM ポリシーで許可）」とあっても、出国を止められます。パスポート自体は権限を与えませんが、行ける場所を「制限」します。

### 👮 3. Service Control Policy (SCP) - 国際航空法
- 最高法規です。「爆発物の持ち込み禁止」というルールがあれば、ビジネスクラス（Admin）でも外交官パスポートでも、違反すれば逮捕されます。SCP はアカウントの所有者（ルートユーザー）さえも制限できます。

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. IAM 条件キーと ABAC
- **aws:SourceIp**: オフィス IP からのアクセスのみを許可。
- **ABAC (Attribute-Based Access Control)**: タグによる権限付与。「プロジェクト X の開発者は、Tag Project: X がついたリソースのみ編集可能」といった運用。組織が巨大化しても非常に柔軟に対応できます。

### 2. Permissions Boundary と SCP
- **Boundary**: 「権限昇格」を防ぎます。開発者が Admin ロールを作成できたとしても、そのロールは開発者の Boundary によって制限されます。
- **SCP**: **AWS Organizations** における集中管理ツール。数百のアカウント全体で危険なアクションを一律に禁止します。

### 3. 2026 年最新アップデート: AI ガバナンス・アイデンティティ 🚀
- **Amazon Q for IAM (2026)**: 複雑な JSON ポリシーを一から書く必要はありません。「日本国内の IP から勤務時間内のみ S3 の読み取りを許可する Lambda 用ロールを作って」と伝えるだけで、AI がポリシーを作成し、脆弱性がないかシミュレーションを実行します。
- **IAM Access Analyzer 2.0 (2026)**: 90 日間使用されていないロールや、権限が広すぎる（Over-privileged）ロールを自動検知します。AI が「このロールは付与された 50 の権限のうち 3 つしか使っていません。権限を縮小しますか？」と提案します。
- **パスキーと生体認証 (2026)**: AWS コンソールへのログインが完全にパスワードレス（FIDO2）になりました。指紋や顔認証を利用することで、パスワード漏洩や MFA 詐欺のリスクを完全に排除します。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実務シチュエーション：** 「たとえ Admin であっても、S3 内のセキュリティログを削除できないようにするにはどうしますか？」

**マスターアーキテクトの回答例：**
「3 つの防御層を構築します：
1. **SCP**: 全アカウントに対し、ログバケットへの `s3:Delete*` アクションを一律禁止します。
2. **S3 Object Lock (Compliance Mode)**: 物理的に X 年間削除できないようロックをかけます。
3. **Permissions Boundary**: Admin であってもこのバケットのポリシーを修正できないよう制限します。
2026 年なら、**Amazon Q** を併用して常時監視を行い、ログへの不審なアクセスを試みるアカウントを自動的に『凍結』させます。」

# 🔦 CASE STUDY: Capital One と S3 設定ミスから学んだ教訓

**背景:** 2019 年、米国の金融大手 Capital One で、1 億人以上の顧客に影響を与える大規模なデータ漏洩が発生しました。原因は AWS の脆弱性ではなく、顧客側のセキュリティ設定ミスでした。

**課題:** 攻撃者は Capital One の Web アプリの **SSRF (Server-Side Request Forgery)** 脆弱性を利用し、その EC2 インスタンスのロール（権限）を奪取しました。このロールには「広すぎる」権限が与えられており、数百の S3 バケットを閲覧・ダウンロードすることが可能でした。

**高度な IAM による解決策（2026 年基準）:**
1.  **Permissions Boundary の適用**: 現在、Capital One のアーキテクトは **Permissions Boundary** を使用して、EC2 ロールの最大権限を厳格に制限しています。たとえ開発者が誤って「S3 フルアクセス」を与えても、Boundary で「特定の 1 バケットのみ」と制限されていれば、他のデータは守られます。
2.  **SCP による「パブリック公開」の禁止**: **AWS Organizations** を通じて、全アカウントで S3 の「ブロックパブリックアクセス」をオフにすることを一律禁止する **SCP** を設定。人為的な「うっかりミス」を組織レベルで防ぎます。
3.  **AI によるリアルタイム監視**: 2026 年には AI 版 **Access Analyzer** を活用。必要以上の権限を持つロールが作成されると、AI が即座に警告を発し、余分な権限を自動的に「トリミング（削除）」します。
4.  **パスキー認証**: 技術スタッフは **パスキー（生体認証）** でコンソールにアクセス。たとえパスワードを盗まれても、本人の指紋や顔がなければログインできません。

**結果:**
- 設定ミスによるデータ漏洩を完全に防止。
- 世界で最も厳しい金融セキュリティ基準を達成。
- 権限の監査と付与の 90% を自動化。

**BrSE への教訓:** 日本の顧客は情報セキュリティに対して非常に敏感です。ソリューションを提案する際は、**SCP** や **Boundary** を使用して「多層の防御網」を張っていることを強調しましょう。個人の小さなミスが企業全体の崩壊に繋がらない仕組みこそが、信頼の源泉です。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — 「デフォルト拒否」の哲学**: 最初はすべてを禁止し、必要な権限だけを一つずつ許可しましょう。ポリシー内でワイルドカード (`*`) を多用してはいけません。`s3:*` ではなく、`s3:GetObject` など具体的に指定しましょう。

> **Tip 2 — SCP は IAM ポリシーではない**: SCP はあくまで「フィルター」であることを忘れないでください。SCP それ自体は権限を与えず、禁止するだけです。SCP で許可されていても、IAM ポリシーで拒否されていれば、最終結果は **「拒否」** です。

> **Tip 3 — 大規模プロジェクトには ABAC**: 100 のプロジェクトに 100 のポリシーを作る代わりに、**属性ベースのアクセス制御**を使いましょう。「Tag Project=A を持つ人は、Tag Project=A を持つリソースを編集できる」というルールを作れば、新しいプロジェクトが増えてもタグを付けるだけで済みます。

> **Tip 4 — Access Advisor を常にチェック**: 権限を削除する前に、IAM コンソールの **Access Advisor** タブを確認しましょう。その権限が最後にいつ使われたか（例：200 日前など）が分かり、安全に削除できます。
