# 🪝 THE HOOK: 「チャットボットから『バーチャル社員』へ」

ほとんどの人は、AI を「辞書」のように使っています。質問して、AI が答える。それだけです。
しかし、次のようなことができる AI を想像してみてください：
- 顧客がメッセージを送ります：「来週、予算 7 万円以内で東京行きの航空券を予約してほしい」
- AI が自動的に：
    1. 航空会社のシステムで価格を調べる。
    2. あなたの Outlook のスケジュールを確認する。
    3. 複数の便を比較し、最適な便を選択する。
    4. あなたに確認のメッセージを送る。
    5. 支払いを実行し、電子チケットをメールで送る。

これはもはや「チャット」ではありません。これは **AI エージェント** です。目標を達成するために **思考（Reasoning）** し、**行動（Acting）** する実体です。

**Day 53: Agentic Workflows** へようこそ。今日は「仕事をする AI」の時代へと足を踏み入れます。

# 🎭 ANALOGY: AI エージェントは「有能な執事（バトラー）」

通常の AI と AI エージェントの違いを見てみましょう：

### 📖 1. 通常の AI - 図書館員
- あなたの質問：「ラーメンの作り方は？」
- 図書館員：「これがラーメンの作り方の本です」（答えたら任務完了）。

### 🤵 2. AI エージェント - 有能な執事
- あなたの要望：「今夜はラーメンが食べたい」
- 執事：
    - 思考：「麺、スープ、具材が必要だ」
    - 行動：自分でスーパーへ買い出しに行き、キッチンで調理し、テーブルに並べます。
    - もしスーパーに麺がなかったら？ 執事は自ら考えます：「別の店に行くか、自家製麺を作るか？」

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. ReAct パターン (Reason + Act)
これはほとんどの AI エージェントの「脳」となる仕組みです：
-   **Thought (思考)**: AI がユーザーのリクエストを分析し、計画を立てます。
-   **Action (行動)**: AI がツール（API）を呼び出して、情報を取得したり変更を実行したりします。
-   **Observation (観察)**: ツールからの結果を受け取り、「完了したか？ 次に何が必要か？」を評価します。

### 2. Amazon Bedrock Agents
AWS のマネージドサービスを使用して、エージェントを迅速に作成できます：
-   **Instruction (指示)**: エージェントの「性格」と「任務」を定義します（システムプロンプト）。
-   **Action Groups**: エージェントが実行を許可される API（Lambda）のセット。
-   **Knowledge Bases**: エージェントが必要に応じて検索できる社内ナレッジ。
-   **Traceability (追跡可能性)**: エージェントの思考プロセス（思考 -> 行動 -> 観察）をステップごとに確認できます。

### 3. マルチエージェント・オーケストレーション (2026 GA) 🚀
現実には、一人のエージェントですべてをこなすのは困難です。エージェントの「軍団」が必要です：
-   **Manager Agent**: リクエストを受け取り、部下のエージェントに仕事を割り振ります。
-   **Researcher Agent**: 情報収集の専門家。
-   **Coder Agent**: コード記述の専門家。
-   **Reviewer Agent**: 他のエージェントの結果を検証する専門家。
-   **AWS Step Functions**: エージェント間のワークフローを調整し、エラー処理（リトライ）や長期的な状態管理を行います。

### 4. 2026 年最新アップデート: エージェントの進化
-   **Autonomous Agents v2**: 過去の失敗から自ら学習し、将来の計画を改善する能力を持ちます。
-   **Bedrock Agents + AWS AppFabric**: 複雑な統合コードを書くことなく、Slack, Salesforce, Jira, Zoom などの数十の SaaS アプリケーションと自動的に連携できます。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実務シチュエーション：** 「返金リクエスト（Refund）を自動処理するシステムを構築したい。プロセスは、購入履歴の確認、返金理由の検証、5,000 円以下なら承認、そして通知メールの送信です。どのように設計しますか？」

**マスターアーキテクトの回答（BrSE 2026）：**
「**Amazon Bedrock Agents** と **AWS Step Functions** を組み合わせて構築します：
1. **Agent**: 顧客と対話し、返金理由を理解する『窓口』となります。
2. **Action Groups (Lambda)**: 
    - `CheckOrderHistory`: RDS データベースを確認。
    - `ValidatePolicy`: リクエストを返金ポリシーと比較。
3. **Step Functions**: 承認プロセスを調整します。金額が 5,000 円を超える場合は、Step Functions が人間による承認を待つフロー（Human-in-the-loop）に移行します。
4. **Trace**: Bedrock の Trace 機能を使用して、返金が拒否された理由を顧客や法務部門に説明できるようにします。」

# 🔦 CASE STUDY: 多国籍企業向けの IT サポート自動化システム

**背景:** 従業員が頻繁にパスワードを忘れたり、ソフトウェアのアクセス権限を必要としたりしていました。IT チームは繰り返されるチケット対応で過負荷状態でした。

**マスターアーキテクトの解決策:**
1.  **IT ヘルプデスク・エージェント**: 会社の Slack に統合。
2.  **エージェントのスキル**:
    - マニュアルの読み込み（RAG）。
    - パスワードリセット（Active Directory に接続された Lambda 経由）。
    - 複雑な問題の場合、Jira チケットを作成。
3.  **安全性**: 管理者権限の付与などの機密アクションは、エージェントが Step Functions + SNS を通じて上司のスマートフォンに承認依頼を送るように設定。

**結果:** 基本的な IT リクエストの 70% が 1 分以内に自動処理されました。IT スタッフは深刻なインシデントに集中できるようになりました。

**BrSE への教訓:** 顧客は常に「自動化（Automation）」を求めています。エージェントを設計する際は、最も繰り返される小さな作業から始めましょう。そして常に忘れないでください：**自動化が進むほど、制御（セキュリティと人間による承認）が必要になります**。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — 無限ループの防止**: エージェントが思考に陥り、結果を出せずに無限ループに陥ることがあります。`Max Iterations`（通常 5-10 ステップ）を設定し、自動的に停止してエラーを報告するようにしましょう。

> **Tip 2 — ツールは小さく保つ**: 100 個のことができる巨大な Lambda を一つ渡すのではなく、単機能のツール（Atomic Tools）に分割して渡しましょう。そうすることで、エージェントは正しくツールを選択しやすくなります。
