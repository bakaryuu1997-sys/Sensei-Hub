# 🪝 THE HOOK: 「渋谷のラーメン店と100万回再生の動画」

あなたが東京・渋谷にある小さなラーメン店を経営していると想像してください。普段は2人の料理人で一時間あたり30人のお客さんをさばいています。すべては順調でした。

しかし突然、登録者数500万人を超える有名YouTuberが来店し、「日本一のラーメンだ！」と動画をアップしました。動画は30分で拡散（バズ）り、店の前には5ブロック先まで続く長蛇の列が。キッチンはパニックになり、ホールのスタッフは立ち尽くし、予約サイトは同時に5万人のアクセスが集中してサーバーダウン……。

インターネットの世界では、このようなシナリオが毎日起きています。楽天のフラッシュセール、Amazonのブラックフライデー、あるいは日本代表が勝利したワールドカップ。システムが「**自動的に援軍を呼ぶ方法**」を知らなければ、最も重要なタイミングであなたのウェブサイトは「沈黙」してしまいます。

**Elastic Load Balancing (ELB)** と **Auto Scaling Group (ASG)** は、システムを「**自動変身**」させるコンビです。数分のうちに小さなラーメン店から巨大なスーパーマーケットへと姿を変え、夜が明ければコスト削減のために元の姿に戻ります。

# 🎭 ANALOGY: 繁忙期の羽田空港

羽田空港のお盆休みや年末年始の運用を考えてみましょう。

### Elastic Load Balancer — チェックインカウンターの案内係

案内係がロビーに立ち、ゲートから流れ込む客の様子をリアルタイムモニターで見張っています。
- 1番カウンターが50人待ち — **過負荷**。4番カウンターへ誘導。
- 3番カウンターが5人待ち — **余裕あり**。3番へ誘導。
- 7番カウンターのPCが故障 — **案内を即座に停止**。

ELBは、一部のサーバーが「過労死」し、他のサーバーが「暇を持て余す」ことがないように調整します。そしてサーバーが故障した際は、人間が気づく前にそこへの通信を遮断します。

### Auto Scaling Group — 超能力を持つ人事部長

部長は管制室に座り、CPU使用率や待機人数を監視しています。
- 行列が長すぎる（CPU > 70%）：指を鳴らすと、3分以内に **10人の新人スタッフ** が現れます。
- 乗客がいなくなった：「みんな帰っていいよ。コスト削減だ。」 — 不要なインスタンスを **自動終了**。
- 一人のスタッフが倒れた：その人を休ませ、2分以内に **全く同じ能力を持つ新人** を補充します。

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. Elastic Load Balancing — 用途に合わせた3つのタイプ

**Application Load Balancer (ALB) — レイヤー7 (アプリケーション):**
- HTTPリクエストの内容を理解できる最も賢いタイプ。
- URLパスによる振り分け：`/api/*` → APIサーバーへ、`/images/*` → 画像サーバーへ。
- HTTPヘッダーによる振り分け：iPhoneユーザー → iOS用バックエンド、Android → Android用バックエンド。
- WebSocketやgRPCをサポート。チャットアプリやリアルタイムダッシュボードに最適。
- **用途:** Webアプリ、REST API、マイクロサービス。2026年現在の標準。

**Network Load Balancer (NLB) — レイヤー4 (TCP/UDP):**
- 超高速：1ミリ秒未満の遅延で **毎秒数百万リクエスト** を処理。
- パケットの中身は見ず、IPとポート番号だけで判断。
- 静的IP（Static IP）をサポート。顧客側でIPのホワイトリスト登録が必要な場合に必須。
- **用途:** オンラインゲーム、証券取引、動画配信、TCP/UDPワークロード。

**Gateway Load Balancer (GWLB) — レイヤー3 (ネットワーク):**
- ファイアウォールや侵入検知（IDS/IPS）などのネットワークアプライアンスのスケーリングに特化。

### 2. Auto Scaling Group — 2026年のインテリジェントなスケーリング

**機械学習による予測スケーリング (Predictive Scaling):**
- AWSが **過去14日間のトラフィック履歴** を分析してパターンを予測します。
- 「毎週金曜の18時〜22時はトラフィックが400%増えるから、17時45分からサーバーを増やしておこう」と判断。
- 「遅くなってから増やす」のではなく、「**必要になる前に増やす**」プロアクティブな対応が可能です。

**動的スケーリング (Dynamic Scaling) — 3つの戦略:**
- **ターゲット追跡 (Target Tracking)**: CPU使用率を常に60%に保つように設定。ASGが自動で必要台数を計算。最も簡単で推奨される方法。
- **ステップスケーリング**: CPU 70%以上 → 2台追加、80%以上 → 5台追加、90%以上 → 10台追加のように、負荷に応じて段階的に反応。
- **簡易スケーリング**: アラーム発生時に固定数を増減。

**クールダウン期間 (Cooldown Period):**
- スケーリング実行後、一定時間（デフォルト300秒）待機してから次のアクションを起こします。
- 「増やす → 起動中につきCPU高止まり → さらに増やす → 起動完了でCPU急落 → 減らす」という過剰反応を防ぎます。

### 3. 高可用性（HA）アーキテクチャ — 2026年の標準設計

**マルチAZ配備 (Multi-AZ Deployment) — 商用環境の鉄則:**
ELBとASGを3つのアベイラビリティゾーン（AZ）に分散させます。一つのAZ全体が停電しても、他のAZでシステムが動き続けます。

**ヘルスチェック — HAの心臓:**
- ELBは30秒ごとに `/health` エンドポイントを叩きます。
- 失敗が続くとインスタンスを「異常 (Unhealthy)」とマークし、通信を送るのをやめます。
- ASGがその異常を検知し、古いインスタンスを破棄して新しいものを立ち上げます。

# ☁️ AWS IN PRACTICE / INTERVIEW

**面接シチュエーション：** 「ECサイトを運営しています。普段は毎分100ユーザーですが、ブラックフライデーには2時間だけ毎分5万ユーザーに激増します。高可用性とスケーリングをどう設計しますか？」

**マスターアーキテクトの回答例：**
「3つのレイヤーで設計します：
1.  **プロアクティブ（先行）防御**: ブラックフライデーの30分前から **スケジュールスケーリング** で50台追加しておきます。過去の履歴があるなら **予測スケーリング** も併用します。
2.  **リアルタイム反応**: **ターゲット追跡ポリシー** でCPUを60%に維持します。予測以上のスパイクが来てもASGが3〜5分以内に追随します。
3.  **コスト最適化**: キャパシティの40%に **スポットインスタンス** を採用します。オンデマンドより70%安く、中断されてもASGが自動でオンデマンドに切り替えてHAを維持します。
セッション状態はEC2ではなくElastiCache（Redis）に保存し、どのインスタンスがリクエストを受けても継続できるようにします。」

# 🔦 CASE STUDY: Amazon Prime Day 2023 — 世界で最も過酷なスケーリング

**背景:** 2023年のプライムデーでは、48時間で3億7500万個の商品が販売されました。トラフィックは通常時の25倍。皮肉なことに、Amazon.comを落とさないためにAWSがこの課題を解決しなければなりませんでした。

**技術的解決策:**
- **ECS Fargate + ALB:** コンテナベースのスケーリングを採用。EC2の起動を待つ時間を短縮し、30秒で拡張可能にしました。
- **Spot Instances の活用:** キャパシティの多くをスポットインスタンスで賄い、インフラコストの爆発を抑えました。
- **ElastiCache (Redis):** リクエストの90%以上をキャッシュで処理し、背後のデータベースへの負荷を最小限に抑えました。

**結果:** 48時間を通して **ダウンタイム・ゼロ** を達成。インフラコストはトラフィック増（25倍）に対し、わずか8倍の増加に抑えられました。

**BrSEへの教訓:** スケーリングとは単に「サーバーを増やす」ことではありません。**「キャッシュ + 水平スケーリング + スポット最適化」** の組み合わせです。顧客への提案時にはこの3レイヤーで構成を説明してください。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — ヘルスチェックは「賢く」作る**: `/health` が常に200を返すだけでは不十分です。「DBに繋がるか？」「メモリは足りているか？」までチェックさせましょう。アプリがDB接続エラーを吐いているのにELBがリクエストを送り続ける、という事態を防げます。

> **Tip 2 — インスタンスの「ウォーミングアップ」を忘れずに**: 新しいサーバーが立ち上がっても、JVMやコネクションプールが温まるまでには時間がかかります。ALBの **Slow Start Duration** を設定して、徐々にトラフィックを流し込みましょう。

> **Tip 3 — 最小容量 (Min Capacity) は常に2以上に**: コストをケチって最小1にすると、その1台が壊れた瞬間にダウンタイムが発生します。高可用性を謳うなら、常に2台以上で待機させるのが鉄則です。

> **Tip 4 — スケールインは「慎重に」**: トラフィックが減った瞬間にサーバーを消すと、直後の小さなスパイクでパンクします。クールダウン期間を長めに設定し、安定を確認してから台数を減らしましょう。
