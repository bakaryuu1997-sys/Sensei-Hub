# 🪝 THE HOOK: 「深夜 2 時のミステリー」

あなたは巨大な E コマースシステムを運用しています。深夜 2 時、電話が鳴り響きます。怒った顧客の声です。「決済ができない！ 曖昧なエラーが出るぞ！」

あなたはパソコンを開きます。システムには 50 台のサーバー、5 つのデータベース、20 個の Lambda 関数があります。あなたはパニックに陥ります：
- どのサーバーでエラーが起きているのか？
- データベースが遅いのか、それとも決済ゲートウェイ（外部サービス）が落ちているのか？
- 顧客の「リクエスト」は、この複雑なサービスの迷宮のどこで止まっているのか？

監視ツールがなければ、このエラー探しは暗闇の中で針を探すようなものです。**Amazon CloudWatch** と **AWS X-Ray** へようこそ。これらはクラウドシステムの「監視カメラ」と「X 線検査機」の役割を果たします。

---

# 🎭 ANALOGY: 「近代的な病院」の管理

あなたが**近代的な病院**を管理していると想像してみましょう。

### 🌡️ 1. CloudWatch Metrics: バイタルサイン（生命兆候）
- CloudWatch Metrics は心拍計や血圧計のようなものです。「心拍数 80、体温 37 度」といった数字を報告します。
- もし心拍数が 150（CPU 使用率 90%）に跳ね上がれば、アラーム（**CloudWatch Alarm**）が鳴り響きます。

### 📝 2. CloudWatch Logs: 詳細なカルテ（診療録）
- Metrics（数字）は「何が」起きているか（心拍が速い）は教えてくれますが、「なぜ」は教えてくれません。
- CloudWatch Logs はカルテのようなものです。「午前 2 時 05 分、患者が薬 A を飲み間違えた」。ログを読むことで、根本原因（Root Cause）を突き止められます。

### 🔬 3. AWS X-Ray: X 線写真（レントゲン）
- X-Ray はリクエストの流れを可視化します。「ユーザー -> API -> Lambda -> DB と進むのに何秒かかったか」。どこかが詰まっている（血流が悪い）箇所は、写真上で赤く表示されます。

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. Amazon CloudWatch
- **Metrics**: CPU、ネットワーク、ディスクなどを収集（詳細モニタリングでは 1 分間隔）。
- **CloudWatch Agent**: OS にインストールして、AWS がデフォルトでは見ることができない **メモリ使用率** や **ディスク空き容量** などの「内部」指標を測定します。
- **Logs Insights**: SQL のようなクエリを使って、数テラバイトのログから数秒で特定の情報を検索できます。
- **Synthetics Canaries**: 「仮想顧客ロボット」が自動でウェブサイトにアクセスして注文を試し、本物の顧客が困る前に異常を検知します。

### 2. AWS X-Ray
- **Service Map**: サービス間の接続マップを描画します。
- **Trace ID**: 各リクエストに一意の ID を付与し、複数のマイクロサービスを横断するリクエストの全行程を追跡します。

### 3. 2026 年最新アップデート: AI オブザーバビリティの時代 🚀
- **Amazon Q in CloudWatch Logs**: 2026 年、複雑なクエリを自分で書く必要はありません。「2 時にアプリが遅くなったのはなぜ？」と聞くだけで、AI が何十億行ものログをスキャンし、「データベースのテーブルロックが原因です」と答えてくれます。
- **CloudWatch Application Signals (2026)**: コードを一行も変更することなく、アプリケーションのゴールデンシグナル（遅延、エラー、スループット）を自動収集します。
- **AI-Powered Alarms**: 「80% 以上」といった固定値ではなく、AI がシステムの「普段の癖」を学習し、いつもと違う「異常な振る舞い」をした時だけ賢くアラートを出します。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実務シチュエーション：** 「アプリが遅いのですが、CPU やメモリの使用率は低く、ログにもエラーが出ていません。どう調査しますか？」

**マスターアーキテクトの回答例：**
「これはオブザーバビリティ（可観測性）の課題です。まず **AWS X-Ray** の **Service Map** を確認し、どのフェーズで遅延が発生しているか特定します。もしデータベース層で遅延があれば、**CloudWatch Logs Insights** と **Amazon Q (2026)** を併用して遅い SQL クエリを分析します。また、**CloudWatch Agent** を導入して、コネクションプールやスレッド待機などの深い指標をチェックし、ボトルネックを突き止めます。」

# 🔦 CASE STUDY: Coinbase と仮想通貨取引所の監視術

**背景:** Coinbase は毎分何百万もの取引を処理しています。仮想通貨の世界では、1 秒のダウンタイムが数百万ドルの損失と顧客の信頼喪失に直結します。彼らのシステムは、EKS (Kubernetes) と Lambda 上で動く数千のマイクロサービスで構成されています。

**課題:** ビットコインなどの価格が急変動すると、アクセスが通常の 100 倍に跳ね上がります。システム全体が崩壊する前に、どのサービスが「悲鳴を上げ始めているか」をどう早期発見するか？

**CloudWatch & X-Ray による解決策（2026 年基準）:**
1.  **Metric Math による早期警告システム**: 単なる CPU 測定ではなく、` (エラー数 / 総リクエスト数) * 100 ` といった複雑な指標を **Metric Math** で算出。エラー率が 2 分間で 1% 上昇したら、即座に緊急オートスケーリングを発動させ、Slack に警告を送ります。
2.  **X-Ray による「静かな殺し屋」の追跡**: 各取引に Trace ID を付与。ある時、中間サービスが 200ms だけ遅延しました。これは CPU アラームを鳴らすほどではありませんでしたが、決済チェーン全体を詰まらせていました。**X-Ray Service Map** により、そのサービスの「赤い点」を即座に発見し、5 分で修正しました。
3.  **Amazon Q による超速ログ分析 (2026)**: 2026 年、エンジニアは何テラバイトものログを手動でフィルターする代わりに、「Q、過去 15 分間でタイムアウトした取引を特定して」と指示。AI は即座に Trace ID と「サードパーティ API の応答が 500ms を超えているため」という理由を返します。
4.  **Synthetics Canaries (仮想顧客)**: 日本、米国、欧州など世界中に数百の「Canaries」を配置し、1 分ごとにログインや残高確認を試行。日本だけが遅い場合、アジア圏のネットワーク経路に問題があると即座に判断できます。

**結果:**
- システムの稼働率（Uptime） **99.999%** を達成。
- 平均故障検知時間 (MTTD) が 15 分から **1 分未満** に短縮。
- AI 駆動型アラームにより、運用チームの「誤報」への対応が 70% 削減。

**BrSE への教訓:** 日本の顧客はシステムの「突然死」を非常に嫌います。ソリューションを提案する際は、必ず **「Observability Plan（監視計画）」** をセットで提示しましょう。X-Ray を使って「なぜアプリが遅いのか」を論理的に説明できる能力は、顧客からの信頼を勝ち取る最大の武器になります。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — Embedded Metric Format (EMF) の活用**: `PutMetricData` API を呼ぶ代わりに、ログを EMF 形式で出力しましょう。CloudWatch がログから自動的にメトリクスを抽出してくれるため、API コストを抑えつつ高速にメトリクスを生成できます。

> **Tip 2 — Contributor Insights で「犯人」を特定**: 「リクエストを最も多く送っている上位 10 顧客」や「負荷の高い上位 10 個の SQL」などを特定できます。DoS 攻撃の対策やヘビーユーザーの特定に極めて有効です。

> **Tip 3 — X-Ray サンプリングルール**: 全リクエストを記録するとコストがかさみ、アプリも重くなります。「エラー（5xx）は 100% 記録し、成功（2xx）は 5% だけ記録する」といったサンプリングルールを構成しましょう。

> **Tip 4 — Amazon CloudWatch Application Insights**: これは「かかりつけ医」のような存在です。.NET、Java、SQL Server などの技術スタックを自動認識し、重要なダッシュボードやアラームを自動でセットアップしてくれます。

> **Tip 5 — アラームと Lambda の連携 (自己修復)**: 警告メールを受け取って手動で直すのではなく、アラームから **Lambda** を呼び出しましょう。例えば、メモリ不足を検知したら Lambda が自動でサービスを再起動したり不要なファイルを削除したりする **「自己修復インフラ」** を目指しましょう。
