# 🪝 THE HOOK: 「新宿の真ん中にある、ドアのないマンション」

東京・新宿のど真ん中に建つ、100階建ての巨大なタワーマンションに住んでいると想像してみてください。そこには何千もの部屋がありますが、奇妙なことに、すべての住人が決して鍵のかからない一つのメインドアを共有し、大きな共用バスルームを使い……そして、廊下を歩いている人なら誰でも、いつでもあなたのリビングルームに足を踏み入れることができるのです。

そんな部屋に、あなたのお金やビジネスの機密情報を置いておく勇気がありますか？間違いなく **「いいえ」** でしょう。

インターネット全盛の2026年、ネットワーク保護メカニズムを持たずにクラウド上でサーバーやデータベースを動かすことは、顧客データを満載したコンピュータを渋谷のスクランブル交差点のど真ん中に放り出しておくのと同じです。何十億ものボットや悪意のあるAIが、24時間365日、そのような「ドアのない部屋」を探し回っています。

**Amazon VPC (Virtual Private Cloud)** はその解決策です。AWSという広大な宇宙の中に、完全に隔離された「自分専用の土地」を切り出すことができます。壁を築き、門番を置き、信頼できる人だけが入れるようにする全権限があなたに与えられます。

# 🎭 ANALOGY (現実世界の例え)

あなたが **「高級なプライベート別荘地 (VPC)」** を設計していると考えてみましょう。

### 🧱 1. VPC (全体のフェンス)
VPCは、敷地全体を囲む高い壁です。あなたの空間を隣の家から切り離します。隣の家が火事になっても、この壁のおかげであなたの家まで火が燃え移ることはありません。

### 🚪 2. インターネットゲートウェイ (メインゲート)
別荘地と大通り（インターネット）を結ぶ唯一の門です。
- お客さんを招き入れたいなら、この門を開けます。
- 完全に隠居したいなら、この門を取り外してしまいます。

### 🛋️ 3. パブリックサブネット (受付・応接室)
メインゲートのすぐ後ろにあるエリアです。世界中の人が見に来るウェブサイトを置く場所です。
- メインゲートへ直通する道（**ルートテーブル**）が設定されています。

### 🔐 4. プライベートサブネット (金庫室)
奥深くにあり、入るには何重もの内部セキュリティを通過しなければなりません。データベースを置く場所です。
- 外の通りを歩いている人からは、この部屋の存在すら見えません。
- メインゲートへの直通ルートはありません。

### 🪟 5. NAT ゲートウェイ (一方通行の荷出し窓)
時々、金庫室の人が新しいソフトウェアをダウンロードしたり、ウイルス対策の更新（インターネットからの取得）が必要になることがあります。彼らはメインゲートからは出られません。
- そこで「一方通行の窓（NAT ゲートウェイ）」を使います。中から手を伸ばして物を受け取ることはできますが、外の人がこの窓から中に手を突っ込むことはできません。

# ⚙️ UNDER THE HOOD (ディープダイブ)

### 1. CIDR と IP プランニング
VPCの設計は、**CIDR**（例：`10.0.0.0/16`）というIPアドレスの範囲を選ぶことから始まります。
- **サブネット (Subnet)**: 大きなIP範囲を、各部屋（サブネット）用の小さな範囲に分割します。
- **2026年の注意点**: 世界中でIPv4アドレスが枯渇しています。2026年のAWSでは **IPv6-only VPC** アーキテクチャが推奨されています。IPv6はほぼ無限のアドレスを提供し、拠点間接続（VPCピアリング）時のIP重複の心配を過去のものにしました。

### 2. 二つの鉄壁：セキュリティグループ vs ネットワークACL
ここが最も難しく、かつ重要な部分です：
-   **セキュリティグループ (部屋のドアの守衛)**:
    - **インスタンス**（サーバー）単位で動作します。
    - **ステートフル (Stateful)** 性質：入ってくる通信を許可すれば、AWSが自動的に帰りの通信も許可してくれます。賢くて使いやすいのが特徴です。
-   **ネットワークACL (敷地の門の守衛 - サブネット単位)**:
    - **サブネット**単位で動作します。
    - **ステートレス (Stateless)** 性質：入れるルールを書いたら、出るルールも手動で書かなければなりません。書かなければお客さんは中に閉じ込められてしまいます。これはセキュリティグループが設定ミスをした際の、強力な「バックアップの盾」となります。

### 3. VPC Lattice: 2026年の接続革命 🚀
以前は、異なるVPCにある2つのサービスを繋ぐのは、ルーティングやピアリングの設定が複雑で「悪夢」のようでした。
- **VPC Lattice** はその複雑さを完全に排除しました。これはアプリケーション層のネットワークとして機能します。
- 「サービスAがサービスBを呼び出せる」と宣言するだけで、Latticeがルーティング、セキュリティ、負荷分散をすべて自動で処理します。IP範囲やルートテーブルをいじる必要はもうありません。

### 4. Network Access Analyzer (AI監査人)
あなたのデータベースに、インターネットから侵入できる経路が100%存在しないと、どうやって確信を持てますか？
- **Network Access Analyzer** は形式手法（数学的な証明アルゴリズム）を使用して、ネットワーク構成全体をスキャンします。そして「おい、5番のネットワークACLに隙間があるぞ。ここからデータベースが露出する可能性がある」と正確に指摘してくれます。これは現代のBrSEにとって不可欠なツールです。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実戦シチュエーション：** 「あなたのシステムには、Webサーバー（パブリックサブネット）とデータベース（プライベートサブネット）があります。Webサーバーからデータベースに接続できません。どのように診断しますか？」

**マスターの回答例：**
「OSI参照モデルを逆行する形で、以下の4ステップで確認します。
1.  **インスタンス層**: データベースの **セキュリティグループ** が、WebサーバーのIPアドレスからのポート3306（MySQLの場合）を許可しているか確認します。
2.  **サブネット層**: 両方のサブネットの **ネットワークACL** に、戻りのトラフィックをブロックする拒否ルールがないか確認します。
3.  **ルーティング層**: パブリックサブネットの **ルートテーブル** に、データベースへ到達するための内部ルート（`10.0.0.0/16 -> local`）が存在するか確認します。
4.  **2026年流**: **AWS Reachability Analyzer** を実行します。このツールは実際のパケットを飛ばさずにネットワーク経路をシミュレーションし、どこのコンポーネントが（どのような理由で）通信をブロックしているかを瞬時に特定してくれます。」

**試験のヒント:** 「**インターネットゲートウェイ** と **NAT ゲートウェイ** の違いは何ですか？」
-   **インターネットゲートウェイ**: VPCとインターネットの間で双方向（入出力）の通信を許可します。
-   **NAT ゲートウェイ**: プライベートサブネットにあるサーバーからインターネットへの一方通行（出力のみ）の通信を許可し、外部からの侵入を防ぎます。

# 🔦 CASE STUDY: 楽天グループと高セキュリティVPCアーキテクチャ

**背景:** 日本最大級のECサイトを運営する楽天グループは、一日数百万件の取引を処理し、数千万人のクレジットカード情報を扱っています。AWSへの移行にあたり、国際的なクレジットカード業界のセキュリティ基準である「PCI-DSS」の厳しい要件を満たすVPC設計が求められました。

**課題:** PCI-DSSでは、カード会員データ環境 (CDE) をインターネットや他の無関係なシステムから **完全に隔離** することが求められます。違反があれば、多額の罰金やカード決済権限の剥奪に繋がります。

**楽天の多層VPCソリューション:**
- **第1層 — パブリックサブネット (DMZ):** Application Load BalancerとNATゲートウェイのみを配置。データ処理サーバーはここには決して置きません。セキュリティグループは443番（HTTPS）のみを許可。
- **第2層 — プライベートサブネット (アプリ層):** Web/APIサーバーが稼働。NAT経由で外へアップデートを取りに行けますが、外からは直接入れません。ロードバランサーからの特定のポートのみを許可。
- **第3層 — 隔離サブネット (CDE):** データベースと決済処理サービスを配置。NAT経由の **インターネット接続すら禁止**（Zero Internet Access）。アプリ層からの内部通信のみを許可。
- **付加層 — VPC エンドポイント:** S3やDynamoDBへの接続にインターネットを経由せず、AWSの内部ネットワークのみを通る **VPC エンドポイント** を活用。

**結果:**
- 設計からわずか **6ヶ月** でPCI-DSS Level 1の認定を初取得。
- 3年間の運用でネットワーク経由のセキュリティインシデントは **ゼロ**。
- AWSが多くのコンプライアンスレポートを提供しているため、監査費用をオンプレミス時代より **40%削減**。

**BrSEへの教訓:** 日本の金融やEC業界の顧客向けにVPCを設計する際は、まず **「準拠すべき基準は何か？ (PCI-DSS, FISC, ISMSなど)」** を確認してください。その答えがネットワーク構成のすべてを決定します。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — CIDRプランニングはやり直しが効かない**: VPC作成時に選ぶCIDR（例：`10.0.0.0/16`）は、一度作成すると後から変更や縮小ができません（拡張は可能）。最初から慎重に計画しましょう。`10.0.0.0/16` は65,536個のIPを持て、大企業でも十分なサイズです。

> **Tip 2 — セキュリティグループはステートフル**: インバウンド（入り）を許可すれば、アウトバウンド（出）のルールをわざわざ書かなくても戻りの通信は通ります。対してネットワークACLは「ステートレス」なので、両方向のルールを書く必要があります。

> **Tip 3 — インターネットからEC2へ直接SSHするな**: 代わりに **AWS Systems Manager Session Manager** を使いましょう。22番ポートを開ける必要がなく、キーペアも不要、コマンド履歴もすべてログに残ります。これが2026年の標準的な接続方法です。

> **Tip 4 — ピアリングかTransit Gatewayか**: 2〜3個のVPCを繋ぐならピアリング（安い、簡単）。5個以上、あるいはオンプレミスと複雑に繋ぐならTransit Gateway（一元管理可能）。10個のVPCをピアリングで網羅しようとすると45個もの接続管理が必要になり破綻します。

> **Tip 5 — フローログはVPCの「防犯カメラ」**: すべてのパケットの出入りを記録するVPCフローログを有効にしましょう。S3に保存してAthenaで分析すれば、何十億もの記録から不審なIPを数秒で特定できます。
