# 🪝 THE HOOK

ある穏やかな夜、会社のシニアDevOpsエンジニアのもとに、AWSから一通のメールが届きました。タイトルは不気味な赤文字でこう書かれていました：**「Your AWS Account usage has exceeded the budget threshold（AWSアカウントの利用料金が予算を超過しました）」**。

慌ててコンソールにログインした彼は、目の前の光景に凍りつきました。わずか4時間の間に、請求額が**15,000ドル（約230万円）**にまで跳ね上がっていたのです。アイルランドとシンガポールのリージョンで、数百台の超高額なインスタンス（強力なGPUを搭載したP3インスタンス）がフル稼働していました。謎のハッカーのために、せっせと**暗号資産（仮想通貨）をマイニング**していたのです。

2時間にわたる必死の調査の結果、原因が判明しました。あるジュニアデベロッパーがコードのエラーに焦るあまり、ルートアカウントの**アクセスキー（Access Key）**と**シークレットキー（Secret Key）**をソースコードに直接書き込み（ハードコード）、誤ってGitHubのパブリックリポジトリに`git push`してしまったのです。

知っていますか？GitHubにはハッカーが放った何千もの「ボット」が24時間365日目を光らせ、プッシュされるコードを一行ずつスキャンしています。あなたがEnterキーを押してからボットがキーを見つけ出すまで、わずか**15秒**。そして、ハッカーがあなたのAWS「王国」の全権を掌握し、パスワードを変更して、あなたの会社の資金を使い果たし始めるまで、さらに2分もかかりません。

**血の教訓：** クラウドにおいて、**セキュリティは優先順位「0」**です。アクセス権限に関する一つのミスが、莫大な金銭的損失に直結します。そして、あなたを守る最強の武器こそが**AWS IAM**なのです。

# 🎭 ANALOGY (現実世界の例え)

IAMの本質を理解するために、あなたのAWSアカウント全体を、東京の港区にあるような超高級でセキュアな**Aクラスオフィスビル**だと想像してみてください。

### 👑 ルートユーザー (Root User): ビルの所有者
ビルを借りる契約を結んだ本人です。彼はすべての部屋を開けられる**マスターキー（親鍵）**を持っています。
- この鍵一つで、社長室から金庫、電気・水道の管理室、さらにはビルの解約手続きまで、あらゆる操作が可能です。
- もしこの鍵が悪者の手に渡れば、ビル一棟を丸ごと失うことになります。
- **マスターの鉄則**: このマスターキーを普段の仕事で持ち歩いてはいけません。金庫（MFA有効化）の中に厳重に保管し、会社名の変更やアカウントの解約といった極めて特別な場合にのみ使用します。

### 👥 IAM ユーザー (IAM Users): ビルの従業員
ビルで働く従業員（エンジニア、経理、マーケティング担当者）です。一人ひとりに、名前と写真が入った**専用の社員証（IAMユーザー）**を発行します。
- 誰かが社員証を失くしても、そのカードを無効化（デアクティベート）するだけで済みます。ビル全体は安全なままです。

### 🏢 IAM グループ (IAM Groups): 部署
入り口で警備員に「Aさんは1番の部屋、Bさんも1番の部屋」といちいち指示するのは非効率です。代わりに部屋の前に「**エンジニア部**」という看板を掲げます。
- 「エンジニア部のメンバーなら、サーバー室に入室してよい」というルールを決めます。
- 新人が入ってきたら「エンジニア部」に入れるだけで、必要なアクセス権が自動的に与えられます。これがプロフェッショナルの効率的な管理方法です。

### 📜 IAM ポリシー (IAM Policies): 入退室ルール
各部屋のドアに貼られた「利用規則」です。例えば、*「この社員証を持つ人は、部屋の中の書類を閲覧できるが、持ち出しや編集は禁止する」*といった内容です。
- AWSでは、これらのルールを**JSON**という機械も人間も読みやすい論理的な言語で記述します。

### 🎭 IAM ロール (IAM Roles): 臨時用作業服
これが最も面白い概念です。人間ではないエンティティ（例えばプリンターやサーバー）が任務を遂行する必要がある場合があります。
- プリンターに社員証を持たせる代わりに、専用の**「作業服」**を用意します。
- プリンターが倉庫へ紙を取りに行くときだけ、この作業服を「着用」します。作業が終われば脱ぎ捨てます。
- この作業服には固定のパスワードがなく、数時間だけ有効な一時的な認証情報（トークン）を使います。これがクラウドにおける最高峰のセキュリティ手法です。

# ⚙️ UNDER THE HOOD (ディープダイブ)

**IAM (Identity and Access Management)** は、誰がログインできるか（認証）と、その人が何をできるか（認可）を管理する、AWSの中心的なサービスです。

### 1. ポリシー構造の解剖 (JSON)
典型的なIAMポリシーの「ルール」を見てみましょう：
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::my-company-data/*"
    }
  ]
}
```
-   **Effect**: 許可（Allow）か拒否（Deny）か。AWSでは、何も指定がなければデフォルトで「拒否」されます。もしAllowとDenyが両方存在する場合、**Deny（拒否）が常に優先されます**。
-   **Action**: 具体的なアクション。例えば `s3:GetObject` はファイルのダウンロード権限です。
-   **Resource**: 対象となる「物」。ここでは `my-company-data` というバケット内の全ファイルが対象です。

### 2. 「最小権限の原則」 (#(Least Privilege))
これはすべてのセキュリティエンジニアのバイブルです。
- アプリケーションがディスクからデータを読み取るだけでいいなら、削除や変更の権限を与えてはいけません。
- 経理担当者が請求書をチェックするだけでいいなら、サーバーを起動する権限を与えてはいけません。
- 常に最小の権限から始め、どうしても必要なときだけ権限を広げていきます。

### 3. MFA & パスキー: 最後の防衛線
**多要素認証 (MFA)** は、ルートユーザーや高い権限を持つアカウントには必須です。
- **2026年アップデート**: 世界は**パスキー (FIDO2)**へと移行しています。Google Authenticatorなどの数字を入力する代わりに、FaceID、TouchID、あるいは物理的なセキュリティキー（Yubikey）を使ってログインします。これはフィッシング攻撃をほぼ完全に防ぐ手法です。

### 4. IAM ロール vs IAM ユーザー (決定的な違い)
-   **ユーザー**: 特定の「個人」に紐付き、長期的な認証情報（ユーザー名/パスワード、アクセスキー）を持ちます。
-   **ロール**: 特定の個人に紐付きません。EC2などのサービスや、外部システム（Google/Facebook連携など）からのユーザーが一時的に権限を借りるために使用します。**ロールは長期的なキーを使用しないため、ユーザーよりも安全です。**

### 🤖 2026年トレンド: AIによるポリシー自動生成
2026年、あなたはもう複雑なJSONと格闘する必要はありません。
- **IAM Access Analyzer**にAIが統合され、ログ（CloudTrail）からポリシーを自動生成できるようになりました。アプリケーションを1日動かすだけで、AIが分析し、「これがあなたのアプリに必要な正確な最小権限（Least Privilege）です」と提案してくれます。
- **ゼロトラスト・アーキテクチャ**: すべてのアクセス要求を常に検証します。IPアドレスだけでなく、行動パターン（AIによる異常検知）も判断材料となります。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実戦シチュエーション：** 「あなたのIT会社に5人の新しいエンジニアが入社しました。上司から、彼らが東京リージョンのEC2サーバーを管理できるように権限を与えてほしいと頼まれました。AWSのベストプラクティスに則って、どのように対応しますか？」

**マスターの回答例：**
「クラウドアーキテクトとして、個々のユーザーに直接権限を与えることは決してしません。以下の手順で進めます。
1. まず、`EC2_Admins_Tokyo` という名前の **IAMグループ** を作成します。
2. AWS管理ポリシーの `AmazonEC2FullAccess` をこのグループにアタッチします。より厳密にするなら、`region: ap-northeast-1` でのみ操作できるようにポリシーをカスタマイズします。
3. 5人のエンジニアそれぞれに **IAMユーザー** を作成し、初回ログイン時に **MFA** の設定を強制します。
4. 最後に、この5人のユーザーを `EC2_Admins_Tokyo` グループに追加します。
この方法なら、将来エンジニアが増えてもグループに追加するだけで済みます。権限を一括で変更したいときも、グループのポリシーを修正するだけで完了します。」

**面接のヒント:** 「EC2で動くアプリにアクセスキーではなく **IAMロール** を使う最大の利点は何ですか？」
- **回答**: それは **「安全性」** です。アクセスキーは固定されており漏洩のリスクがありますが、IAMロールはAWSが自動的に発行・更新（ローテーション）する一時的な認証情報を使用するため、コードが万が一流出しても被害を最小限に抑えられます。

# 🔦 CASE STUDY: 金融機関におけるゼロトラストとIAM

**背景:** 日本のある大手メガバンクは、数千人の開発者がクラウドを利用する中で、内部不正や設定ミスによるデータ漏洩を極限まで減らす必要がありました。

**課題:** 従来の「境界型セキュリティ（社内ネットワークは安全）」という考え方では、VPNが破られたり、内部の人間が悪意を持った場合に防げません。

**AWS IAMによる解決策:**
- **権限のコード化 (Infrastructure as Code)**: すべてのIAMポリシーをTerraformで管理。人間が手動でコンソールから権限を変更することを禁止しました。
- **一時的な特権アクセス (Just-In-Time Access)**: エンジニアが管理者権限を必要とする場合、チャットツールで承認を得ると、AIが**1時間だけ有効なIAMロール**を自動発行します。時間が過ぎると権限は自動消滅します。
- **IAM Access Analyzerによる継続的監視**: 外部（インターネット）からアクセス可能になっているリソースがないか、AIが24時間体制で数学的に証明（フォーマル検証）します。

**結果:**
- 設定ミスによる不要な公開リソースを**100%排除**。
- 監査レポートの作成時間を数週間から**数分**に短縮。
- 「誰も信じない（検証なしには）」という**ゼロトラスト（Zero Trust）**の文化が組織に定着しました。

**BrSEへの教訓:** 日本のエンタープライズ、特に金融や公共案件では「権限管理のプロセス」が非常に重視されます。単に「動く」だけでなく、「誰が、いつ、なぜその権限を持ったのか」を説明できる設計が求められます。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — 「ルートユーザーは封印せよ」**: AWSアカウントを作ったら、まずMFAを設定し、パスワードをパスワードマネージャーに放り込んで、二度と使わないつもりでいましょう。普段は管理者権限を持つIAMユーザーを使ってください。

> **Tip 2 — 「Deny（拒否）は最強」**: ポリシーが複雑になっても、一つでも「Deny」があればそれが最優先されます。全社員にS3へのアクセスを許可していても、機密フォルダに対して「Deny」を設定しておけば安心です。

> **Tip 3 — 「タグによる権限管理 (ABAC)」**: ユーザーに「Project: A」というタグを付け、リソースにも「Project: A」と付けます。そして「同じタグを持つリソースのみ操作可能」というポリシーを一つ作れば、ユーザーが増えても個別にポリシーを修正する必要がなくなります。

> **Tip 4 — 「認証情報のローテーション」**: 2026年でも、もしアクセスキーを使う必要があるなら、90日ごとに新しく作り直す（ローテーション）のが鉄則です。AWS Secrets Managerを使えば自動化できます。

> **Tip 5 — 「マネージドポリシーを活用せよ」**: 最初から自分でJSONを書くのは大変です。まずはAWSが用意してくれている `ReadOnlyAccess` などの既存のポリシーから使い始め、徐々に絞り込んでいきましょう。
