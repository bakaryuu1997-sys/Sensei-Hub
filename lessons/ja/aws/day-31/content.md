# 🪝 THE HOOK: 「11.11 セールと Shopee の舞台裏」

あなたが **Shopee** のチーフアーキテクトとして、**11.11** の超大型セールの日に立ち会っていると想像してください。毎秒、何百万ものアクションが発生します：
1. 「支払い」ボタンのクリック
2. 在庫の確認
3. ウォレットからの引き落とし
4. クーポンの付与
5. 配送通知の送信

もし古い設計（**モノリス**）であれば、「支払い」機能は「在庫確認」の返答を待たなければなりません。たった一つのモジュールが遅れるだけで、システム全体が麻痺し、わずか数分で数十億円の売上を失うことになります。

どうすれば、お互いを待つことなく、オーケストラのように調和して動作するシステムを作れるでしょうか？ **AWS Master Professional** 段階へようこそ。今日は、**イベント駆動型アーキテクチャ (EDA)** と **マイクロサービス** について学びます。

# 🎭 ANALOGY: 「個人経営の食堂」と「現代のファストフードチェーン」

レストランの運営方法の違いで考えてみましょう。

### 🍱 1. 従来の方法（同期）: 個人経営の食堂
- あなたが注文すると、店主が厨房に走って料理を作ります。あなたはその間、カウンターの前で待ち続けます。もし店主が病気になったり厨房が火事になったりすれば、店は閉まります。1000 人の客を同時にさばくことは不可能です。

### 🏭 2. 新しい方法（イベント駆動型）: 現代のファストフードチェーン
- あなたが注文すると、レジ担当者がレシート（**イベント**）を印刷します。レジ担当者はすぐに次の客の対応に移ります。料理人はレシートを見て調理を開始し、在庫担当者はレシートを見てポテトを準備します。
- **魔法のような仕組み**: レジ担当者は厨房が何をしているか知る必要はありません。もしオーブンが壊れても、システムは注文を受け続け、厨房に別のメニューを指示できます（**疎結合/Decoupling**）。

# ⚙️ UNDER THE HOOD: 技術ディープダイブ

### 1. イベント駆動型アーキテクチャ (EDA)
EDA は「**イベント（出来事）**」を通じて通信します：
- **EventBridge**: 最も強力なイベントの中継基地。イベントのフィルタリングとルーティングをインテリジェントに行います。
- **SQS**: 依存関係を解消（疎結合）するためのキュー。サービス A はメッセージを投げて別の仕事に移ることができ、サービス B の完了を待つ必要はありません。

### 2. AWS Step Functions
複雑なワークフローを指揮する「指揮者」：
- **ステートマシン**: Task、Choice、Parallel などのロジック図。
- **Saga パターン**: 分散トランザクションの解決策。「予約」が失敗した場合、Step Functions が自動的に「払い戻し」をトリガーします（補償トランザクション）。

### 3. 2026 年最新アップデート: 自己修復アーキテクチャ 🚀
- **AI 駆動型オーケストレーション (2026)**: Step Functions に **Amazon Q** が統合されました。ワークロードを自動最適化し、特定の Lambda が頻繁にタイムアウトする場合、AI が自動的にメモリ増設や並列実行への変更を提案・実行します。
- **EventBridge AI フィルタリング (2026)**: 複雑な JSON フィルタリングルールを書く必要はありません。「ユーザーの行動に基づいて不正注文の兆候がある場合のみイベントを送信して」と自然言語で指示するだけで、AI がリアルタイムでスキーマとルールを生成します。
- **Zero-Code Pipes**: 新世代の **EventBridge Pipes** により、DynamoDB ストリームを Step Functions や外部 API に直接接続できます。中継用の Lambda コードを書く必要はもうありません。

# ☁️ AWS IN PRACTICE / INTERVIEW

**実務シチュエーション：** 「外部の配送業者 API が頻繁にエラーや遅延を起こします。ユーザーを待たせないためにはどうしますか？」

**マスターアーキテクトの回答例：**
「**SQS** と **Step Functions** を使用した **非同期（Asynchronous）** アーキテクチャに切り替えます。注文を受けた瞬間に『処理中』と即座に回答し、メッセージを SQS に投入します。ワーカーが後から API を呼び出します。2026 年なら、**Step Functions AI-Retry** を活用し、API の過去の稼働実績に基づいて再試行間隔（バックオフ）を AI が自動調整し、システムを止めずに 100% 処理を完了させます。」

# 🔦 CASE STUDY: Coca-Cola と「サーバーレス」自動販売機システム

**背景:** Coca-Cola は世界中で数百万台の自動販売機を管理しています。コーラを一本買うたびに、決済確認、在庫更新、ポイント付与、時には画面上でのパーソナライズされた広告表示が必要です。

**課題:** 従来のサーバーで数百万台の接続を維持するのはコストと保守の悪夢です。購入時のみ費用が発生する **Pay-as-you-go** モデルで、毎秒数千件の注文をさばく必要があります。

**マイクロサービスと EDA による解決策（2026 年基準）:**
1.  **指揮者 AWS Step Functions**: 購入プロセス全体を調整。決済が成功すれば商品を排出し、同時に在庫更新と顧客アプリへの通知を並列で実行します。エラー時には自動で「キャンセル」ブランチへ移行します。
2.  **イベントハブ EventBridge**: 異なるシステムを繋ぐ屋台骨。一本売れると「イベント」が発行され、マーケティングシステムが「この客は今月 5 本目なので、次回 50% オフクーポンを送ろう」と判断します。
3.  **Express Workflows による最適化**: 大量かつ高速な取引には **Step Functions Express Workflows** を使用。標準型より安価で、毎秒 10 万件以上のイベントを処理可能です。
4.  **AI による監視 (2026)**: **Amazon Q** がイベントフローを分析し、「パートナー API の応答が悪いため、ポイント付与処理を一時的にキューイング（後回し）モードに切り替え、販売を継続させました」と自動で対応します。

**結果:**
- 運用コストを旧システム比で **60% 削減**。
- Step Functions の自己修復能力により、システムエラー率がほぼ **0** に。
- 新機能（クリスマスキャンペーンなど）のリリース期間を数ヶ月から数日に短縮。

**BrSE への教訓:** 品質とロジックを重視する日本の顧客に対して、**Step Functions** の明確な図解を提示することは、システムの信頼性を勝ち取るための最も強力な武器になります。

### 🚀 Master Architect Pro-Tips

> **Tip 1 — Standard vs Express Workflows**: **Standard** は最大 1 年間の長期プロセスや、一歩ずつの厳密な監査が必要な場合に。**Express** は 5 分以内の高速かつ大量の処理、コスト削減を優先する場合に使用します。

> **Tip 2 — エラーハンドリングを最優先に**: Step Functions では常に **Catch** と **Retry** を設定しましょう。外部 API の些細なエラーでワークフロー全体を死なせてはいけません。処理できないメッセージのために **Dead Letter Queue** を設計するのがプロです。

> **Tip 3 — EventBridge Pipes の活用**: SQS から Step Functions へのデータ転送などに **EventBridge Pipes** を使いましょう。仲介用の Lambda を排除でき、低遅延かつ低コストになります。

> **Tip 4 — Saga パターンによる整合性**: マイクロサービスの世界に、従来の DB のような「ロールバック」はありません。Step Functions で失敗時の「補償アクション」を定義し、データの整合性を守りましょう。
