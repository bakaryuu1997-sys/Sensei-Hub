# Jenkins vs GitHub Actions：王と新星の戦い ⚔️

Day 16へようこそ！ここ数日、皆さんは GitHub Actions に触れ、その便利さを実感してきたことでしょう。しかし、もし皆さんが大手銀行や歴史あるテック企業に入社した場合、高い確率で「老練な執事」のアイコンを目にすることになるでしょう。それが **Jenkins** (#(Jenkins)) です。

今日は特定のツールの使い方を学ぶのではなく、**「アーキテクチャ思考」** (#(Architectural Thinking)) を学びます。なぜ世界は2つの陣営に分かれているのでしょうか？ スピード感のある GitHub Actions を選ぶべき時はいつか、そして Jenkins の「馬力」が必要になるのはどのような時でしょうか？

---

## 🪝 THE HOOK：間違った選択と自由の代償

非常に高いセキュリティが求められる金融プロジェクトの CI/CD システムを構築していると想像してください。
- あなたは現代的で使いやすい GitHub Actions を選びました。
- 突然、クライアントから要求が来ます。「すべてのソースコードとビルドプロセスを、社内の内部ネットワークから一歩も外に出してはならない。クラウド（Cloud）の利用は一切禁止する。」

この時点で、クラウド版の GitHub Actions は無力化されます。独自のランナー（Runner）を必死に設置しなければなりませんが、社内インフラ上で数千台のランナーを管理することは、設定の悪夢となります。

逆に、2人だけのスタートアップで Jenkins を選んだ場合、サーバーの設置、プラグインの設定、Java のセキュリティパッチの適用だけで1週間を費やしてしまうかもしれません。GitHub Actions を使っていれば、初日に製品をデプロイできていたはずです。

CI/CD ツールの選択は、どちらが「かっこいいか」ではなく、企業にとってどちらが最も **「安全で経済的」** かで決めるべきものです。

---

## 🎭 ANALOGY：古城の執事と未来のロボット

違いを理解するために、2つのサービススタイルを想像してみましょう：

### 1. Jenkins：忠実な執事（セルフホスト）
Jenkins は、大きな古城に仕える伝統的な **「執事」** のような存在です。
- **メリット**: 彼は城の隅々まで知り尽くしています。どんなに奇妙な要求でも応えてくれます。あなたのあらゆる好みに合わせるための数千の「プラグイン（道具）」を持っています。最も重要なのは、彼があなたの城の中に留まり、外部の人間が干渉できないことです。
- **デメリット**: 彼を養うコスト（サーバー代）がかかり、彼の健康管理（パッチの更新）も自分で行う必要があります。適切なプラグインがないと、新しい技術を学ぶのが少し遅いです。

### 2. GitHub Actions：未来のサービスロボット（クラウドネイティブ）
GitHub Actions は、大企業からレンタルした **「ロボット軍団」** のようなものです。
- **メリット**: 彼らを養う必要はありません。必要なときにボタンを押せば「クラウド」として現れます。非常に高速で、インターフェースも現代的。コードが置いてある場所に最初から統合されています。
- **デメリット**: 彼らはその大企業のルールに従って働きます。特殊すぎることを頼もうとすると「サポート対象外です」と言われることがあります。そして、あなたのコードやデータは、その企業のサーバーを通過することになります。

## ⚙️ UNDER THE HOOD：CI/CD アーキテクチャの比較

### 1. Jenkins - 「Configuration as Code」の魂
Jenkins は **Groovy Script** (#(Groovy Script)) に基づいています。コードを書いてパイプラインを制御します（**Jenkinsfile**）。
- **プラグインのエコシステム**: 1,500以上のプラグインがあります。Docker の管理から、古いポケベルへのメッセージ送信まで、Jenkins にできないことはほぼありません。
- **Master-Agent アーキテクチャ**: Master サーバーが調整し、Agent マシンがビルドを実行します。これにより、物理インフラ上での強力な拡張（Scale）が可能になります。

### 2. GitHub Actions - コミュニティによる創造の時代
GitHub Actions は **YAML** (#(YAML)) と **コンテナ** に基づいています。
- **Marketplace**: プラグインの代わりに「アクション（Actions）」を使います。誰でもアクションを書いて共有でき、あなたは `use` と書くだけで完了です。
- **深い統合**: GitHub 内に存在するため、PR の作成、コメント、タグ付けのタイミングを正確に把握し、パイプラインを精密にトリガーできます。

```mermaid

        Jenkins : "完全に社内（オンプレミス）で完結"
        GitHub Actions : "クラウドプロバイダーの基準に準拠"
```

## 💻 DEVOPS IN PRACTICE：どちらを選ぶべきか？

### シナリオ A：スタートアップ、現代的な SaaS プロジェクト
- **選択**: **GitHub Actions**。
- **理由**: スピードがすべてです。CI/CD サーバーの管理ではなく、コードに集中すべきです。クラウドが高い可用性を保証してくれます。

### シナリオ B：銀行、政府機関、大手物流
- **選択**: **Jenkins**。
- **理由**: 厳格なデータセキュリティ要件。Jenkins にしかプラグインがないような古い技術（レガシーシステム）の運用。数千の複雑なロジック条件を持つパイプラインのカスタマイズ。

### 面接での質問：「なぜ Jenkins は古いのに、今でも人気があるのですか？」
- **回答**: Jenkins には絶対的な柔軟性があるからです。Jenkinsfile（Scripted Pipeline）を使えば、YAML ベースの現代的なツールでは表現できないような複雑なロジックを Groovy 言語で記述できます。また、大企業にとって、数万件のパイプラインを Jenkins から別のツールへ移行させることは、膨大で不要なコストがかかるためです。

## 🛡️ MASTER THINKING：「クラウド・ファーストだが、オンプレミスにも対応可能」

DevOps マスターは、**「ツールに依存しない（Tool Agnostic）」** (#(Tool Agnostic)) ようにパイプラインを設計します。
- `.github/workflow/main.yml` や `Jenkinsfile` にロジックを書きすぎないようにしましょう。
- ロジックは **シェルスクリプト** や **Makefile** に押し出します。
- そうすれば、CI ファイルは単に `./scripts/deploy.sh` を呼び出すだけになります。
- もし明日、会社が Jenkins から GitHub Actions に切り替えることになっても、スクリプトの呼び出し箇所をコピー＆ペーストするだけで5分で済みます。これこそが柔軟性の頂点です。
