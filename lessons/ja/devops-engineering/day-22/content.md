# Advanced Terraform：モジュールとステート管理 🧩

Day 22へようこそ！昨日は Terraform を使ってシンプルなサーバーを作成する方法を学びました。しかし現実には、数千行のコードを一つのファイルに書き続けることはできません。それはインフラの「スパゲッティコード」を生成する最短ルートです。

今日は、**モジュール（Modules）** (#(Modules)) と **リモートステート（Remote State）** (#(Remote State)) を使いこなし、真の **Terraform アーキテクト** として働く方法を学びます。

---

## 🪝 THE HOOK：数千ドルの代償を払った「コピー＆ペースト」のミス

あなたの会社に **Dev**, **Staging**, **Production** の3つの環境があると想像してください。
あなたは Dev 環境の `main.tf` を Production 環境にコピーしました。しかし、`instance_type` を `t2.micro` から `m5.large` に変更し忘れ、さらにデータベースの名前も変更し忘れてしまいました。

結果：
1. 本番環境が非力なサーバーで動作し、アクセスが集中した瞬間にダウンしました。
2. 開発環境のテストデータが、本番環境のデータベースを誤って上書きしてしまいました（接続文字列の変更を忘れたため）。

インフラコードをコピー＆ペーストしているようでは、自分で自分の首を絞めているのと同じです。DevOps マスターは「金型（テンプレート）」を作成し、それを安全に再利用します。

---

## 🎭 ANALOGY：LEGO セットと工業用の金型

**Terraform モジュール** を、あらかじめ組み立てられた LEGO セットのように考えてみましょう：
- 「ゲート」セット
- 「オフィスビル」セット
- 「給水システム」セット

新しい都市（新しい環境）を作るたびに、これらのセットを取り出して組み合わせ、いくつかのパラメータ（例：このビルは青、あちらは赤）を変更するだけです。レンガを一から一つずつ作る必要はありません。

## ⚙️ UNDER THE HOOD：標準的なモジュールの構造

モジュールとは、実のところ `.tf` ファイルが含まれたフォルダに過ぎません。マスター基準のモジュールは、通常以下の3つの主要ファイルで構成されます：

1. **`main.tf`**: リソース（Resources）を定義するコード。
2. **`variables.tf`**: モジュールをカスタマイズするための入力変数（Inputs）。
3. **`outputs.tf`**: 他のモジュールが利用できる戻り値（Outputs）。

### ディレクトリ構造の例：
```text
├── modules/
│   ├── vpc/             # ネットワーク管理モジュール
│   └── ec2/             # サーバー管理モジュール
├── dev/
│   └── main.tf          # Dev 用のパラメータでモジュールを呼び出す
└── prod/
    └── main.tf          # Prod 用のパラメータでモジュールを呼び出す
```

### モジュールの呼び出し方：
```hcl
module "my_web_server" {
  source        = "../modules/ec2"
  instance_type = "t3.medium" # 変数を渡す
  server_name   = "Production-Server"
}
```

## 🌐 ステート管理（STATE MANAGEMENT）

Day 21 で説明した通り、`terraform.tfstate` ファイルはシステムの「魂」です。このファイルを失うと、Terraform は「記憶喪失」になり、現在どのようなインフラが存在しているのか分からなくなります。

### 1. リモートバックエンド（リモート保存）
ステートファイルを Git や個人の PC に保存してはいけません。**S3** (AWS) や **GCS** (Google Cloud) を使用して一元管理します。

### 2. ステートロック（State Locking）
あなたが `apply` を実行している間、Terraform はステートファイルをロックします（通常は DynamoDB を使用）。同僚が同時に `apply` しようとしてもブロックされます。これにより、インフラの混乱した修正を防ぎます。

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-lock" # ロックを管理するテーブル
  }
}
```

## 💻 DEVOPS IN PRACTICE：「ワークスペース（Workspaces）」戦略

Terraform には、同じコードセットから複数の異なるステートを管理できる **Workspaces** (#(Workspaces)) 機能があります。
- `terraform workspace new dev`
- `terraform workspace new prod`

これにより、まず `dev` 環境でコードをテストし、その後 `prod` に切り替えて全く同じコードを実行できます。お互いの環境を干渉（踏みつけ）し合う心配はありません。

## 🛡️ MASTER THINKING：「Terragrunt」と DRY 原則

プロジェクトが巨大になると、モジュールを使っていても `backend` や `provider` の宣言を繰り返していることに気づくでしょう。ここでシニア DevOps が頼るのが **Terragrunt** (#(Terragrunt)) です。
Terragrunt は Terraform のラッパー（Wrapper）であり、コードを徹底的に **DRY (Don't Repeat Yourself / 繰り返しを避ける)** に保つのに役立ちます。リモートステートや環境変数をスマートに自動管理してくれます。

## 💻 INTERVIEW QUESTION：アーキテクトレベル

**質問：クラウド上でインフラが稼働している最中に、誤って `terraform.tfstate` ファイルを削除してしまったらどうしますか？**

**回答（マスターレベル）：**
背筋が凍るような状況ですが、救済策はあります。
1. `terraform import` (#(terraform import)) コマンドを使用する必要があります。
2. 現在クラウドで動いているリソースを定義するコードを `.tf` ファイルに記述します。
3. リソースごとに import コマンドを実行し、Terraform にそれらを「再認識」させ、新しいステートファイルに記録させます。
> **注意**: これは非常に時間がかかり、ミスが起きやすい作業です。そのため、ステートファイルを保存しているバケットには必ず **バックアップ** と **バージョニング（Versioning）** を設定しておきましょう！
