# Splay Tree（スプレー木）：適応する星 🌟

**Day 57**へようこそ。昨日は Treap のランダム性を使って平衡を保つ方法を学びました。今日は、それとは全く異なる哲学、**「適応（Adaptation）」**を学びます。

**Splay Tree（スプレー木）**は、自己調整型の二分探索木（Self-adjusting BST）であり、唯一無二の特徴を持っています。ノードにアクセスするたびに、そのノードが **Splay** と呼ばれる一連の回転操作を通じて、木の根（Root）へと「押し上げ」られるのです。

---

## 🪝 THE HOOK：「なぜ最近使ったアプリが一番上に表示されるのか？」

スマートフォンの「最近開いたアプリ」のリストや、ブラウザでよく使うタブについて考えてみてください。
-   私たちは、膨大なデータの中でも特定の小さなサブセットを繰り返し使う傾向があります（80/20の法則）。
-   もしそのデータが最も見つけやすい場所（木の根）に置かれていれば、アクセス時間は **$O(1)$** になります。
-   Splay Treeはユーザーの行動を自動的に学習します。頻繁に使われるデータほど根の近くに留まり、使われないデータは奥深くへと押しやられます。

これは単なるアルゴリズムではなく、データ構造に組み込まれた自然な **キャッシュ（Cache）** システムなのです。

## 🎭 ANALOGY：書類の山と「取り出したら一番上へ」ルール

顧客の書類が山積みになっていると想像してください。
1.  顧客から電話がかかってくるたびに、書類を使い終わった後、元の場所に戻すのではなく、書類の山の **一番上** に置きます。
2.  次にその顧客から電話が来たとき、すぐに見つけることができます。
3.  長い間連絡がない顧客の書類は、次第に山の底の方へと沈んでいきます。

Splay Treeの動作はこれと全く同じです。**Splay** 操作とは、山の途中から書類を「抜き取って」一番上に持っていく動作であり、同時に検索の順序を維持するために関連する書類を整理し直すことなのです。

## ⚙️ UNDER THE HOOD：Splay回転（Zig, Zag, Zig-Zig, Zig-Zag）

Splay Treeの本質は回転（Rotations）です。ノード `x` を上に持っていく際、主に3つのケースがあります：

### 1. Zig（単一回転）
-   `x` が根の直接の子である場合に使用します。1回の回転で `x` が根になります。

### 2. Zig-Zig（同方向回転）
-   `x` とその親 `p` が両方とも左の子（または両方とも右の子）である場合に使用します。
-   親 `p` を先に回転させ、その後に `x` を回転させます。これにより、木が「平坦」になり、深さが大幅に減少します。

### 3. Zig-Zag（逆方向回転）
-   `x` が `p` の左の子だが、`p` が祖父 `g` の右の子である場合（またはその逆）に使用します。
-   `x` を2回連続で回転させ、`g` の位置まで持っていきます。

**なぜ Splay Tree は平衡を保てるのか？**
1回の操作で木が大きく偏ることもありますが、その後の Splay 操作（特に Zig-Zig）によって、木は自動的に再び平衡な状態へと戻されます。**ならし計算量（Amortized complexity）** は常に **$O(\log N)$** です。

## 📊 BIG-O ANALYSIS：適応するパフォーマンス

| 操作 | 計算量（ならし） | 解説 |
| :--- | :--- | :--- |
| **検索 / アクセス** | **$O(\log N)$** | 1回あたり最悪 $O(N)$ ですが、平均は $\log N$ です。 |
| **挿入 / 削除** | **$O(\log N)$** | 挿入・削除後に Splay を実行します。 |
| **Splay 操作** | **$O(\log N)$** | 回転を通じてノードを根に移動させます。 |
| **頻繁に使うデータ** | **$O(1)$** | 根のすぐ近くに配置されます。 |

## 💻 LOGIC & PSEUDO-CODE：Splay操作の実装

```javascript
class SplayNode {
    constructor(val, parent = null) {
        this.val = val;
        this.ch = [null, null]; // ch[0]: 左の子, ch[1]: 右の子
        this.p = parent;
    }
}

/**
 * 基本的な回転: ノード u を一段上げる
 */
function rotate(u) {
    let p = u.p, g = p.p;
    let k = (p.ch[1] === u); // k=0: 左, k=1: 右
    
    // u を g に接続
    if (g) g.ch[g.ch[1] === p] = u;
    u.p = g;
    
    // u の反対側の子を p に接続
    p.ch[k] = u.ch[k ^ 1];
    if (u.ch[k ^ 1]) u.ch[k ^ 1].p = p;
    
    // p を u の子として接続
    u.ch[k ^ 1] = p;
    p.p = u;
}

/**
 * Splay: u を根まで押し上げる
 */
function splay(u) {
    while (u.p) {
        let p = u.p, g = p.p;
        if (g) {
            // Zig-Zig か Zig-Zag かを判定
            if ((g.ch[0] === p) === (p.ch[0] === u)) rotate(p);
            else rotate(u);
        }
        rotate(u);
    }
    root = u; // 木の新しい根を更新
}
```

## 🧠 LEETCODE STRATEGY：いつ Splay Tree を選ぶべきか？

Splay Tree は以下のケースで最良の選択肢となります：

1.  **参照の局所性（Locality of Reference）**: 「今使ったデータは、すぐにまた使われる可能性が高い」という性質がある場合。
2.  **Link-Cut Trees**: Day 54 で学んだように、LCT は補助構造として Splay Tree を使います。パスの分割や結合に非常に柔軟だからです。
3.  **データ圧縮 (Lempel-Ziv)**: 一部の圧縮アルゴリズムは、頻出する文字パターンを管理するために Splay Tree を使用します。
4.  **LeetCode #???**: クエリの分布が不均一（よく使われるものとそうでないものがある）な動的集合を管理するあらゆる問題。

## 🎯 EXAM & INTERVIEW LOGIC：IPA ＆ 外資テックの戦略

-   **IPA 基本情報技術者 (科目B)**: 平衡木（BST, AVL）の種類について問われることがあります。Splay Tree は高さ（height）や平衡係数を保存する必要がなく、メモリを節約できるという点を強調しましょう。
-   **外資テック システムデザイン面接**: 「頻繁に使用される権限を極めて高速にチェックする必要があるアクセス制御リスト（ACL）システムをどのように設計しますか？」
    -   *回答*: 「ルールを保存するために **Splay Tree** を実装します。よく使われるルールは自動的に根に浮上するため、$O(1)$ または極めて短い時間でチェックでき、全体の計算量は $\log N$ に抑えられます。」
-   **ソクラテス・ゲート**: なぜ Zig-Zig では子よりも先に親を回転させるのですか？
    -   *回答*: 子を2回連続で回転させると（旧式のZig-Zig）、木は長いままです。親を先に回転させることで木が「折りたたまれ」、その枝全体の深さが半分になります。これが Splay Tree が $\log N$ の計算量を達成する秘訣です。

## 🛡️ RELIABILITY & BUGS：マスターへのアドバイス

1.  **「ならし」は「ばらつき」を意味する**: 深い木での1回の Splay 操作は非常に遅くなる（$O(N)$）可能性があります。あらゆる状況で絶対的な高速レスポンスが求められる **ハードリアルタイム** システムには Splay Tree を使わないでください。
2.  **Null チェック**: 回転操作には3つのノード（u, p, g）と4〜5個のポインタが関わります。「null のプロパティにアクセスしました」というエラーに細心の注意を払ってください。
3.  **削除 ＝ Splay ＋ Merge**: 最も良い削除方法：削除するノードを根まで Splay して削除し、残った左の部分木と右の部分木を Merge（結合）します。
