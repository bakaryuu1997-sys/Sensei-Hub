# 単方向連結リスト：ポインタの鎖 🔗

**配列**（Array）が明確な住所を持つ固定された連な住宅であるならば、**連結リスト**（Linked List / 連結リスト）はドラマチックな宝探しのようなものです。現在の場所にあるヒントを開くまでは、次の宝がどこにあるのか分かりません。

---

## 🪝 THE HOOK：「連続メモリ不足」の悪夢

あなたは配列を使って 100 万件のレコードを処理しています。RAM には 500MB の空きがあり、データを追加するのに十分なはずです。しかし、100MB の配列を作成しようとすると、システムは **メモリ不足**（Out of Memory / メモリ不足）エラーを吐き出します。

**なぜでしょうか？** それは、その 500MB が他のプロセスによって数千の小さな破片に断片化されているからです。配列は、単一の統合されたブロックである**連続メモリ**（Contiguous Memory / 連続メモリ）を要求します。500 個のバラバラな席はあっても、100 個が隣り合って並んでいる場所はどこにもないのです。

解決策は？ メモリを隣り合わせるように強制するのをやめることです。メモリを RAM のあらゆる隅々に「分散」させ、それらを透明な「糸」で繋ぎましょう。**単方向連結リスト**（Singly Linked List）へようこそ。これはメモリの自由を解放するデータ構造です。

---

## 🎭 ANALOGY：宝探しゲームと伝令部隊

秘密のメッセージを渡している伝令部隊を想像してください：
- A さんは手紙と、B さんの住所を持っています。
- B さんは次の手紙と、C さんの住所を持っています。
- 最後の人は手紙と、終わりを告げる白紙の紙（NULL）を持っています。

**重要な特徴**:
- 10 番目の手紙を見つけるには、その前の 9 人を**必ず**通過しなければなりません。配列のようにテレポートする「超能力」は持っていません。
- 部隊の真ん中に新しい人を追加したい場合は？ 前の人に新しい人の住所を渡し、新しい人に後ろの人の住所を持たせるだけです。誰も席を「移動」させる必要はありません。これこそが連結リストの絶対的な柔軟性の源です。

## ⚙️ UNDER THE HOOD：ノードの解剖学とポインタの仕組み

### 1. ノード（Node）の構造 - 基本単位
連結リストの各要素は、**ノード**（Node）と呼ばれる独立した実体です。ノードは 2 つの領域（フィールド）で構成されます：
- **データ（Data）**: 実際の値（数値、文字列、オブジェクトなど）。
- **次へのポインタ（Next Pointer）**: 次のノードのメモリ番地（メモリアドレス）を保持する変数。これが最後のノードの場合、`Next` は `NULL` を指します。

### 2. メモリサイズ、アライメント、レイアウト
現代の 64 ビットシステムでは：
- ポインタは **8 バイト** 消費します。
- `int` 型の整数は **4 バイト** 消費します。
- しかし、**メモリアライメント**（Memory Alignment）の仕組みにより、CPU は通常、データが 8 で割り切れるアドレスから始まることを要求します。そのため、ノード（実際には 12 バイト）は RAM 上でしばしば **16 バイト** を占有します。
**帰結**: 連結リストは、同じ量の整数データに対して、配列よりも 4 倍多くのメモリを消費します。シニアアーキテクトは、「この柔軟性は 4 倍の RAM を消費する価値があるか？」を慎重に検討しなければなりません。

### 3. 割り当て戦略（Allocation Strategy）
- **配列**: 一括で一度に割り当てられます（Chunk allocation）。
- **連結リスト**: 離散的に割り当てられます（Scatter allocation）。`malloc` の呼び出しを繰り返すと、**メモリ断片化**（Memory Fragmentation）を引き起こし、カーネルのメモリ管理オーバーヘッドによりシステムが低速化します。

### 4. ガベージコレクション（Garbage Collection）
C/C++ のような言語では、不要になったノードを自分の手で `free(node)` しなければなりません。忘れると、**メモリリーク**（Memory Leak）が発生します。
現代的な言語（JS, Java, Python）では、**ガベージコレクタ**（GC）が RAM をスキャンします。誰からも指されていない（到達不能な）ノードがあれば、GC がそれを削除します。しかし、何百万もの小さく分散した連結リストのノードに対して GC が頻繁に動くと、アプリがカクつく（Jitter）原因となります。

## 📊 BIG-O ANALYSIS：配列 vs 連結リストの古典的な対決

これはシニア DSA 試験における「生死を分ける」比較表です：

| 操作 | 配列 (Array) | 連結リスト (Linked List) | なぜ？ |
| :--- | :--- | :--- | :--- |
| **位置 k へのアクセス** | **O(1)** | **O(n)** | リストは目的地まで k-1 個のノードを「泳ぐ」必要がある。 |
| **先頭（Head）への挿入** | **O(n)** | **O(1)** | リストは新しい「糸」を繋ぐだけ。配列は全員を右へ押し出す必要がある。 |
| **末尾（Tail）への挿入** | **O(1)** | **O(1)** | **Tail** ポインタを保持していることが条件。 |
| **先頭（Head）の削除** | **O(n)** | **O(1)** | 連結リストでは爆速。キュー（Queue）の鍵。 |
| **探索 (線形探索)** | **O(n)** | **O(n)** | どちらも一つ一つの要素に尋ねる必要がある。 |

**実践的な結論**: メッセンジャーアプリ（新しいメッセージが常に一番上にくる）を作るなら連結リストを使い、写真ビューアーアプリ（任意の写真へジャンプする）を作るなら配列を使ってください。

### 本質的な弱点：一方通行の道
単方向連結リストは一方向にしか走れません。ノード 3 にいてノード 2 のデータを見たいと思っても、それは不可能です。**Head** に戻って最初からやり直さなければなりません。そのため、ポインタの接続は極めて「脆弱」です。もし N3 のアドレスを保持する前に誤って `N2.next = NULL` と代入してしまうと、リストの後半部分はメモリから消え去りますが、依然として RAM を占有し続けます（**ゾンビノード**）。

## 💻 LOGIC & PSEUDO-CODE：連結リストの「暗殺者」アルゴリズム

### 1. 連結リストの反転 (Reverse Linked List) - 思考の挑戦
`1 -> 2 -> 3` を `3 -> 2 -> 1` に、O(1) の空間計算量だけで反転させるには？

```javascript
/**
 * 連結リストを 1 つのループで反転させる
 */
function reverse(head) {
    let prev = null;
    let curr = head;
    while (curr) {
        let nextTemp = curr.next; // 1. 次のノードへの「脱出口」を保存
        curr.next = prev;         // 2. ポインタを後ろ向きに繋ぎ変える
        prev = curr;              // 3. prev を進める
        curr = nextTemp;          // 4. curr を進める
    }
    return prev; // 新しい Head はかつての Tail
}
```

### 2. 循環の検出 (Cycle Detection) - フロイドのアルゴリズム
あるノードが前のノードを指し戻すと、リストは無限ループに陥ります。どうやって検出しますか？
- 2 つのポインタを使います：**Slow**（1 歩ずつ進む）と **Fast**（2 歩ずつ進む）。
- リストに循環があれば、Fast ポインタは必ず Slow ポインタを「追い越し」、その足を踏むことになります。これは O(n) 時間、O(1) 空間の最適解です。

## 🧠 LEETCODE STRATEGY：複雑さを打ち砕くテクニック

1. **ダミーヘッドパターン (Dummy Head Pattern)**: 実際の Head を指す `let dummy = new Node(0)` を常に作成します。これにより、何十もの `if (head == null)` を書かずに、境界条件（リストを全削除する場合など）を処理できます。
2. **Fast & Slow ポインタの応用**:
   - リストの中間点を見つける（Fast がゴールに着いたとき、Slow は真ん中にいる）。
   - 後ろから k 番目の要素を見つける（Fast を k 歩先に進ませ、その後両方を一緒に進める）。
3. **リストの結合 (Merging Lists)**: ソート済みの 2 つのリストを結合します。このテクニックは **マージソート**（Merge Sort）アルゴリズムの核となります。

**推奨 LeetCode 問題**: #21 Merge Two Sorted Lists, #141 Linked List Cycle, #206 Reverse Linked List.

## ⚠️ PITFALLS & EDGE CASES：アマチュアの「墓場」

1. **メモリリーク (Memory Leak)**: C++ において、`delete` を使わずに Head ノードを削除すると、そのノードは RAM 内に永遠に残り続けます。
2. **セグメンテーションフォールト (Segmentation Fault)**: `curr` が `NULL` なのに `curr.next` にアクセスすること。リストに常にデータがあると仮定せず、常に `while (curr !== null)` をチェックしてください。
3. **末尾（Tail）の紛失**: 末尾に要素を追加した際、`tail` ポインタの更新を忘れると、次の挿入に O(n) かかってしまいます。

## 🎯 EXAM & INTERVIEW LOGIC：現実と評価（シニアレベル）

Google や ByteDance などの大手企業の面接において：
- **質問**: 「なぜ連結リストは現代のハードウェアにおいてパフォーマンスが悪いのですか？」
- **回答**: 「**ポインタ追い（Pointer Chasing）**が原因です。CPU は次にキャッシュにロードすべきアドレスを予測できません（絶え間ないキャッシュミス）。キャッシュ局所性により、探索速度では配列が圧倒的に勝利します。」
- **日本市場の洞察（科目 B）**: IPA の擬似コード試験では、しばしばポインタ `p` と `q` を管理することが求められます。コードを書く前に、必ず紙に接続の手順を描き出してください。

## 💼 PROFESSIONAL CONTEXT：連結リストが輝く場所

- **ブロックチェーン**: チェーン内の各ブロックは基本的に連結リストのノードであり、`next` は次のブロックの `Hash` に置き換えられます。
- **ファイルシステム**: FAT（File Allocation Table）システムでは、ハードディスク上のファイルの断片は連結リストを使用して繋ぎ合わされています。
- **ハッシュマップの衝突**: 2 つのキーが同じハッシュ値を持つ場合、その「バケツ」内で連結リストを使用して複数の値を保持します（**チェイン法**）。
