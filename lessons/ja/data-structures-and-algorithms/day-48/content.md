# 平方根分割と Mo's Algorithm：バランスの芸術 ⚖️

**Day 48**へようこそ。ハイパフォーマンス・アルゴリズムの世界では、私たちは常に $O(\log N)$ を追い求めがちです。しかし、時には $O(\log N)$ が不可能であったり、実装があまりに複雑でメンテナンス性が損なわれることがあります。

今日、私たちは **「平方根 (Square Root) の哲学」** を学びます。巨大な問題を $\sqrt{N}$ 個のブロックに分割することで、前処理時間とクエリ時間の美しいバランスを実現します。また、範囲クエリをオフラインで処理するための強力な手法、**Mo's Algorithm** も習得します。

## 🪝 THE HOOK：「効率的な司書の秘策」

あなたが 10,000 冊の本を管理する司書だと想像してください。ある顧客が尋ねます：「150番から8,400番までの本の中で、科学に関する本は何冊ありますか？」
-   **ナイーブな方法**: 8,250 冊の本を一つずつ確認する。$O(N)$。顧客が何千人もいたら、対応しきれません。
-   **過剰設計 (Over-engineered)**: 遅延評価 (Lazy Propagation) を備えた複雑なセグメント木を構築する。$O(\log N)$。高速ですが、「科学」カテゴリーが動的に変わる場合の更新処理は実装が非常に困難です。
-   **マスターの方法**: 本を 100 冊（$\sqrt{10,000}$）ずつの箱にグループ化します。
    -   クエリに答えるとき、範囲内にある「丸ごと入っている箱」の合計を素早く計算し、両端の「はみ出している数冊（端数）」だけを直接確認します。
    -   これが **平方根分割 (SQRT Decomposition)** です。計算量は **$O(\sqrt{N})$**。現実的なデータサイズに対して十分高速であり、何よりメンテナンスが非常に簡単です。

## 🎭 ANALOGY：駅の急行列車とスマートなルームサービス

1.  **平方根分割 (急行列車)**: 100 の駅がある路線を想像してください。
    -   **各駅停車**: すべての駅に止まる（ナイーブ）。
    -   **急行列車**: 10 駅ごとに止まる。
    -   12番駅から88番駅まで行くには、まず各駅停車で20番駅へ、そこから急行で80番駅へ、最後にまた各駅停車で88番駅へ行きます。
    -   訪問した駅はわずか数件 ($2 + 6 + 8 = 16$) です。76駅すべてを通る必要はありません。
2.  **Mo's Algorithm (スマートなルームサービス)**: ホテルの宿泊客がバラバラの部屋からリクエストを出しているとします。1階から10階を行ったり来たりするのではなく、リクエストを部屋番号順に並べ替えてから回ります。ワゴンを効率的に動かし、移動しながら必要なものを追加・削除していくのです。

## ⚙️ UNDER THE HOOD：世界を $\sqrt{N}$ で分割する

### 1. 平方根分割の構造
サイズ $N$ の配列を、サイズ $B \approx \sqrt{N}$ のブロックに分割します。
-   ブロックの数は約 $N/B \approx \sqrt{N}$ 個になります。
-   **前処理**: 各ブロックの「答え」（合計、最小値、最大値など）を計算します。$O(N)$。
-   **範囲クエリ $[L, R]$**:
    -   $[L, R]$ に完全に含まれるフルブロックを合計します（最大 $\sqrt{N}$ ブロック）。
    -   最初と最後の中途半端なブロック（端数）を個別に調べます（最大 $2 \times \sqrt{N}$ 要素）。
    -   **合計時間**: **$O(\sqrt{N})$**。

### 2. Mo's Algorithm (クエリ先読み)
すべてのクエリ $[L_i, R_i]$ が事前にわかっている場合（オフライン）、$L$ と $R$ ポインタの移動距離を最小化するようにクエリを並べ替えることができます。
-   **ソートのロジック**: 配列をブロックに分けます。クエリを「$L$ が含まれるブロックのインデックス」でソートし、$L$ が同じブロック内なら「$R$ の値」でソートします。
-   **移動**: $L$ と $R$ ポインタを一つずつ動かし、答えを逐次更新します。
-   **計算量**: **$O((N+Q)\sqrt{N})$**。

## 📊 BIG-O ANALYSIS：中間地点の力

| 操作 | ナイーブ | セグメント木 | 平方根分割 |
| :--- | :--- | :--- | :--- |
| **前処理** | $O(1)$ | $O(N)$ | **$O(N)$** |
| **一点更新** | $O(1)$ | $O(\log N)$ | **$O(1)$** (ブロックの合計値を更新するだけ) |
| **範囲クエリ** | $O(N)$ | $O(\log N)$ | **$O(\sqrt{N})$** |
| **実装の複雑さ** | 極めて低い | 高い | **中〜低** |

## 💻 LOGIC & PSEUDO-CODE：単純な範囲和 (Range Sum)

```javascript
class SqrtDecomposition {
    constructor(arr) {
        this.n = arr.length;
        this.blockSize = Math.floor(Math.sqrt(this.n));
        this.blocks = new Array(Math.ceil(this.n / this.blockSize)).fill(0);
        this.arr = arr;

        for (let i = 0; i < this.n; i++) {
            this.blocks[Math.floor(i / this.blockSize)] += arr[i];
        }
    }

    query(l, r) {
        let sum = 0;
        let startBlock = Math.floor(l / this.blockSize);
        let endBlock = Math.floor(r / this.blockSize);

        if (startBlock === endBlock) {
            for (let i = l; i <= r; i++) sum += this.arr[i];
        } else {
            // 最初の端数ブロック
            for (let i = l; i < (startBlock + 1) * this.blockSize; i++) sum += this.arr[i];
            // フルブロック
            for (let i = startBlock + 1; i < endBlock; i++) sum += this.blocks[i];
            // 最後の端数ブロック
            for (let i = endBlock * this.blockSize; i <= r; i++) sum += this.arr[i];
        }
        return sum;
    }
}
```

## 🧠 LEETCODE STRATEGY：いつ平方根を使うべきか？

1.  **Range Sum Query - Mutable (#307)**: セグメント木でも解けますが、更新処理が非常に多い場合、平方根分割の方がシンプルで高速な場合があります。
2.  **Range Frequency Queries**: 「範囲 $[L, R]$ 内に $X$ は何回現れるか？」という問題は、オフラインであれば Mo's Algorithm が定番です。
3.  **強力な範囲問題**: 「範囲内の種類の数（Distinct Elements）」や「範囲内の最頻値（Mode）」など、セグメント木では非常に困難な問題も、**Mo's Algorithm** なら自然に解けます。

## 🎯 EXAM & INTERVIEW LOGIC：「バランス」の議論

-   **IPA 基本情報技術者試験 (科目B)**: 時間と空間のトレードオフについて問われることがよくあります。平方根分割は、データベースにおける「ブロック処理」の好例です。
-   **面接でのプロのヒント**: 面接官から複雑な範囲クエリの問題を出されたら、すぐにセグメント木に飛びつかないでください。「$O(\log N)$ のためにセグメント木を使うこともできますが、この制約条件下では **平方根分割** の方が実装がシンプルで、$O(\sqrt{N})$ の性能で十分です」と言いましょう。これは **「実用主義 (Pragmatism)」** をアピールできます。
-   **Socratic Gate**: Mo's Algorithm でクエリをブロックごとにソートするのはなぜですか？単に $L$ でソートするだけではダメなのですか？
    *   **回答**: $L$ だけでソートすると、クエリごとに $R$ ポインタが $0$ から $N$ まで激しく動き回る可能性があり、結局 $O(N \cdot Q)$ になってしまうからです。ブロック内で $R$ をソートすることで、$R$ の移動を単調増加に抑えることができます。

## 💼 PROFESSIONAL CONTEXT：データベース・シャーディングとビッグデータ

-   **データベース・シャーディング**: 大規模なデータベースは「シャード」に分割されます。シャードをまたぐ検索は、平方根分割に似ています。シャード全体（ブロック）の結果をまとめ、端の部分を個別に処理します。
-   **画像処理**: ぼかし（Blur）などのフィルタの多くは、ピクセルをブロック単位で処理します。全ピクセルを計算する代わりに、ブロックごとの「積分画像 (Integral Image)」を前計算しておきます。
-   **動画ストリーミング**: CDN は動画ファイルを 2〜10 秒のチャンク（ブロック）に分割します。再生位置をスキップしたとき、プレーヤーは単一のバイトではなく、そのブロック全体を取得します。

## 🛡️ RELIABILITY & BUGS：端数処理の罠

1.  **「最後のブロック」の罠**: 最後のブロックは常にフルサイズとは限りません。ループの際、常に `if (i < n)` のチェックを忘れないでください。
2.  **精度の問題**: 言語によっては `sqrt(N)` が浮動小数点を返すことがあります。インデックスエラーを避けるため、`Math.floor` などを使って整数化してください。
3.  **メモリ局所性**: 平方根分割は、セグメント木よりも実践的には **高速** なことが多いです。連続したメモリブロックにアクセスするため、キャッシュ効率 (Cache-Friendly) が極めて高いためです。
