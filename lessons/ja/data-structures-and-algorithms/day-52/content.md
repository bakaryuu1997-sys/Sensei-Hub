# 重軽分割（HLD）：木を平坦化する 🪵

**Day 52**へようこそ。昨日は、重心分解（Centroid Decomposition）を使って木構造に分割統治を適用する方法を学びました。今日は、別のテクニックを探求します。競技プログラミングにおいて、パス上のクエリ（Path Queries）を扱う際におそらく最も普及しており、かつ強力な手法である **重軽分割（Heavy-Light Decomposition / 重軽分解）** です。

重心分解がグローバルな距離問題を解決するのに適しているのに対し、**HLD** は、ノード `u` から `v` への特定のパス上での更新やクエリ操作における「王者」です。

---

## 🪝 THE HOOK：「木構造の送電網におけるエネルギー管理」

サイクル（閉路）のない木構造を持つ送電網を運用していると想像してください。各ノードは変電所であり、各エッジは送電線です。
システムでは、以下の2種類のコマンドを継続的に実行する必要があります。
1.  **修正コマンド**: 「変電所AからBまでのパス上にあるすべてのステーションの電圧を $x$ ユニット増加させる」
2.  **報告コマンド**: 「変電所CからDまでのパス上にある合計電圧消費量を計算する」
-   **素朴な方法**: DFSやBFSを使ってCからDまでトラバースします。これは各クエリに **$O(N)$** かかります。$N = 100,000$ の場合、システムはすぐに「オーバーロード」してしまいます。
-   **マスターの方法**: HLDを使用します。木の上のパスを **セグメント木（Segment Tree）** 上の直線的なセグメントに変換します。あらゆる更新と報告の操作は、わずか **$O(\log^2 N)$** で完了します。

HLDは、複雑な2D構造である木を、管理しやすい1Dのシーケンスへと「平坦化」する助けとなります。

---

## 🎭 ANALOGY：高速道路と地方道

交通システムを想像してみましょう。
1.  **重いエッジ (Heavy Edge / 高速道路)**: 各交差点（ノード）から、最も人口の多いエリア（最も多くのノードを持つ部分木）へ続く道が「高速道路」としてアップグレードされます。
2.  **軽いエッジ (Light Edge / 地方道)**: より小さく孤立した村々へ続く道は「地方道」です。
3.  **鎖 (Chains / 高速道路ルート)**: 連続する高速道路のセグメントが、一つの主要な幹線道路を形成します。

**魔法の法則**: どの村から首都へ移動する場合でも、一つの「高速道路」から別の「高速道路」へ乗り換える回数は、最大でも **$\log N$** 回の地方道を経由するだけで済みます。
HLDはこの性質を利用し、これらの「高速道路」をメモリ上で隣接して配置することで、セグメント木を使った超高速なクエリを可能にします。

## ⚙️ UNDER THE HOOD：分解のメカニズム

### 1. エッジの分類（Heavy vs. Light）
-   各ノード `u` について、その子ノードの部分木のサイズを計算します。
-   `u` と、最大の `size` を持つ子 `v` を結ぶエッジを **重いエッジ（Heavy Edge）** と呼びます。
-   それ以外のすべてのエッジは **軽いエッジ（Light Edge）** です。

### 2. 鎖（Chains）の構築
-   連続する重いエッジは、一つの **重いパス（Heavy Path / 鎖）** を形成します。
-   各ノードは、正確に一つの重いパスに属します。
-   同じ重いパス内のノードが連続したインデックスを持つように、ノードを再番号付け（DFS Orderを使用）します。

### 3. パス・クエリ
`u` から `v` へ移動する場合：
-   `u` と `v` が同じ鎖に乗るまで、現在の鎖の先頭から次の鎖へと「ジャンプ」を繰り返します。
-   同じ鎖上のノードは連続したインデックスを持つため、**セグメント木** を使ってその区間を **$O(\log N)$** で処理できます。
-   ジャンプする必要がある鎖の最大数は **$O(\log N)$** です。

## 📊 BIG-O ANALYSIS：究極のパフォーマンス

| 操作 | 計算量 | 解説 |
| :--- | :--- | :--- |
| **事前処理 (DFS)** | **$O(N)$** | サイズ計算と鎖のインデックス付けに2回のDFSを実行。 |
| **パスの更新** | **$O(\log^2 N)$** | $\log N$ 個の鎖を跨ぎ、各鎖でセグメント木の操作（$\log N$）を行う。 |
| **パスのクエリ** | **$O(\log^2 N)$** | 更新と同様。 |
| **部分木クエリ** | **$O(\log N)$** | 部分木もDFS順で連続するため、1回のセグメント木操作で済む。 |

## 💻 LOGIC & PSEUDO-CODE：HLDの実装

```javascript
let parent = [], depth = [], heavy = [], head = [], pos = [];
let curPos = 0;

// DFS 1: 最も「重い」子ノードを見つける
function dfsSize(u, p, d) {
    size[u] = 1; parent[u] = p; depth[u] = d;
    let maxSubtreeSize = -1;
    for (let v of adj[u]) {
        if (v !== p) {
            size[u] += dfsSize(v, u, d + 1);
            if (size[v] > maxSubtreeSize) {
                maxSubtreeSize = size[v];
                heavy[u] = v; // 最も重い子
            }
        }
    }
    return size[u];
}

// DFS 2: セグメント木統合のためのインデックス付け
function dfsHLD(u, h) {
    head[u] = h;
    pos[u] = ++curPos; // セグメント木内での位置
    if (heavy[u] !== -1) {
        dfsHLD(heavy[u], h); // 重い鎖を優先して辿る
    }
    for (let v of adj[u]) {
        if (v !== parent[u] && v !== heavy[u]) {
            dfsHLD(v, v); // 新しい重いパスを開始
        }
    }
}

/**
 * uからvへのパスクエリ
 */
function queryPath(u, v) {
    let res = 0;
    while (head[u] !== head[v]) {
        if (depth[head[u]] < depth[head[v]]) [u, v] = [v, u];
        res += segmentTree.query(pos[head[u]], pos[u]);
        u = parent[head[u]];
    }
    if (depth[u] < depth[v]) [u, v] = [v, u];
    res += segmentTree.query(pos[v], pos[u]);
    return res;
}
```

## 🧠 LEETCODE STRATEGY：HLDの応用

HLDは、複雑な木の問題に対する「重兵器」です。

1.  **Path Sum/Max/Min Query**: ノードやエッジの値を更新し、パス上の情報を問う問題。
2.  **共通祖先 (LCA)**: HLDは鎖をジャンプすることで、自然に **$O(\log N)$** でLCAを見つけることができます。
3.  **LeetCode #2003**: 他の方法でも解けますが、HLDやDFS順の考え方は、部分木やパスの問題を効率的に解くための基盤となります。
4.  **あらゆる「木の上でのセグメント木」問題**: 配列のような操作を木構造に対して行う必要がある場合、HLDを検討してください。

## 🎯 EXAM & INTERVIEW LOGIC：IPA ＆ 外資テック ハイレベル

-   **IPA 基本情報技術者 (科目B)**: 最適な木のトラバーサルについて問われることがあります。HLDは、基本的なデータ構造（木 ＋ セグメント木）を組み合わせて強力なソリューションを生み出す典型例です。
-   **外資テック シニア面接**: 「$N = 100,000$ の木に対して、100,000件の範囲更新クエリをどのように処理しますか？」
    -   *回答*: 「**重軽分割（HLD）**を使用します。この手法は木をいくつかの鎖に分解し、木のパスを単一のセグメント木にマッピングすることを可能にします。$O(Q \log^2 N)$ の計算量は十分に実用的です。」
-   **ソクラテス・ゲート**: なぜ2回目のDFSで常に重い子 (`heavy[u]`) を優先して訪問するのですか？
    -   *回答*: 同じ重い鎖に属するノードが連続した `pos[u]` を持つようにするためです。これにより、その範囲に対してセグメント木を適用できるようになります。

## 💼 PROFESSIONAL CONTEXT：ネットワークとファイルシステム

-   **ルーティングテーブル**: 大規模な階層型ネットワーク構造において、HLDは端末デバイス間のルート探索と更新を最適化するのに役立ちます。
-   **ファイルシステムの整合性**: ディレクトリやサブディレクトリに対して再帰的な操作（権限の管理など）を行う際、現代のOSは効率的な管理のために木の分解の変種を使用しています。
-   **3Dグラフィックス (Bone Graph)**: 3Dアニメーションにおいて、骨の階層（ボーン・ハイエラルキー）の動きを計算する際、関節の位置を「ボーン・チェーン」に沿って素早く更新するために、HLDに似た手法が使われることがあります。

## 🛡️ RELIABILITY & BUGS：マスターへのアドバイス

1.  **エッジ vs. ノード**: HLDは通常、**ノード**上の値に対して教えられます。問題が**エッジ**上の値を要求している場合は、エッジ `(u, v)` の値をより深い方のノード（子ノード）に割り当ててください。クエリの際、LCAは検討中のパス上のどのエッジも代表していないため、含めないように注意してください。
2.  **Head vs. Parent**: `head[u]`（現在の鎖の先頭ノード）と `parent[u]`（直近の親）を混同しないでください。鎖をジャンプするときは `parent[head[u]]` を使用します。
3.  **セグメント木のサイズ**: セグメント木の配列が十分に大きく（$4N$）、`pos[u]` の順序に従って初期化されていることを確認してください。
