# Day 6: トラブルシューティングと高度なGit救済テクニック

Day 6にようこそ！今日のレッスンは、一般的なGitユーザーと **Gitエキスパート** を分ける極めて重要な内容です。

開発を進める中で、次のようなパニックに陥る瞬間が必ず訪れます。
*「しまった、間違ったファイルをコミットしてしまった！」*
*「どうしよう、大事なファイルをうっかり削除してしまった！」*
*「さっきのマージ処理を取り消すにはどうすればいいんだ！？」*

心配はいりません。Gitはデータを極めて堅牢に守るように設計されており、ほとんどすべての操作ミスは安全に修復可能です。

今日は、Gitのタイムトラベル機能をマスターし、高度な救済ツールを使いこなす方法を学びましょう。

---

## 1. コミットの即時修正：`git commit --amend`

コミットメッセージを入力してEnterキーを押した直後に、メッセージのタイポに気づいたり、小さなファイルをステージング（`git add`）し忘れていたことに気づくことがあります。そうした時に、履歴を汚す修正コミットを新しく作成するのではなく、直前のコミットを直接修正・上書きすることができます。

### 実務でのシナリオ：
直前のコミットメッセージを "feat: add logni logic"（loginのスペルミス）で記録してしまった場合。

**修正手順：**
```bash
git commit --amend -m "feat: add login logic"
```

**内部で何が起きているか？**
Gitは現在のステージングエリアにある変更点を取り込み、直前のコミット内容とマージした上で、元のコミットを新しいコミット（コミットハッシュIDは変更されます）に **置き換え** ます。

> ⚠️ **極めて重要な警告：** `--amend` を使用するのは、まだリモートリポジトリにプッシュしていない **ローカル環境のコミットだけ** にしてください。すでにプッシュ済みのコミットをamendすると、ローカルとリモートの履歴が分岐し、次回のプッシュ時に競合エラーが発生します。

---

## 2. 変更の安全な取り消し（Undoing Changes）

Gitは、作業状態（ライフサイクル）のどこに変更があるかに応じて、安全に取り消すためのコマンドを個別に提供しています。

### 2.1. 変更したファイルを元の状態に戻す（Working Directory）
`index.html` に試験的なコードを書いたものの、すべて破棄して直前のコミット状態に完全に戻したい場合：
```bash
git restore index.html
```

### 2.2. ステージングしたファイルを元に戻す（Staging Area）
`git add index.html` を実行した後に、コミットする前にもう少し修正を加えたくなった場合：
```bash
git restore --staged index.html
```
*ファイル内の編集内容はディスク上に残ったまま、ステージング（コミット準備エリア）から安全に除外されます。*

---

## 3. `git reset` を使用したタイムトラベル（徹底解説）

`git reset` はGitの最も強力かつ危険なコマンドの1つです。`HEAD` ポインタを指定した過去のコミット地点まで巻き戻すことができます。以下の3つのモードは **必ず** 正確に区別できるようにしてください。

### 歴史のタイムライン状態：
```text
コミットA (Hash: 111) -> コミットB (Hash: 222) -> コミットC (Hash: 333)
                                                   ^ (あなたの現在の位置)
```

#### モード 1: `--soft`（最も優しい取り消し）
ブランチポインタを指定コミットまで巻き戻しますが、編集したコードはすべてステージングエリア（Staging Area）に保持されます。
```bash
git reset --soft HEAD~1
```
*結果：* コミットBに巻き戻ります。コミットCで行った変更点はステージング状態（緑色）でそのまま残るため、すぐに再編集や再コミットが可能です。複数の細かなコミットを1つに統合（Squash）したい場合に非常に便利です。

#### モード 2: `--mixed`（デフォルトの挙動）
ブランチポインタを指定コミットまで巻き戻し、編集したコードはディスク上（Working Directory）に保持しますが、ステージングは解除します。
```bash
git reset --mixed HEAD~1
```
*結果：* コミットBに巻き戻ります。コミットCで行った変更点は、ステージングされていない状態（赤色）の変更として保持されます。

#### モode 3: `--hard`（危険・すべて破棄）
ブランチポインタを指定コミットまで巻き戻し、さらにディスク上の変更点（ステージング内外問わず）をすべて跡形もなく消去して、過去のコミット状態と完全に一致させます。
```bash
git reset --hard HEAD~1
```
*結果：* コミットBより後の変更内容は **永久に失われます**。本当に直前の作業をすべて破棄してやり直したい時以外は、絶対に使用しないでください。

---

## 4. 公開履歴の安全な打ち消し：`git revert`

`reset` が過去の歴史を書き換えて消去するのに対し、`revert` は **過去の歴史を打ち消す新しい歴史（コミット）を追加** する協調的なコマンドです。

### なぜResetではなくRevertを使うのか？
すでにGitHubの共同ブランチにプッシュしてしまったコミットに対して、絶対に `reset --hard` を行って歴史を消去してはいけません。同僚の開発環境で歴史の不整合が発生し、多大な迷惑をかけることになります。代わりに `revert` を使用します。

**使用手順：**
```bash
git revert <打ち消したいコミットのハッシュ>
```

Gitは指定されたコミットと全く逆の変更を行う新しいコミットを自動的に作成します。指定コミットで10行コードが追加されていた場合、リバートコミットはその10行を削除します。歴史の流れを一切乱すことなく、安全に修正を行えます。

---

## 5. 作業の一時退避：`git stash`

新機能Aの実装中（まだコードは書きかけで動かない状態）に、突然チームリーダーから「mainブランチの重大なバグを今すぐ修正してリリースしてくれ！」と指示されたとします。コミットしていない変更が残っている状態では、他のブランチに切り替える（switch）ことができません。

**解決策：一時退避用の魔法のポケット `stash`**

*   **作業中のコードを安全に一時退避する：**
    ```bash
    git stash
    ```
    *作業ディレクトリが瞬時にクリーンな状態に戻り、安全に別ブランチに切り替えられるようになります。*
*   **退避した作業の一覧を確認する：**
    ```bash
    git stash list
    ```
*   **退避した作業を復元して再開する：**
    ```bash
    git stash pop
    ```

## 6. バグの調査と特定（Git Forensics）

数千行に及ぶコードベースで突然バグが発生した際、Gitのフォレンジック機能（調査機能）を使って原因を特定できます。

### 6.1. Git Blame：この行を書いたのは誰だ？
ファイル内の各行について、「誰が」「いつ」「どのコミットハッシュで」最後に編集したかを一行ずつマッピングして表示します。
```bash
git blame index.html
```

### 6.2. Git Bisect：二分探索によるバグ原因コミットの特定
「昨日は完璧に動いていたのに、今日50件のコミットをマージしたらアプリがクラッシュするようになった」という場合、バグを仕込んでしまった特定のコミットをどのように探せばよいでしょうか？ `git bisect` が解決します。

1.  探索を開始する：`git bisect start`
2.  現在のバグが発生している状態を「不良」とマーク：`git bisect bad`
3.  過去の正常に動いていたコミット（例: ハッシュ `abc123`）を「良好」とマーク：`git bisect good abc123`
4.  Gitは自動的に中間地点のコミットにチェックアウトし、あなたにテストを求めます。
5.  アプリを起動して動作確認し、`git bisect good` または `git bisect bad` と報告します。
6.  Gitはこの二分探索を繰り返し、最終的にバグの原因となった「最初のコミット」をピンポイントで特定します。手動で一つずつ確認する手間を大幅に削減できます！

---

## 7. 究極のセーフティネット：`git reflog`（飛行機のブラックボックス）

うっかり `git reset --hard` を実行してしまい、数週間分のコードが消えてしまったと絶望していませんか？ **まだ諦める必要はありません！**

Gitは、ローカル環境で `HEAD` ポインタが移動したすべての歴史を「**Reflog**」と呼ばれる内部ログに記録しています。ブランチから参照されなくなった（削除されたように見える）コミットであっても、Gitのデータベース内に約30日間は残されています。

**「削除された」コミットの救出方法：**
1.  移動ログを表示する：
    ```bash
    git reflog
    ```
2.  ミスをする直前の状態（例: `HEAD@{5}`）を見つけます。
3.  その状態にブランチを完全復旧させます：
    ```bash
    git reset --hard HEAD@{5}
```
*奇跡のように、消えてしまったはずのコードが完全に復元します。*

## Day 6 のまとめ：Gitエキスパートの黄金律

1.  **こまめにコミット（または `git add`）する：** Gitが救済できるのは、一度でもコミット（またはステージング）されたデータだけです。
2.  **パニックにならない：** `git reflog` を使えば、ローカルで行ったほぼすべてのミスは復旧可能です。
3.  **公開された歴史をリスペクトする：** 共有サーバーにプッシュしたコミット履歴は、絶対に書き換え（resetやamend）を行ってはいけません。
4.  **コードを書く前にまず調査：** `blame` や `bisect` を使いこなし、バグの根本原因を理解してから修正に着手しましょう。

**本日の応用課題：**
1.  何度も変更を加えたファイルに対して `git blame` を実行してみてください。
2.  `git stash` を使って、書きかけの機能から別の作業へスムーズに切り替える練習をしましょう。
3.  *（上級チャレンジ）* 意図的に `git reset --hard HEAD~1` で直前のコミットを消去し、`git reflog` を使って元の状態に無傷で復元させてみてください。
