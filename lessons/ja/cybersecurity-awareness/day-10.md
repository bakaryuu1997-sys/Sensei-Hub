# Day 10: Webセキュリティ（その3）- 認証の不備 ＆ IDOR

SQLインジェクションからデータベースを保護し（Day 8）、ブラウザ側をXSS/CSRFから防衛（Day 9）したのに続き、本日はWebアプリケーションの最も重要なビジネスロジックの根幹である **認証（Authentication - あなたは誰ですか？）** と **認可（Authorization - あなたは何ができますか？）** について深く掘り下げます。

現代のWeb APIやモバイルAPIにおいて極めて高頻度で発生する深刻な2大脆弱性、**認証の不備（Broken Authentication）** と **IDOR（Insecure Direct Object Reference / 不適切な直接オブジェクト参照）** を徹底的に解剖します。

---

## 1. 認証の不備（Broken Authentication）

**認証の不備（Broken Authentication）** は、ハッカーがユーザーアカウントを簡単に乗っ取ったり、セッションを窃取したり、正規のユーザーになりすましたりすることを可能にしてしまう、認証設計や設定上の脆弱性の総称です。

### 認証の不備が生じる代表的な原因：
*   **ブルートフォース保護の欠如：** ログインAPIに対して、ハッカーが辞書攻撃や総当たり攻撃（ブルートフォース攻撃）で何百万通りものパスワードを連続して試行できる状態（アカウントロックやレート制限 - Rate Limiting がない）。
*   **推測可能なセッションID：** セッションIDが短すぎる、あるいは連番（例：`session_1`、`session_2`）などの推測しやすい規則性を持っているため、ハッカーに他のアクティブなセッションIDを推測（Session Guessing）され、不正ログインされる。
*   **URLパラメータへのセッション情報の漏洩：** セッションIDやトークンをURLクエリパラメータ（例：`https://my-app.com/dashboard?session_id=xyz`）経由で送信するため、ブラウザ履歴、プロキシログ、サーバーのアクセスログなどに機密情報が残ってしまう。
*   **ログアウト時の不完全なセッション破棄：** ユーザーがログアウトボタンを押した際、クライアント側（ブラウザ）のトークンを削除するだけで、バックエンドのデータベースやサーバー側でトークンの有効性を無効化していない。

### 安全なコーディング手法：
1.  **レート制限（Rate Limiting）の導入：** `express-rate-limit` ライブラリを使用するか、エッジゲートウェイ（CloudflareやNginx）を設定し、同一IPアドレスからのログイン試行の失敗回数を厳格に制限します（例：15分間に最大5回まで）。
2.  **暗号学的に安全なセッションIDの生成：** 暗号学的に安全な擬似乱数ジェネレータを使用し、エントロピーが高く十分な長さのランダムな文字列（UUID v4など）をセッションキーとして使用します。
3.  **セッションCookieの厳重な保護：** 前日に学んだように、セッションCookieには必ず `HttpOnly` および `Secure` フラグを付与し、ログアウト時にはサーバー側とクライアント側の双方でセッション状態を完全に抹消します。

## 2. IDOR（Insecure Direct Object Reference）とは何か？

**IDOR（不適切な直接オブジェクト参照）** は、今日のWeb APIおよびモバイルAPIにおいて極めて一般的であり、かつ極めて容易に悪用されてしまう認可制御（Access Control）の欠陥です。これは、データベース内のレコードIDやファイル名など、オブジェクトに対する直接的な識別子（参照値）をAPIで直接公開しているにもかかわらず、**「リクエストを送信したユーザーが、そのオブジェクトに対して正当な所有権やアクセス権を持っているか」をサーバー側で一切検証していない**ことによって発生します。

```text
APIにおけるIDOR脆弱性のモデル：

1. ユーザーAが正常にログインする。
2. アプリケーションがユーザーAの請求書を取得するAPIを呼び出す：
   GET /api/invoices/1001 ──> サーバーは1001がユーザーAの所有物か確認 ──> OK（表示成功）。
3. ユーザーA（またはハッカー）がリクエスト内のIDを「1002」（ユーザーBの所有物）に変更する：
   GET /api/invoices/1002
4. サーバーがリクエストを受信 ──> データベースで請求書1002を検索
   ──> 所有権チェックを行わず、そのままユーザーBのデータを返却！ ──> 個人情報漏洩発生！
```

### なぜIDORは極めて危険なのか？
*   ハッカーは、IDパラメータを自動的なループ（`1001`、`1002`、`1003`など）で連番で増加させるスクリプトを実行するだけで、システム上の全ユーザーの機密データ（個人情報、請求書、機密ドキュメントなど）を一括して収集（スクレイピング）することができます。
*   さらに、ハッカーはHTTPメソッドを `PUT` や `DELETE` に変更することで、他のユーザーのリソースを不正に改ざんしたり、完全に削除したりすることが可能になります（例：`POST /api/user/1002/update` を介して他人のアカウント情報を勝手に書き換える）。

## 3. IDOR脆弱性のあるコードの解剖

請求書情報を読み込む処理を実装した、典型的なIDOR脆弱性を持つNode.js ExpressのAPIコードを見てみましょう：

```javascript
// 警告：このコードには深刻な認可制御の欠陥（IDOR）が存在します！
app.get('/api/invoices/:id', async (req, res) => {
    // URLパラメータから請求書IDを取得
    const invoiceId = req.params.id;

    try {
        // 致命的な欠陥：データベースからIDだけで請求書を検索しており、
        // その請求書のuser_idと現在ログインしているユーザーのIDを照合していない！
        const result = await db.query('SELECT * FROM invoices WHERE id = $1', [invoiceId]);
        
        if (result.rows.length === 0) {
            return res.status(404).json({ error: "請求書が見つかりません" });
        }

        // 請求書データをそのままクライアントに返却
        res.json(result.rows[0]);
    } catch (err) {
        res.status(500).json({ error: "サーバーエラーが発生しました" });
    }
});
```

## 4. IDOR脆弱性を根本から解決する防衛策

IDORを完全に排除するためには、バックエンド側で以下の鉄則を遵守する必要があります：**「クライアントから送られてくるオブジェクトIDを信用せず、必ず所有権の有無をデータベースレベルで検証すること」**。

### 解決策 1：データベースクエリ内で所有者のIDを照合する
最も確実で推奨される対策は、サーバー側で検証・復号されたセッション情報（JWTトークンなど）から取得した「ログイン中のユーザーのID」を、データベースのクエリ文の条件式（WHERE句）に必ず含めることです。

```javascript
// 安全なセキュアコードの実装例
app.get('/api/invoices/:id', async (req, res) => {
    const invoiceId = req.params.id;
    
    // 認証ミドルウェアが設定したログイン中のユーザーIDを取得（req.user.id）
    const loggedInUserId = req.user.id;

    try {
        // 安全：請求書ID（invoiceId）と所有者（user_id）の双方が一致することを強制する
        const result = await db.query(
            'SELECT * FROM invoices WHERE id = $1 AND user_id = $2', 
            [invoiceId, loggedInUserId]
        );
        
        if (result.rows.length === 0) {
            // ハッカーにIDの存在有無を推測させないため、403ではなく「404 Not Found」を返却する
            return res.status(404).json({ error: "請求書が見つかりません" });
        }

        res.json(result.rows[0]);
    } catch (err) {
        res.status(500).json({ error: "サーバーエラーが発生しました" });
    }
});
```

### 解決策 2：非連番の識別子（UUID v4）の採用
データベースのプライマリキーとして自動インクリメント（連番の数字 `1`, `2`, `3`）を使用する代わりに、ランダムで強固な文字列である **UUID v4**（例：`f81d4fae-7dec-11d0-a765-00a0c91e6bf6`）を採用します。
*   これにより、ハッカーが隣り合うIDを予測して自動スキャンを実行することが物理的に不可能になります。
*   *注意：* UUIDの採用は「Security through obscurity（隠蔽によるセキュリティ）」に過ぎず、**解決策1の所有権チェックを代替することはできません**。UUIDを採用した場合でも、所有権チェックの実装は必須です。

## 📝 本日のミニ課題：安全なミドルウェアの構築

あなたがバックエンド開発者となり、リソースのアクセス制御を行うためのNode.js/Expressの共通ミドルウェア `checkResourceOwner` を作成してください。

データベースには、ユーザーが作成したプロジェクト情報を管理する `projects` テーブルがあり、カラムとして `id`, `name`, `user_id`（プロジェクト所有者のユーザーID）が存在するものとします。

プロジェクト編集用のすべてのルート（例：`PUT /api/projects/:id`）で共通利用できるミドルウェアを書いてください。このミドルウェアに必要な処理は以下の通りです：
1.  URLパラメータからプロジェクトID（`req.params.id`）を取得する。
2.  先行する認証ミドルウェアによって復号され、`req.user.id` に格納されているログインユーザーのIDを取得する。
3.  データベースを検索し、対象のプロジェクトが現在ログイン中のユーザーの所有物であるか確認する。所有権が確認できれば `next()` を呼び出して次の処理へ進み、所有権がない場合は処理を遮断して `403 Forbidden`（または `404 Not Found`）を返却する。

このミドルウェアの具体的なコードを記述し、その設計判断について簡潔に説明してください！
