## 1. ケーススタディ解剖：エクイファックス個人情報漏洩事件（2017年）

**エクイファックス（Equifax）** は、米国の三大信用情報機関の1つであり、8億人以上の消費者の極めて繊細な金融・信用データを管理している企業です。2017年、同社は歴史上最悪規模の壊滅的なサイバー攻撃を受け、**1億4700万人分**の氏名、社会保障番号（SSN）、生年月日、クレジットカード番号などの極めて秘匿性の高い個人情報（PII）が外部に漏洩しました。

```text
エクイファックス侵入・情報搾取の攻撃チェーン分析：

[ 攻撃者 ] ──(1) Apache Strutsの脆弱性を攻撃 ──> [ 公開 Web サーバー ]
                                                         │
                                               (2) 任意コード実行とシェル奪取
                                                         │
                                                         ▼
[ 基幹 DB サーバー ] <──(4) データを平文のまま搾取 ── [ 社内ネットワーク ]
 (データベース暗号化の欠如！)                          (ハードコードされたDBアクセスキー)
```

### 惨劇をもたらした決定的な「4つのセキュリティ不備」：

*   **不備 1：脆弱性管理の怠慢（パッチ適用の不備）**
    *   攻撃者は、Webアプリケーションフレームワーク **Apache Struts** の既知の脆弱性（CVE-2017-5638）を突いて最初のアクセスを獲得しました。この脆弱性に対しては、ベンダーから2ヶ月前に修正パッチが提供されていましたが、同社のセキュリティチームは**パッチの適用を見落としていました**。
*   **不備 2：社内ネットワークのセグメンテーション（分断）の欠如**
    *   外部向けの問い合わせ用Webサーバーがハッキングされた後、そのサーバーから社内の基幹ネットワークへファイヤーウォールなどの境界なしに直接接続できる状態であったため、攻撃者は社内ネットワーク全体への横展開（Lateral Movement）を容易に行うことができました。
*   **不備 3：認証情報のずさんな管理（ハードコード）**
    *   侵入したWebサーバー内に、中央データベースにアクセスするための管理者IDとパスワードが平文テキスト（プレーンテキスト）のままハードコードされて保存されていました。
*   **不備 4：保存データの暗号化の欠如**
    *   1億4700万人分の個人情報を保管する中央データベース内のデータが暗号化されておらず、**すべて平文のまま保存されていました**。このため、攻撃者は情報を復号する手間もなく、76日間にわたり誰にも気づかれることなく全データを外部にダウンロードし続けました。

### アーキテクチャ上の教訓：
エクイファックスの惨劇は、いくら高価なファイヤーウォールを境界線に設置しても、単一の不備から破綻することを示しています。本質的なセキュリティは、継続的なパッチの適用、厳格なネットワークセグメンテーション、適切なシークレット管理、そして何よりも「すべての機密データの暗号化」が連動して初めて実現されます。

## 2. ゼロトラストアーキテクチャ（ZTA）とは？

従来の企業セキュリティモデルは、**「キャッスル ＆ モート（城と堀）」** モデルと呼ばれていました。システムの周囲に頑丈な境界ファイヤーウォール（堀）を築き、境界の「外側」にいるものはすべて敵、「内側（社内ネットワーク）」にいるものはすべて味方であり信頼できるという前提で設計されていました。
*   **致命的な弱点：** エクイファックスの事件が証明したように、攻撃者が一度でも境界の内側に侵入（Webサーバーを1台乗っ取るなど）すると、社内ネットワーク内のすべてのリソースに制限なくアクセスし、システム全体を破壊・窃取できるようになります。

この境界型モデルの根本的な欠陥を解決するため、現代のグローバルテック企業は **ゼロトラストアーキテクチャ（ZTA）** へのシフトを完了しています。その基本思想は以下の通りです：

> **「誰も信用しない、常に検証する（Never Trust, Always Verify）」**

```text
セキュリティパラダイムの移行モデル：

従来の「境界型」セキュリティモデル：
   [ 外部インターネット (不審) ] ──(ファイヤーウォール)──> [ 社内ネットワーク (無条件で信頼) ]

「ゼロトラスト」セキュリティモデル：
   [ 社内ネットワーク ] ───┐
   [ デバイスの状態 ]   ───┼───( 常に明示的な認証 ＆ 検証を実行 )───> [ データベース / API ]
   [ ユーザーのアイデンティティ ] ┘
```

自宅のWi-Fiから接続しているか、本社のオフィスから接続しているかにかかわらず、また一般の業務委託メンバーか、あるいは最高技術責任者（CTO）であるかにかかわらず、ゼロトラストモデルは**すべての通信を「潜在的な脅威」として扱い**、リソースへのアクセスの都度、厳格かつ動的な検証を実施します。

## 3. ゼロトラストの「3大原則」

ゼロトラスト基準に準拠したソフトウェアシステムを設計する際は、以下の3つの基本原則を徹底的に適用する必要があります：

1.  **明示的に検証する（Verify Explicitly）：** 利用可能なすべてのデータ（ユーザーの身元、地理的位置、デバイスの健全性状態、リソースの機密レベル、異常検知情報）に基づいて、アクセスの都度常に認証と認可を実行します。
2.  **最小権限アクセス（Least Privilege Access）：** ユーザーやサービスアカウントに付与する権限を、業務の遂行に必要な最小限の範囲に限定します（必要な時に必要なだけ権限を与える JIT - Just-In-Time、および必要最小限の権限のみを与える JEA - Just-Enough-Access の徹底）。これにより、万が一アカウントが窃取されても被害範囲（ブラスト半径）を最小限に抑えられます。
3.  **侵害を前提とする（Assume Breach）：** システムの一部は**すでに攻撃者に侵入されている**という前提（侵害前提）で運用を行います。システム内部を非常に細かく分断（マイクロセグメンテーション）して横展開による侵入拡大を防ぎ、ネットワークトラフィックを全監視し、保存時（At Rest）および転送時（In Transit）のすべてのデータを常に暗号化します。

## 🎓 卒業制作プロジェクト（Graduation Project）

あなたが **リードセキュリティアーキテクト（Lead Security Architect）** に就任したと仮定し、クラウドネイティブな **エンタープライズ向けSaaS型ECシステム** のための包括的なセキュリティシステム設計書を作成してください。

システムの構成要素は以下の通りです：
*   顧客向けのフロントエンドWeb（React/Next.js）
*   バックエンドREST API（Node.js/Express）
*   クレジットカード情報や注文履歴を保存する中央PostgreSQLデータベース
*   デプロイプラットフォームは AWS（Amazon Web Services）

### 設計成果物の要求事項：
以下の4つのセクションで構成されるセキュリティアーキテクチャ設計仕様書を記述してください：
1.  **XSS ＆ CSRF防御戦略：** フロントエンドにおいてアクセストークンをどこに保存しますか？ クライアントを保護するためにどのようなCookie属性（SameSite, HttpOnlyなど）を構成し、どのようなコンテンツセキュリティポリシー（CSP）ヘッダーを実装しますか？
2.  **認可の設計とIDOR対策：** 顧客Aが、自身の注文以外の注文ID（`order_999`）を不正に閲覧・改ざんするのを防ぐために、Expressの認可ミドルウェアのロジックをどのように設計するか説明してください。
3.  **自動化されたDevSecOpsパイプラインの統合：** 開発者がmainブランチに新しいコミットをプッシュした際、Gitパイプライン内で自動実行すべきセキュリティスキャン（SAST, SCA, シークレット検出）の具体的なフローとツールを説明してください。
4.  **データベースのゼロトラストと最小権限：** PostgreSQLデータベースを最も深いレイヤーで保護するために何を行いますか？ 「最小権限」および「明示的検証」の原則を適用し、APIサーバーに対してどのようなDB接続権限を与え、機密データを保存時にどのように暗号化するか設計を述べてください。
