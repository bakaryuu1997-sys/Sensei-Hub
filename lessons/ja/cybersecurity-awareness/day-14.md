# Day 14: DevSecOps（パート2）- シークレット管理（Secrets Management）

昨日私たちは、ソースコードやオープンソースライブラリの脆弱性を自動排除するためのセキュリティスキャンパイプラインの構築方法を学びました。本日は、企業のセキュリティインフラにおいて最も致命的かつ頻発し、瞬時に重大な財務的損害をもたらすセキュリティ惨劇の1つである **「機密情報の漏洩（Secrets Leakage）」** を防止する仕組みに焦点を当てます。

ここで言う「シークレット（Secrets / 機密情報）」とは、データベースの接続パスワード、外部有償サービス（OpenAIやStripeなど）のAPIキー、JWT署名用の暗号秘密鍵、SSH秘密鍵などを指します。攻撃者がどのようにしてこれらの鍵を探し出しているかを研究し、企業がプロフェッショナルなシークレット管理ツールである **HashiCorp Vault** や **AWS Secrets Manager** を使ってこれらをどのように保護しているかを分析します。

---

## 1. Gitへの機密情報コミットによる惨劇（The Git Leak Disaster）

一部の開発者に見られる極めて危険な習慣として、ローカル環境での迅速な動作確認のためにAPIキーやデータベースのパスワードをソースコード内に直接書き込み（ハードコード）、その後誤って `git commit` を実行してGitHubなどの公開リポジトリ（Public Repository）へプッシュしてしまうケースが挙げられます。

```text
漏洩したAPIキーを攻撃者が検出して悪用するまでの流れ：

[ 開発者 ] ──(1) APIキー入りのコードをプッシュ ──> [ 公開 GitHub リポジトリ ]
                                                              │
                                                     (2) ボットが24時間監視
                                                              │
                                                              ▼
[ 悪意あるスキャンボット ] <──(3) キー情報を瞬時に抽出 ───────┘
      │
   (4) キーを即座に自動悪用開始
      │
      ▼
【 恐るべき結末 】：
  - 高価な仮想マシンが数千台立ち上げられ、仮想通貨のマイニングに悪用される（AWSで数万ドルの請求）。
  - 本番データベースのデータがすべて外部にダウンロードされる。
  - 企業は巨額の請求書を受け取り、サービス停止や廃業の危機に直面する。
```

### 攻撃者はどのように探しているか？
攻撃者は手動でコードを探しているのではありません。GitHubにプッシュされるすべてのリポジトリのコミット履歴を、自動スキャンボット（Git Bots）を用いて24時間365日リアルタイムで監視しています。
*   ボットがAWSのアクキーやOpenAIのAPIキーなどの特徴的な文字列パターンを検知すると、即座にそのキーを利用してマイニング用のインスタンスを作成したり、データベースからデータを抜き取ったりする自動攻撃プログラムを実行します。
*   あなたが誤ってキーをGitHubにプッシュしてから、ボットがそれを検知して悪用を開始するまでの時間は、**通常1分未満**です！

## 2. エンタープライズレベルのシークレット管理とは？

機密情報を守るため、エンタープライズシステムでは以下の厳格なルールを徹底します：**「ソースコードやローカルの構成ファイル（`.env`）などに静的なシークレット（Static Secrets）を生のテキスト形式で永続保存してはならない。」** 代わりに、セキュリティ管理専用の **シークレットマネージャー（Secrets Manager）** を導入します。

```text
シークレットマネージャーの動作モデル（3層防御）：

┌──────────────────┐               (1) IAMによる認証要求
│ アプリケーション │ ────────────────────────────────────────┐
└──────────────────┘                                         │
         ▲                                                   ▼
         │ (3) 復号されたシークレットの返却       ┌───────────────────────┐
         │                                       │ シークレットマネージャー│
         └────────────────────────────────────── │ (暗号化されたDB情報/API)│
                                                 └───────────────────────┘
                                                             ▲
                                                 (2) キーの自動変更
                                                             │
                                                 ┌───────────────────────┐
                                                 │ 自動ローテーションボット │
                                                 └───────────────────────┘
```

### シークレットマネージャーの3つのコア機能：
1.  **保存時の暗号化（Encryption at Rest）：** すべての機密情報は、データベースやディスクに書き込まれる前に強力な暗号化アルゴリズム（AES-256など）で自動的に暗号化されます。万が一、物理サーバーのディスクデータが盗まれても、生のデータが漏洩することはありません。
2.  **最小権限の適用とIAM統合：** IAM（Identity and Access Management）ロールなどで明確に認証・許可されたアプリケーションプロセスのみが、該当シークレットにアクセスして復号することを許可されます。
3.  **シークレットの自動ローテーション（Secret Rotation）：** 同じデータベース接続パスワードを何年も使い続けるのではなく、システム側で定期的（例：30日ごと）にデータベースのパスワードを自動変更（ローテーション）し、アプリケーションに影響を与えることなく最新の値を反映し続ける仕組みです。

## 3. AWS Secrets Manager と HashiCorp Vault の比較

| 評価基準 | AWS Secrets Manager | HashiCorp Vault |
| :--- | :--- | :--- |
| **提供元** | Amazon Web Services (AWS) | HashiCorp (オープンソース ＆ エンタープライズ) |
| **環境** | Cloud-native (AWSエコシステムとシームレスに統合) | マルチクラウド対応、オンプレミスのプライベートインフラにも構築可能 |
| **ローテーション** | AWS Lambdaを活用して自動化を容易に実装可能 | **動的シークレット（Dynamic Secrets）**（使い捨ての認証情報をその場で生成）をサポート |
| **複雑さ** | 低（完全管理型のSaaSであり、即座に利用可能） | 高（スケーラブルな運用や高可用性構成の構築には高度な専門スキルが必要） |

## 4. 実践：シークレットの動的取得（Dynamic Secrets Fetching）

ローカルの静的ファイルから変数を読み込む従来のコード：
```javascript
// リスク：.envファイルが漏洩したり、ログに出力された場合にパスワードが丸見えになります
const dbPassword = process.env.DB_PASSWORD;
```

以下は、アプリケーションの起動時に公式のAWS SDK v3を使用して、**AWS Secrets Manager** からデータベースの認証情報を動的に安全に取得するNode.jsの実装例です：

```javascript
const { SecretsManagerClient, GetSecretValueCommand } = require("@aws-sdk/client-secrets-manager");

// 特定のリージョンに接続するシークレットマネージャークライアントを初期化
const client = new SecretsManagerClient({ region: "ap-southeast- Southeast-1" });

async function getDatabaseCredentials() {
    const secretName = "production/database/credentials";

    try {
        // 暗号化されたシークレット値の取得コマンドを送信
        const response = await client.send(
            new GetSecretValueCommand({
                SecretId: secretName,
                VersionStage: "AWSCURRENT", // 常に現在有効な最新バージョンを取得
            })
        );

        if (response.SecretString) {
            // 復号されたJSON文字列をパースして接続に必要な情報を抽出
            const credentials = JSON.parse(response.SecretString);
            return {
                host: credentials.host,
                username: credentials.username,
                password: credentials.password
            };
        }
    } catch (error) {
        console.error("AWS Secrets Manager からのシークレット取得に失敗しました:", error);
        throw error;
    }
}

// アプリケーション起動時の初期化処理
async function startApp() {
    const dbConfig = await getDatabaseCredentials();
    // ここで安全にデータベース接続プールを初期化します...
    console.log("-> 認証情報の取得に成功。安全なデータベース接続を確立しています...");
}
```

## 📝 本日のミニ課題：安全なCI/CDリリースの設計

あなたが **DevSecOpsエンジニア（DevSecOps Engineer）** となり、安全な配信システムとインシデント対策を設計してください。

あなたのアプリケーションは、顧客の取引処理のために決済サービス **Stripe** のライブAPIシークレットキー `sk_live_51N...` と接続する必要があります。

### 課題：
1.  GitHub Actions上で自動統合テスト（APIを呼び出すテスト）を実行する必要がある場合、開発チームの誰もが実際のテスト用Stripeキーの中身を参照・コピーできないようにしつつ、テストを実行できるようにするには、どのように設定を構成すべきですか？
2.  プロジェクトの商用APIキーが誤ってコミットされ、3日前にGitHubの公開リポジトリへプッシュされていたことに気づいた場合、あなたが直ちに実行すべき緊急対応手順（4つのステップ）を論理的に記述してください。
3.  オープンソースの機密情報検知ツール **TruffleHog** または **git-secrets** について調査し、開発者のローカルPC環境のコミット前・プッシュ前のイベント（Git Hooks）にこれらを組み込んで、キー情報の含まれるコードのコミットを未然に自動ブロックする仕組みの構築方法を説明してください。
