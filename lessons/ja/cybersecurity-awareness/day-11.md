# Day 11: 高度なID管理 ＆ 認証（OAuth 2.0、OIDC、JWT）

本日は、過去のレガシーなセッションCookie管理メカニズムに別れを告げ、分散型認証およびエンタープライズレベルの現代的なID管理の時代へと足を踏み入れます。

インターネット全体の「*Google / Facebook / Appleでログイン*」ボタンの背後で骨組みとして機能している **OAuth 2.0** と **OpenID Connect (OIDC)** の仕組みを徹底解剖します。また、**JSON Web Token (JWT)** の本質と、それに関連する極めて危険なセキュリティ上の脆弱性を明らかにします。

---

## 1. 認証（Authentication）と認可（Authorization）の区別

技術的な仕様に進む前に、セキュリティにおけるこれら2つの基本概念を厳密に区別しておく必要があります：
*   **認証（Authentication - AuthN）：** 「*あなたは誰ですか？*」という問いに答えるプロセス。ユーザーが自身の身元（アイデンティティ）を証明する行為（例：パスワード入力、指紋スキャン、ワンタイムOTPコードの入力）。
*   **認可（Authorization - AuthZ）：** 「*あなたは何をすることが許可されていますか？*」という問いに答えるプロセス。認証されたユーザーが、特定のリソースへのアクセス権や操作権限を持っているかを検証する行為（例：一般社員は読み取りのみ、マネージャーは承認と編集が可能）。

---

## 2. OAuth 2.0 と OpenID Connect (OIDC) とは何か？

*   **OAuth 2.0（認可フレームワーク）：** 本質的に **認可（Authorization - AuthZ）** を行うためのプロトコルです。サードパーティのアプリケーション（例：航空券予約アプリ）が、ユーザーの別サービス上にあるリソース（例：Googleカレンダー）に対して、**ユーザーのパスワードを入力させることなく**、限定的なアクセス権を与えるために設計されています。
*   **OpenID Connect (OIDC - 認証プロトコル)：** OAuth 2.0のフレームワークを**拡張し、その上に構築**された **認証（Authentication - AuthN）** レイヤーです。OIDCは、ユーザーのアイデンティティ情報（名前、メールアドレス、プロフィール画像など）を認証サーバーからクライアントアプリケーションに安全に渡すための仕組みとして、**IDトークン（ID Token）**（主にJWT形式）というコア概念を導入しました。

### OAuth 2.0 / OIDCにおける主要なロール（役割）：
1.  **リソース所有者（Resource Owner）：** アカウントを所有するエンドユーザー（User）。
2.  **クライアント（Client）：** ユーザーデータへのアクセスを要求するWebサイトまたはモバイルアプリケーション。
3.  **認可サーバー（Authorization Server）：** ユーザーを認証し、各種トークンを発行するサーバー（例：Google Identity Provider）。
4.  **リソースサーバー（Resource Server）：** 保護されたユーザーデータを保持するAPIサーバー（例：Google Drive API）。

### 標準的な認可コードフロー（Authorization Code Flow）：

```text
OAuth 2.0 ＆ OIDC 認可コードフローの動作モデル：

[ クライアント (アプリ) ] ──(1) ユーザーをログイン画面へリダイレクト ──> [ 認可サーバー (Google) ]
        ▲                                                                    │
        │                                                           (2) ユーザー認証完了
        │                                                           ＆ アクセス権限の同意
        │                                                                    │
        │ <─────(3) 認可コード（Authorization Code）を返却 ──────────────────▼
        │
        ├──(4) 認可コード ＋ クライアントシークレットを送信 ─────┐
        │                                                       ▼
        │ <────(5) アクセストークン ＆ IDトークンを返却 ──────── [ 認可サーバー ]
        ▼
[ リソースサーバー (API) ] ──(6) アクセストークンを提示 ──> [ 保護されたリソースを返却 ]
```

## 3. JSON Web Token (JWT) とは何か？

**JWT（JSON Web Token）** は、当事者間で情報をJSONオブジェクトとして安全に転送するためのコンパクトで自己完結的なオープン標準（RFC 7519）形式です。この情報は、送信元の秘密鍵（Symmetric Secret）または公開鍵/秘密鍵のペア（Public/Private Key Pair）によって**電子署名（Digitally Signed）**されているため、改ざんを検知でき、信頼することができます。

### JWTトークン文字列の構造：
JWT文字列はBase64URLエンコードされ、ピリオド（`.`）で区切られた以下の3つのセクションで構成されています：
`[Header].[Payload].[Signature]`

*   **ヘッダー（Header）：** トークンのタイプ（JWT）および使用されている署名アルゴリズム（例：HMAC-SHA256を示す `HS256` や RSA-SHA256を示す `RS256`）を格納します。
    *   *デコード後のJSON例：* `{"alg": "HS256", "typ": "JWT"}`
*   **ペイロード（Payload）：** ユーザーのクレーム（主張する情報）や有効期限（`exp`）、ユーザーID（`sub`）、権限（`role`）などのメタデータを格納します。
    *   *デコード後のJSON例：* `{"sub": "1234567890", "name": "John Doe", "role": "admin", "exp": 1779999999}`
*   **署名（Signature）：** エンコードされたヘッダーとペイロードをドットで結合し、サーバー側で厳重に保管している秘密鍵を組み合わせて、指定されたアルゴリズムでハッシュ化して生成します。受信側のAPIは、この署名を用いてデータが途中でハッカーによって改ざんされていないかを検証します。

> [!WARNING]
> JWTのヘッダーおよびペイロードセクションは、単なる **Base64Urlエンコード** であり、**暗号化はされていません**。誰でも中身をデコードして生のJSONデータを閲覧できます。したがって、**クレジットカード情報やパスワードなどの機密データをJWTのペイロード内に絶対に格納してはいけません！**

## 4. JWTに関する致命的なセキュリティ脆弱性

開発者が独自の検証エンジンを構築する際、以下のような致命的な設計上の失敗が生じがちです：

### 脆弱性 1：アルゴリズム「none」の受け入れ（Algorithm none Attack）
一部の古いJWT検証ライブラリは、ヘッダー内のアルゴリズムに `"alg": "none"` が指定されているトークンを無条件で信頼してしまう欠陥があります。これは、そのトークンには署名が不要であると宣言するものです。
*   **攻撃手法：** ハッカーは有効なJWTをデコードし、ペイロード内の `role` を `"admin"` に書き換え、ヘッダーの `"alg"` を `"none"` に変更し、署名（Signature）セクションを完全に削除してサーバーに送信します。
*   サーバーがこの不適切なリクエストを許容すると、署名のない改ざんトークンを正しいものとみなしてしまい、ハッカーに管理者権限を奪取されてしまいます。
*   **防衛策：** JWTライブラリは常に最新のパッチが適用されたものを採用し、検証用のコードでは **`none` アルゴリズムを明示的に除外（拒否）する設定**を強制してください。

### 脆弱性 2：有効期限（exp）検証の欠如
サーバーがトークンの暗号署名の正当性（データの整合性）のみをチェックし、ペイロードに含まれる有効期限タイムスタンプ（`exp`）の検証をスキップしてしまうミスです。
*   **被害：** ハッカーは、過去に流出した3年以上前の古い期限切れトークンを送信しても、引き続きシステムにアクセスできてしまいます。

## 5. 安全なJWT検証の実装（Secure JWT Implementation）

本番システムでJWTを使用する際は、以下の2つの原則を厳格に守ってください：
1.  **HS256（対称鍵方式）より RS256（非対称鍵方式）を推奨：**
    *   `HS256` は単一の秘密鍵を署名と検証の双方で共有します。もし検証を行うAPIサーバーがハッキングされ、この秘密鍵が漏洩すると、ハッカーは自身で署名した不正トークンを無限に作成できるようになります。
    *   `RS256` は非対称暗号を使用します。認可サーバーは厳重に保護された **秘密鍵（Private Key）** で署名し、リソースAPI側は安全に公開されている **公開鍵（Public Key）** で署名を検証します。これによりAPIサーバー側からの秘密鍵の流出リスクを完全に防止できます。
2.  **検証時に許容するアルゴリズムを明示的にホワイトリスト化する：**

以下は、Node.jsの標準的な `jsonwebtoken` ライブラリを使用して、JWTを安全に検証するミドルウェアの実装例です：

```javascript
const jwt = require('jsonwebtoken');

// 安全な検証ミドルウェアのパターン
function verifyAccessToken(req, res, next) {
    const authHeader = req.headers['authorization'];
    // "Bearer <token>" 形式からトークン部分を抽出
    const token = authHeader && authHeader.split(' ')[1];

    if (!token) {
        return res.status(401).json({ error: "アクセストークンが必要です！" });
    }

    // セキュリティ設定：許可するアルゴリズムを「HS256」のみに厳格に制限
    // これにより、アルゴリズム "none" を使ったバイパス攻撃を完全に無力化します
    jwt.verify(token, process.env.JWT_SECRET_KEY, { algorithms: ['HS256'] }, (err, decodedUser) => {
        if (err) {
            // トークンの期限切れや署名の改ざんはここで確実にキャッチされます
            return res.status(403).json({ error: "アクセストークンが無効または期限切れです！" });
        }

        // 検証されたデコードデータをリクエストコンテキストに格納し、次のハンドラーへ渡す
        req.user = decodedUser;
        next();
    });
}
```
