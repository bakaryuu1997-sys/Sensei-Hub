# 🪝 1. THE HOOK: 「Go-live」という栄光のその先に

プロジェクトの「Go-live」（本番リリース）の日は、結婚式のようなものです。しかし、結婚式の後には**運用（Operation）**という、長く、時には困難な「結婚生活」が待っています。

もし決済システムが深夜2時にダウンしたら、誰が直すのでしょうか？もし顧客データが流出したら、誰が法的責任を負うのでしょうか？

日本では、システムの安定稼働は企業の「血流」そのものと考えられています。単にシステムを「作る」人だけでなく、そのシステムを10年、20年と守り抜き、円滑に維持し続ける方法を知っているマスターエンジニアが求められています。Day 65はPhase 7の最終章です。自分の製品の真の「守護者（Guardian）」になる方法を学びます。

# 🎭 2. ANALOGY: システム管理は「病院の経営」と同じ

あなたのITシステムを総合病院に例えてみましょう：

1.  **ITIL (Information Technology Infrastructure Library)**: すべての医師や看護師が従うべき標準作業手順書（SOP）です。
2.  **サービスデスク (Service Desk)**: 患者（ユーザー）を受け入れ、症状を分類する総合受付です。
3.  **インシデント管理 (Incident Management)**: 救急外来です。目的は、一刻も早く患者の命を救うこと（システムを暫定的に復旧させること）です。
4.  **問題管理 (Problem Management)**: 研究所です。患者が危機を脱した後、再発を防ぐために「根本原因（Root Cause）」を突き止めます。
5.  **システム監査 (System Audit)**: 医療監査委員会です。病院が手順を守っているか、薬品の期限は切れていないか、医師が専門性を欠いた行為をしていないかを検査します。

名医がいても運用ルールがない病院は、すぐに混乱の渦に飲み込まれてしまいます。

# ⚙️ 3. UNDER THE HOOD: ITILサービスライフサイクル

**FE Master**試験において、ITILは必須の語彙です。以下の5つの段階で構成されます：

1.  **サービス戦略 (Service Strategy)**: そのサービスが顧客にどのような価値を提供するかを定義します。
2.  **サービス設計 (Service Design)**: インフラ、セキュリティ、SLA（合意事項）を設計します。
3.  **サービス移行 (Service Transition)**: テスト、パッケージングを行い、本番環境へリリースします。
4.  **サービス運用 (Service Operation)**: ユーザーサポートや日々のトラブル対応を行います。
5.  **継続的なサービス改善 (CSI)**: サービスをより良くするための改善を常に行います。

# 🚀 4. DEEP DIVE: インシデント管理 vs 問題管理

これはIPA試験で最も「紛らわしい」部分です。マスターエンジニアは明確に区別する必要があります：

### 4.1 インシデント管理 (Incident Management)
-   **目的**: サービスを可能な限り迅速に復旧させる。
-   **アクション**: 「回避策（Workaround）」を使用する。
-   *例*: サーバーがダウンした？ -> 即座に再起動して復旧させる。

### 4.2 問題管理 (Problem Management)
-   **目的**: 根本原因を特定し、再発を防止する。
-   **アクション**: ログ分析やコードのバグ修正を行う。
-   *例*: なぜサーバーがダウンしたのか？ -> メモリリークを発見 -> コードを修正する。

# 🎯 5. EXAM LOGIC: IPA試験の重点 - 監査とSLA

**マスターが避けるべき「罠」：**
1.  **SLA (サービスレベル合意書)**: サービスの品質に関する合意（例：稼働率99.9%以上）。これを下回ると、ベンダーはペナルティを負うことがあります。
2.  **システム監査 (System Audit)**: 監査人は、開発チームから**独立（Independent）**していなければなりません。自分で自分の仕事を監査することはできません！

**過去問サンプル（FE試験風）：**
「ITサービスマネジメントにおいて、サービスの停止時間を最小限に抑え、迅速に回復させることを目的とするプロセスはどれか。」
A. 問題管理 B. インシデント管理 C. 構成管理 D. 変更管理
*正解：B.*

# 💼 6. PROFESSIONAL CONTEXT: 日本のITサポートにおける「おもてなし」

日本の企業において、ITサポートは単なるバグ修正ではありません。それは「献身」です。
-   サーバー障害が発生した場合、マスターBrSEは復旧していなくても30分ごとに顧客に状況を報告します。
-   事象解決後、極めて詳細な**障害報告書（Failure Report）**を作成します：原因、影響範囲、暫定対策、恒久対策。
*マスターのスキル*: 危機的状況下で冷静さを保ち、プロフェッショナルなコミュニケーションを行う能力こそが、マスターレベルの証明です。

# 🚀 4.3 変更管理 (Change Management)

運用フェーズにおけるすべての変更（ソフトの更新、サーバーの入れ替え）は、管理下に置かれなければなりません。
-   **変更要求 (RFC)**: すべての変更要求は記録される必要があります。
-   **影響評価**: 変更が失敗した場合のリスクを評価します。
-   **切り戻し計画 (Rollback Plan)**: 更新後に不具合が出た際、即座に元の状態に戻すための計画です。

### 4.4 資産・構成管理 (Asset & Configuration Management)

マスターエンジニアは、自分のシステムにサーバーが何台あり、どのライセンスが有効かを正確に把握していなければなりません。
-   **構成管理データベース (CMDB)**: すべての構成要素（**CIs - Configuration Items**）とその関係性を管理するデータベースです。

# 📖 8. MASTER GLOSSARY: ITSM 深掘り用語集

-   **SLI (サービスレベル指標)**: 実際のサービス品質指標（例：平均レスポンス時間200ms）。
-   **SLO (サービスレベル目標)**: 達成すべき目標値（例：90%のリクエストは500ms以内に返す）。
-   **MTTR (平均復旧時間)**: 故障が発生してから復旧するまでの平均時間。短いほど良い。
-   **サービスデスク**: ユーザーとサービス提供者の間の単一接触窓口（SPOC）。
-   **内部監査**: 自社の従業員によって行われる監査。

# 📍 9. MASTER CASE STUDY: ECサイトでの「深夜2時の惨劇」

**課題**: 深夜2時、決済システムに重大な障害が発生し、すべての取引が失敗しました。

**マスターの解決策 (ITSMフロー)**:
1.  **サービスデスク**: 自動監視システムからのアラートを受信。
2.  **インシデント管理**: 当番のエンジニアが、待機系（Standby）サーバーへの切り替えという「回避策」を実施。15分でシステムを復旧。
3.  **問題管理**: 翌朝、チームでログを分析し、前夜に投入された重いSQLクエリが原因であることを特定。クエリを最適化し、再発を防止。

**結果**: 売上損失を最小限に抑え、顧客からの信頼を維持しました。

# 🎯 10. EXAM LOGIC: システム監査のプロセス

IPA試験では、**システム監査**の段階がよく問われます：
1.  **監査計画**: 監査の範囲や対象を決定します。
2.  **監査実施**: 証拠の収集、関係者へのヒアリングを行います。
3.  **監査報告**: 報告書を作成し、改善勧告を行います。
**マスターの洞察**: 監査人は必要な情報すべてにアクセスする権限を持ちますが、システムの運用そのものに干渉してはいけません。

# 💼 12. PROFESSIONAL CONTEXT: 日本におけるITIL資格の価値
