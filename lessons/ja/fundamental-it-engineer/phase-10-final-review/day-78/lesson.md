# 🎭 2. ANALOGY: 弁当の製造ラインと工程管理

プロジェクト管理は、高速な **弁当 (Bento)** の製造ラインに似ています：
1.  **タスク (工程)**: 米を炊く、卵を焼く、おかずを詰める。
2.  **依存関係**: 米が炊き上がらなければ、おかずを詰めることはできません -> **終了-開始 (FS: Finish-to-Start)** 関係。
3.  **クリティカルパス**: 最も時間がかかる一連の工程。もし「炊飯」が1分遅れたら、弁当全体の完成も1分遅れます。
4.  **バッファ (余裕時間)**: 「卵焼き」が予定より早く終われば、料理人は全体の完成を遅らせることなく2分間休めます -> これを **総余裕時間 (Total Float)** と呼びます。

# ⚙️ 3. UNDER THE HOOD: ネットワーク工程表のマスタークラス

科目Bでは、図を見るだけでなく、外科手術のような精密さで計算を行う必要があります。

### PERT (Program Evaluation and Review Technique)
IPAではよく、期待値としての **所要期間 ($T_e$)** の計算が問われます：
$$T_e = \frac{最良 + (4 \times 最確) + 最悪}{6}$$
-   **最良 (Optimistic)**: すべてが完璧に進んだ場合。
-   **最確 (Most Likely)**: 最も可能性が高い期間。
-   **最悪 (Pessimistic)**: 最悪の事態が起きた場合。

### CPM (クリティカルパス法)
Masterにとって必須の指標：
1.  **ES (Early Start)**: 最早開始時刻。
2.  **EF (Early Finish)**: 最早終了時刻。
3.  **LS (Late Start)**: 最遅開始時刻（プロジェクトを遅らせない限界）。
4.  **LF (Late Finish)**: 最遅終了時刻。
5.  **余裕時間 (Float)**: $LS - ES$ または $LF - EF$。**Float = 0** のタスクが **クリティカルパス** 上にあります。

# 🗺️ 4. ARCHITECTURE & FLOW: 山積み法 (Leveling) vs 山崩し法 (Smoothing)

PMとして、現実に直面します：開発者はスーパーマンではありません。

1.  **リソース平準化 (Resource Leveling)**: 誰も1日8時間以上働かないように、プロジェクト期間を延ばす構成。 (**優先度: リソース > 時間**)。
2.  **リソース平滑化 (Resource Smoothing)**: プロジェクト完了日を変えずに、全員の忙しさが均等になるよう調整する。 (**優先度: 時間 > リソース**)。

# 💻 5. LOGIC & PSEUDO-CODE: クリティカルパス・アルゴリズム

コンピュータがES/EF（前進計算）を算出するロジックをシミュレートしてみましょう：

```
/* ○ 前進計算 (Forward Pass) のロジック */
For Each Task t in SortedTasks:
    if (t.isStartTask)
        t.ES = 0
    else
        t.ES = Max(先行タスク.EF)
    t.EF = t.ES + t.Duration
```

**Master Rule**: 左から右（前進）へ進むときは **MAX** 値を取ります。右から左（後退）へ戻るときは **MIN** 値を取ります。この「マントラ」を覚えれば、試験で間違えることはありません！

# 🎯 6. EXAM LOGIC: 「クラッシング (Crashing)」シナリオ

**問題**: 「プロジェクトが3日遅れています。タスクA（短縮コスト：100ドル/日）とタスクB（300ドル/日）があります。タスクAはクリティカルパス上にありますが、タスクBは違います。あなたはどうしますか？」

**Master Strategy (戦略)**:
1.  必ず **クリティカルパス上** のタスクのみを短縮する。
2.  **最も短縮コストが低い** タスク（この場合はA）を選ぶ。
3.  **注意**: 短縮した後、別の経路が *新しい* クリティカルパスになる可能性があります！

# 💼 7. PROFESSIONAL CONTEXT: 日本のIT文化における「完璧」と「納期」

日本のIT業界において、**納期遅延 (Delay)** は **信用 (Shin-nin)** の重大な毀損とみなされます。
-   日本のPMは **EVM (アーンドバリュー管理)** を厳格に運用します：
    -   **PV (Planned Value)**: 計画値。
    -   **AC (Actual Cost)**: 実績コスト。
    -   **EV (Earned Value)**: 出来高（実際に完成した価値）。
-   もし **CPI (EV/AC) < 1** であれば、そのプロジェクトは予算オーバーで「出血」している状態です。

# 🕵️ 8. MASTER DEEP DIVE: EVMの数学 —— 数字は嘘をつかない

FE試験において、EVMの問題は公式さえマスターすれば「得点源」です：

1.  **CV (コスト差異) = EV - AC**: 予算内か、オーバーか？ (正なら良好)。
2.  **SV (スケジュール差異) = EV - PV**: 進んでいるか、遅れているか？ (正なら良好)。
3.  **CPI (コスト効率指数) = EV / AC**: 1ドルの支出でいくらの価値を生んだか？ (> 1なら効率的)。
4.  **SPI (スケジュール効率指数) = EV / PV**: 計画に対する進捗速度。 (> 1なら早い)。

**EAC (完成時総コスト見積もり) の公式**:
$$EAC = \frac{BAC}{CPI}$$
(BACは当初の総予算)。

# 🗺️ 9. MASTER CASE STUDY: 日本の「マイナンバー」システムの遅延

日本の「マイナンバー」カードプロジェクトは、大幅な遅延とデータセキュリティの問題に直面しました。
-   **原因**: リスク管理において、膨大なデータ量と法規制の頻繁な変更を予測しきれませんでした。
-   **Master Solution**: 巨大なシステム全体に硬直的な **ウォーターフォール** を適用するのではなく、小さなモジュールごとに **アジャイル** を適用して柔軟性を持たせるべきでした。

# 🛡️ 10. UNDER THE HOOD: プロジェクトリスク対応戦略

リスク管理はプロジェクトの「鎧」です：

1.  **回避 (Avoid)**: 計画を変更してリスクを完全に排除する。
2.  **軽減 (Mitigate)**: リスクの発生確率または影響度を下げる。
3.  **転嫁 (Transfer)**: 保険をかけたり、第三者にリスクを負わせる。
4.  **受容 (Accept)**: 何もせず、**予備費 (Contingency Fund)** を設定しておく。

**EMV (期待金額価値)**:
$$EMV = 発生確率 \times 影響額$$

# 💻 11. MASTER SIMULATION: 余裕時間 (Float) の計算

**シナリオ**:
-   タスクA（2日） -> タスクB（3日）とタスクC（5日）へ分岐。
-   BとCの両方が完了したら、タスクD（2日）へ。
-   **課題**: タスクBの総余裕時間を求めよ。

**Master Walkthrough**:
1.  **経路1 (クリティカル)**: A(2) -> C(5) -> D(2) = **9日間**。
2.  **経路2**: A(2) -> B(3) -> D(2) = **7日間**。
3.  **Bの余裕時間** = 全体期間(9) - 経路2の期間(7) = **2日間**。
-   **結論**: 工程Bは、最終納期に影響を与えずに2日間まで遅れることができます。

IPAの問題で、データポイントが **UCL (上方管理限界)** または **LCL (下方管理限界)** の外にある図が出た場合：

-   **7の法則 (Rule of Seven)**: 限界線内であっても、7点連続で中心線の一方にある場合は、異常とみなされます。

# 💻 14. MASTER SIMULATION: スキルの重複とリソース配分

**問題**: プロジェクトにタスクA（DBスキルが必要）とタスクB（FEスキルが必要）が同時に走っています。
-   メンバーX（DBとFEの両方のエキスパート）とメンバーY（FEのみのエキスパート）がいます。
-   **問い**: タスクAの優先度が高い場合、どう配分しますか？

**Master Solution**:
1.  専門的なタスクには、その専門スキルを持つメンバーを優先的に割り当てる。
2.  **XをタスクAに割り当てる**（XしかDBを扱えないため）。
3.  **YをタスクBに割り当てる**（YはFEを扱えるため）。
-   **理由**: もしXをFEに割り当ててしまうと、DBタスクをこなせる人がいなくなり、**ボトルネック**が発生します。これがリソース最適化の核心です。
