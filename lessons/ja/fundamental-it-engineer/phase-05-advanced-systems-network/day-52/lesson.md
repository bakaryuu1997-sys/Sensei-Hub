# 🪝 1. THE HOOK: 「99.999%」の約束とエンジニアの執着

AWSやGoogleが、サービスの稼働率（Availability）を **99.999%** と約束しているのを聞いたことがありますか？この数字は非常に小さく見えますが、1年間のうちシステムが「死んでもいい時間」が最大で **5分15秒** しかないことを意味します。

彼らはどうやってその数字を算出しているのでしょうか？なぜサーバーを1台追加するだけでこの数字が跳ね上がるのか、しかしやり方を間違えるとコストだけが10倍になってしまうのはなぜか？

Day 52へようこそ。今日は単なるコードの話ではありません。 **「システム工学の数学」** の話です。 **MTBFやMTTR** といった「生命指標」を解読し、サーバークラスターの生存確率を計算し、システムのボトルネックを正確に予測するための武器 **「M/M/1」** と仲良くなりましょう。シニアアーキテクトを目指すなら、これらはクライアントとの交渉の場で、空で言えなければならない数字です。

# 🎭 2. ANALOGY: 東京の救急車隊を管理する

あなたが東京の救急車隊のマネージャーだと想像してください。

1.  **稼働率 (Availability)**: 緊急通報があった時、少なくとも1台の救急車がすぐに出動できる確率。
2.  **MTBF (平均故障間隔)**: 平均して何日走ると、1台の救急車が故障するか。長いほど良い（丈夫な車）。
3.  **MTTR (平均修理時間)**: 車が壊れた時、整備士が修理に平均何時間かかるか。短いほど良い（腕の良い整備士）。
4.  **待ち行列 (Queueing Theory)**: 1台しか車がないのに、同時に2人の患者から電話が来た時、2人目は何分待たされるか。サービスの提供スピードより、患者が来るスピードが速ければ、待ち行列は無限に伸びていきます。

ITの世界では：救急車はサーバー、患者はユーザーのリクエスト、整備士はSRE/DevOpsチームです。

# ⚙️ 3. UNDER THE HOOD: MTBF, MTTR と 稼働率

これは **FE Master (IPA)** 試験における「システム管理」の心臓部です。

### 3.1 MTBF (Mean Time Between Failures - 平均故障間隔)
- **定義**: システムが故障してから、次に故障するまでの平均的な正常稼働時間。
- **公式**: `合計稼働時間 / 故障回数`。

### 3.2 MTTR (Mean Time To Repair - 平均修理時間)
- **定義**: 故障が発生してから、システムが復旧するまでに必要な平均的な修理時間。
- **公式**: `合計修理時間 / 故障回数`。

### 3.3 稼働率 (Availability)
- **定義**: 全時間のうち、システムが実際に稼働している時間の割合。
- **黄金の公式**: `稼働率 = MTBF / (MTBF + MTTR)`。

# 🚀 4. DEEP DIVE: 複合システムの信頼性

ネットワーク全体の稼働率はどう計算するのでしょうか？

### 4.1 直列システム (Series System)
**すべて** の構成要素が動いていないと、システムが動かない構成。（例：サーバーとデータベースが1台ずつ直列）。
- **全体の稼働率** = `A1 × A2 × ... × An`。
- *マスターの鉄則*: 全体の信頼性は、最も弱い構成要素の信頼性よりも必ず低くなります。

### 4.2 並列システム (Parallel System)
**少なくとも1つ** が動いていれば、システムが動く構成。（例：2台のサーバーでロードバランシング）。
- **全体の稼働率** = `1 - [(1 - A1) × (1 - A2) × ... × (1 - An)]`。
- *マスターの鉄則*: これこそが、99%の安価な部品から、99.999%のシステムを作り出す「魔術」です。

# 🏛 *MASTER KNOWLEDGE*: M/M/1 待ち行列理論

CPU使用率が50%なのに、ユーザーが「遅い」と感じるのはなぜか？その答えは **M/M/1 待ち行列モデル** にあります。

### 5.1 基本パラメータ:
- **λ (ラムダ)**: リクエストの到着率（例：10件/秒）。
- **μ (ミュー)**: システムの処理率（例：20件/秒処理できる能力）。
- **ρ (ロー) - 利用率**: `ρ = λ / μ`。（システムがパンクしない条件： `ρ < 1`）。

### 5.2 待ち時間の計算公式:
- **応答時間 (システム内滞在時間)** = `1 / (μ - λ)`。
- **待ち行列の長さ (並んでいるリクエスト数)** = `ρ / (1 - ρ)`。

*マスターの教訓*: システムの利用率が80-90%（ `ρ = 0.9`）に達すると、待ち時間は指数関数的に増大します。日本の熟練アーキテクトが「CPU使用率は70%以下に抑えろ」と口を酸っぱくして言うのはこのためです。

# 📍 8. MASTER CASE STUDY: 2020年 東京証券取引所 (TSE) の全停止

2020年10月、東京証券取引所はハードウェアの故障により、終日売買停止に追い込まれました。
- **原因**: 共有ストレージの故障。本来、並列化された待機系に自動で切り替わる（フェイルオーバー）はずでしたが、設定ミスにより切り替わりませんでした。
- **マスターの教訓**: 並列システムで理論上の稼働率を 99.999% にしても、 **「検知 (Detection)」** と **「切り替え (Failover)」** の仕組みを定期的に監査 (Audit) しなければ、冗長化は無意味になります。

# 🎯 9. EXAM LOGIC: IPA 試験の急所

1.  故障履歴の表から **MTBF** を算出する。
2.  **M/M/1** 待ち行列モデルで、平均待ち時間を計算する。
3.  **フェイルセーフ、フェイルソフト、フールプルーフ** の違いを判別する。

**サンプル問題（日本語）**:
「MTBFが450時間, MTTRが50時間のシステムの稼働率はいくらか。」
- **正解**: 0.9 (計算: 450 / 500)。
