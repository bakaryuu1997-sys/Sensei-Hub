# 🪝 1. THE HOOK: なぜ銀行システムは「変化」を恐れるのか？

**三菱UFJ銀行 (MUFG)** や **みずほ銀行** といった日本の巨大銀行を運営していると想像してください。毎秒、数百万件の取引が行われます。もし、すべてのデータと処理ロジックをたった一台のコンピュータ（メインフレーム）に詰め込んだら、そのマシンがショートした瞬間に何が起きるでしょうか？逆に、システムを数千台のミニサーバーに分散させた場合、どうやってデータが互いに衝突しないように保証すればいいのでしょうか？

Day 51へようこそ。今日は、ITシステムの「背骨」であるシステム構成の設計方法を学びます。古典的な **集中処理** から、現代的な **分散処理** ネットワークまで。 **システム構成** を理解することは、単にFE試験に合格するためだけでなく、ソフトウェアの「陣形」を正しく選ぶことができる **システムアーキテクト** としての思考力を養うことにつながります。

# 🎭 2. ANALOGY: 回転寿司チェーン「スシロー」の運営

システムアーキテクチャを理解するために、回転寿司の **スシロー** をどう運営するか考えてみましょう。

1.  **集中処理 (Centralized)**: 全店舗の注文を東京の「マスターキッチン」一箇所に送り、そこで作ってから各店舗に配送します。管理は非常に楽ですが、東京のキッチンが火事になれば全店舗が止まります。
2.  **分散処理 (Distributed)**: 各店舗にキッチンがあり、独自に仕入れ、独自に寿司を握ります。渋谷店がダメになっても、新宿店は通常通り営業できます。品質の同期は難しいですが、非常に強靭（タフ）です。
3.  **クライアントサーバー**: 客（クライアント）がタブレットで注文し、キッチンのサーバー（サーバー）がそれを受けて料理を準備します。
4.  **3層アーキテクチャ**:
    - **プレゼンテーション層**: 客が手にする美しいメニュー画面。
    - **アプリケーション層**: 注文の順番や調理時間を計算する職人の頭脳。
    - **データ層**: 新鮮なネタが入っている冷蔵庫。

# ⚙️ 3. UNDER THE HOOD: 集中処理 vs. 分散処理

**FE Master (IPA)** 試験では、これらの処理モデルを明確に分類する必要があります。

### 3.1 集中処理 (Centralized Processing)
1台の巨大なコンピュータ（メインフレーム）ですべてを処理します。ユーザーの端末は「ダミーターミナル」（計算能力なし）です。
- **長所**: セキュリティが極めて高く、データの一貫性が100%保たれる。
- **短所**: メインフレームのハードウェアが超高額。 **単一障害点 (SPOF)** になるリスクがある。

### 3.2 分散処理 (Distributed Processing)
ネットワークで繋がれた複数のコンピュータに仕事を分担させます。
- **クライアントサーバーシステム**:
    - **クライアント**: 要求 (Request) を送り、結果を表示する。
    - **サーバー**: 要求を受け取り、処理して応答 (Response) を返す。
- **シンクライアント (Thin Client)**: 端末には最低限の機能しか持たせません。ハードディスクもなく、重いアプリも入れません。すべてのロジックとデータはサーバー側にあります。
    - *日本での実例*: 金融機関や官公庁では、個人情報の持ち出しを防ぐためにシンクライアントが「王道」として使われています。

# 🚀 4. DEEP DIVE: 3層アーキテクチャ (Three-tier Architecture)

現代のマスターウェブアプリケーションの標準モデルです。

### 4.1 プレゼンテーション層
- **役割**: ユーザーインターフェース (ブラウザ、モバイルアプリ)。
- **技術**: HTML, CSS, JavaScript (フロントエンド)。

### 4.2 アプリケーション層
- **役割**: 業務ロジック (Business Logic)、計算、権限チェック。
- **技術**: Java, Node.js, Python (バックエンド)。

### 4.3 データ層
- **役割**: データの安全な保存と取り出し。
- **技術**: Oracle, MySQL, PostgreSQL。

*なぜ3層に分けるのか？*
それは **「独立性」** のためです。MySQLからMongoDBに乗り換えたい時、第3層だけを修正すれば第1層（見た目）には影響を与えずに済みます。

# 🏛 *MASTER KNOWLEDGE*: デュアル、デュプレックス、クラスタリング

システムを「絶対に止めない」ためにはどうすればいいか？IPA試験では以下の区別が問われます。

### 5.1 デュアルシステム (Dual System)
2つの全く同じシステムを **「並列」** に動かし、常に同じ処理をさせます。結果を互いに照合し、AとBの結果が違えばエラーを検知します。
- *用途*: 1ミリのミスも許されない銀行の基幹系や航空制御など。

### 5.2 デュプレックスシステム (Duplex System)
主系（オンライン）と待機系（スタンバイ）の2台を用意します。
- **ホットスタンバイ**: 待機系も起動しており、データも同期済み。数秒で切り替え可能。
- **ウォームスタンバイ**: OSは起動しているが、アプリはまだ動いていない。切り替えに数分かかる。
- **コールドスタンバイ**: 待機系は電源オフの状態。切り替えに最も時間がかかる（RTOが高い）。

### 5.3 クラスタリング (Clustering)
複数のサーバーを束ねて、1台のサーバーのように見せる技術です。
- **フェイルオーバー**: 1台が壊れたら、自動で別のサーバーに処理を引き継ぐ。
- **負荷分散 (Load Balancing)**: 仕事を均等に割り振り、特定のサーバーが過負荷になるのを防ぐ。

# 📍 7. MASTER CASE STUDY: NTTデータ「全銀システム」

日本の銀行間決済を支える **「全銀システム」** は、安定性の傑作です。
- **構成**: 中心となる決済処理には信頼性の高いメインフレーム（集中処理）を使い、周辺サービスには柔軟な分散システムを組み合わせています。
- **信頼性**: 最も重要なノードには **デュアルシステム** を採用し、24時間365日の稼働を保証しています。
- *マスターの教訓*: すべての目的に完璧な単一のアーキテクチャはありません。優れたエンジニアは、IaaS、オンプレミス、クラウドを組み合わせた **ハイブリッド** な構成を設計できるのです。

# 🎯 8. EXAM LOGIC: IPA 試験の急所

1.  **シンクライアント** の導入メリット（TCOの削減、セキュリティ向上）。
2.  **3層アーキテクチャ** の各層の役割（「入力チェックはどこですべきか？」など）。
3.  直列・並列システムの **稼働率計算** 。

**サンプル問題（日本語）**:
「プレゼンテーション層, アプリケーション層, データ層の3階層に分離したシステムの利点はどれか。」
- **正解**: 各層の独立性が高く, 変更時の影響を抑えられる。

# 💼 9. PROFESSIONAL CONTEXT: 日本のSEが「ミドルウェア」を重視する理由

大手SIer（システムインテグレーター）の世界では、 **ミドルウェア (Middleware)** の知識がシニアへの登竜門です。
- **役割**: OSとアプリケーションの「接着剤」。
- **実例**: データベース接続を管理する **Prisma** や **Hibernate** 、非同期処理を担う **RabbitMQ** など。
日本の大規模システムでは、これらのミドルウェアをいかに正しく設定し、性能を引き出すかがプロジェクトの成否を分けます。
