# 🪝 1. THE HOOK: NASAが学んだ1億2500万ドルの「純粋」な教訓

1999年、NASAの探査機**マーズ・クライメイト・オービター (Mars Climate Orbiter)** は火星の大気圏で分解・消失しました。その驚くべき原因は、単純なデータの不一致でした。ソフトウェア開発のあるチームはヤード・ポンド法（ポンド・秒）を使い、別のチームはメートル法（ニュートン・秒）を使っていたのです。

JavaScriptの世界において、これは**「状態の破壊的な変更（State Mutation）」**によるバグと同じです。アプリケーションのある場所で変数を書き換えた結果、全く無関係なコンポーネントが、元の値を期待していたために「分解」してしまうのです。

**マスターの使命**: **野村證券**の超高速取引（HFT）プラットフォームや、ミッションクリティカルな宇宙開発において、私たちはただコードを書くのではありません。**「関数型コード（Functional Code）」**を書くのです。ロジックの「純粋性」を追求することで、予測可能で、テスト可能で、破壊不可能なシステムを構築します。

# 🎭 2. ANALOGY: 静岡の純水ろ過システム

静岡県にある、富士山の湧き水を利用した高級な水ろ過工場を想像してください。

1.  **入力（引数）**: 富士山の天然の生水。
2.  **プロセス（純粋関数）**: 特殊なフィルターを通したろ過。このプロセスは、元の湧き水の源泉を汚染することも、工場の外の気温を変えることもありません。
3.  **出力（戻り値）**: 純粋なミネラルウォーターのボトル。
4.  **副作用なし**: フィルターが工場の照明を点けたり、近くの川の魚の数を変えたりすることはありません。
5.  **予測可能性**: 同じ生水を1,000回入れれば、1,000回とも全く同じ品質のミネラルウォーターが出てきます。

**関数型プログラミング (FP)** とは、アプリケーション全体をこのような「純粋なフィルター」の組み合わせで構築する技術です。隠れた驚き（サプライズ）はなく、そこにあるのは純粋なロジックだけです。

# ⚙️ 3. UNDER THE HOOD: 関数型プログラミングの柱

FPは単に関数を使うことではありません。「どうやってやるか（Imperative/命令型）」から「それは何か（Declarative/宣言型）」へのパラダイムシフトです。

### 3.1 純粋関数 (Pure Functions): FPの最小単位
関数が「純粋」であるためには、以下の条件を満たす必要があります。
1.  **同一性**: 同じ入力に対して、常に同じ出力を返すこと。
2.  **副作用（Side Effects）なし**: スコープ外の状態（グローバル変数、コンソール出力、DOM操作など）を一切変更しないこと。

```javascript
// ❌ 不純（Impure）: 外部の状態に依存し、変更する可能性がある
let tax = 0.1;
const calculateTotal = (price) => price + (price * tax); 

// ✅ 純粋（Pure）: 自己完結している
const calculateTotalPure = (price, taxRate) => price + (price * taxRate);
```

### 3.2 不変性 (Immutability): 「触るな」のルール
FPでは、データ（オブジェクトや配列）を直接変更することはありません。代わりに、新しいバージョンを作成します。
- **なぜ？**: データが決して変わらないのであれば、デバッグ中に「誰がこの値を変えたのか？」と悩む必要がなくなるからです。
- **V8エンジンの仕組み**: オブジェクトをミューテート（変更）せずに新しいオブジェクトを作成する場合、V8は「構造共有（Structural Sharing）」という仕組みを使って、変更されていない部分のメモリを再利用し、効率を最適化します。

### 3.3 高階関数 (Higher-Order Functions: HOF)
他の関数を引数として受け取るか、関数を戻り値として返す関数のことです。
- `map`、`filter`、`reduce` は、JavaScriptにおけるHOFの「三種の神器」です。

# ⚙️ 4. ARCHITECTURE & FLOW: 宣言型 vs 命令型

日本の**SIer**（システムインテグレーター）の環境では、「トリッキーなコード」よりも「読みやすさ」が優先されます。FPはコードを一つの物語（ストーリー）のように見せます。

```mermaid
graph TD
    subgraph 命令型アプローチ
        A[配列をループ] --> B[条件をチェック]
        B --> C[新しい配列にPush]
        C --> D[カウンターを修正]
    end

    subgraph 関数型アプローチ
        E[データソース] --> F[フィルター]
        F --> G[マップ]
        G --> H[最終結果]
    end
```

**マスターの視点**: 命令型コードはマニュアル車のようなものです。クラッチ、ギア、エンジン回転数をすべて管理しなければなりません。関数型コードはオートマ車です。行き先（何をするか）を伝えれば、内部の仕組みはエンジン（JSエンジン）が処理してくれます。

# 💻 5. LOGIC & PSEUDO-CODE: パイプライン・アルゴリズム (IPA標準)

マスターエンジニアは、小さな関数を組み合わせて（合成して）複雑なロジックを構築します。

### アルゴリズム: ProcessOrder(注文データ: data)

```text
■ ProcessOrder(data)
| // パイプラインパターン: データが関数を流れていく
| 
| 関数 ApplyDiscount(o) ← o.price * 0.9
| 関数 AddTax(p) ← p * 1.1
| 関数 FormatCurrency(v) ← "¥" + v
| 
| 結果 ← data
| ▲ 結果 ← ApplyDiscount(結果)
| ▲ 結果 ← AddTax(結果)
| ▲ 結果 ← FormatCurrency(結果)
| 
| 戻り値 結果
```

**マスターの分析**: ロジックを `ApplyDiscount` や `AddTax` に分割することで、それぞれのユニットを独立してテストできます。**日本銀行**の監査が入るようなシステムでは、このレベルの透明性が「合格」か「システム障害」かの分かれ目になります。

# 🎯 6. EXAM LOGIC: 基本情報技術者試験 (FE) におけるFP

FE試験（特に科目A）では、**再帰（Recursion）**や**Map/Reduce**のロジックに関する理解が問われます。

**問題**: 「純粋関数」の説明として適切なものはどれか？
- **A**: APIを呼び出し、UIを更新する関数。
- **B**: 戻り値が入力値のみによって決定され、外部に観測可能な副作用を与えない関数。
- **C**: グローバル変数を使用してカウントを保持する関数。
- **D**: 現在時刻に基づいて乱数を生成する関数。

**正解**: **B**。これは関数型プログラミングの最も基本的な定義です。

# 💼 7. PROFESSIONAL CONTEXT: 日本のエンタープライズにおけるFP

1.  **データ整合性**: 日本のフィンテック（**PayPay**、**LINE Pay**など）では、不変なデータ構造を使用することで、高並列環境でのレースコンディション（競合状態）を防いでいます。
2.  **レガシー・モダナイゼーション**: 多くのSIerが古いJavaやC#のシステムをTypeScriptに移行しています。FPパターンは、新しいコードが「監査に耐えうる（Audit-Ready）」ものであることを保証するための推奨される方法です。
3.  **コードの「改善（Kaizen）」**: 関数型コードはリファクタリングが容易です。関数が独立しているため、ある関数を入れ替えても、システム全体のバグが連鎖する「ドミノ倒し」を恐れる必要がありません。

### 3.4 DEEP DIVE: カリー化と部分適用 (Currying)
カリー化とは、複数の引数を取る関数を、「一つの引数を取る一連の関数」に変換するプロセスのことです。

**現場のシナリオ（ソニー・インタラクティブエンタテインメント）**:
SIEのロギングシステムを構築していると想像してください。すべてのログに「サービス名」というプレフィックスを付けたいとします。

```javascript
// 通常の関数
const log = (service, message) => `[${service}] ${message}`;

// カリー化バージョン
const curriedLog = (service) => (message) => `[${service}] ${message}`;

const gameServiceLog = curriedLog("PlayStation-Network");
console.log(gameServiceLog("Server started")); // "[PlayStation-Network] Server started"
console.log(gameServiceLog("User logged in")); // "[PlayStation-Network] User logged in"
```
**メリット**: `service` 引数を部分適用することで、特定の用途に特化した「Game Service Logger」を簡単に作成できます。これは、高度なアーキテクチャの再利用性（Reuse）を実現します。

---

### 3.5 ADVANCED: 合成 vs 継承 (Composition vs Inheritance)
Phase 2ではプロトタイプ（継承）について学びました。Phase 3では**「合成（Composition）」**を推奨します。
- **継承**: 「猫は動物である」（親クラスが壊れると子も壊れる「Fragile Base Class」問題の原因）。
- **合成**: 「猫は食べる、寝る、鳴くという機能を持つ」（小さな振る舞いを組み合わせて大きなオブジェクトを作る）。

**マスターの鉄則**: 継承よりも合成を優先せよ。要件が毎週変わる東京のアジャイルチームにおいて、合成はより柔軟で壊れにくい構造を提供します。

# 🏆 9. MASTER Q&A: 関数型エキスパートの視点

**Q1: オブジェクトを新しく作り続ける（不変性）のは、メモリの無駄ではありませんか？**
- **回答**: 確かにメモリ消費は増えますが、現代のV8エンジンはガベージコレクションが非常に高速です。それよりも**「予測可能性」**を得る価値の方が圧倒的に高いです。ミュータブルなコードでバグを10時間探すコストに比べれば、5msのGCオーバーヘッドは微々たるものです。

**Q2: FPを使うべきでない場面はありますか？**
- **回答**: 60fpsのゲームエンジンや、極めて高度な画像処理ループなど、1フレーム内でのパフォーマンスが極限まで求められる場合は、オブジェクトの生成コストを避けるために「破壊的な変更（In-place Mutation）」が「必要悪」として選ばれることもあります。

**Q3: FPはテストにどう役立ちますか？**
- **回答**: 純粋関数は、世界で最もテストが簡単なものです。データベースを「モック」したり、グローバルな状態を「セットアップ」したりする必要はありません。入力を渡し、出力を確認するだけです。一度動けば、永久に動きます。

**Q4: 「ポイントフリー・スタイル」とは何ですか？**
- **回答**: 操作対象のデータを明示的に書かないスタイルです。
  例: `const getNames = users => users.map(u => u.name);` (標準)
  例: `const getNames = map(prop('name'));` (ポイントフリー)
  日本のプロジェクトでは、チーム全体の読みやすさが向上する場合にのみ、控えめに使用してください。
