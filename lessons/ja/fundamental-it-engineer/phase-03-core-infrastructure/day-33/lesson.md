# 🪝 1. 導入：コールバック地獄（Callback Hell）という悪夢

2012年にタイムスリップしたと想像してください。あなたは東京の大手SIerのプロジェクトで働いています。システム要件は、「ユーザー情報を取得し、そのユーザーの注文リストを取得し、さらに各商品の詳細を取得する」というものでした。あなたのコードは、おそらく以下のようになっていたはずです：

```javascript
getUser(id, (user) => {
    getOrders(user.id, (orders) => {
        getOrderDetail(orders[0].id, (detail) => {
            console.log(detail);
            // どんどん右側にインデントが深くなっていく...
        });
    });
});
```

これが **コールバック地獄 (Callback Hell)** です。すべての開発者にとっての悪夢です。単に読みにくいだけでなく、エラーハンドリングが極めて困難です。どこか一つのステップで失敗した場合、すべての階層で `if(err)` をネストして書かなければなりませんでした。

今日、私たちは **Promise (プロミス)** と **Async/Await** を使ってこの「地獄」を破壊する方法を学びます。また、なぜイベントループにおいて Promise が `setTimeout` よりも優先されるのか、その裏側の仕組みを解明します。

# 🍱 2. 例え話：新宿のラーメン屋の注文システム

新宿にある自動券売機式のラーメン屋に入ったと想像してください：

1.  **取引 (Promiseの作成)**: 券売機にお金を入れ、メニューを選びます。券売機はあなたに「食券（**Promise**）」を渡します。この時点での状態は `Pending`（保留中）です。
2.  **調理 (実行)**: 厨房で店員がラーメンを作り始めます（非同期タスク）。
3.  **結果 (Settled/解決済み)**:
    -   **成功 (Fulfilled/Resolved)**: ベルが鳴り、熱々のラーメンを受け取ります。これが `.then()` または `await` が結果を返す瞬間です。
    -   **失敗 (Rejected)**: 店員が「すみません、材料が切れました！」と言いに来ます。あなたはお金を返金（エラー）してもらいます。これが `.catch()` または `try/catch` が動作する瞬間です。

**ポイント**: ラーメンを待っている間、あなたは座ってスマホをいじることができます（メインスレッドはブロックされません）。

# ⚙️ 3. 詳細解説：マイクロタスクキューと優先順位

Day 31で、マクロタスクキュー（setTimeout, setInterval）について学びました。しかし、Promise は **マイクロタスクキュー (Microtask Queue)**（またはジョブキュー）という別の待ち行列を使用します。

### 3.1 イベントループの優先順位ルール
1.  **コールスタック (Call Stack)** 内のすべてのコードを実行する。
2.  **マイクロタスクキュー** を確認する。タスクがあれば、そのキューが空になるまで **すべて** のタスクを実行する。
3.  **マクロタスクキュー** を確認する。タスクを **一つだけ** 取り出して実行する。
4.  ステップ2に戻る。

**結論**: Promise は常に `setTimeout(0)` よりも先に実行されます。

```javascript
console.log("Start");
setTimeout(() => console.log("Macrotask"), 0);
Promise.resolve().then(() => console.log("Microtask"));
console.log("End");

// 実行結果: Start -> End -> Microtask -> Macrotask
```

### 3.2 スターベーション (Starvation)：マイクロタスクがブラウザを窒息させる時
もしマイクロタスクを過剰に詰め込むと（例：再帰的な Promise ループ）、マクロタスクキュー（UIレンダリングを含む）が実行されなくなります。これにより、スクリプトエラーがなくてもブラウザが「フリーズ」します。マスターエンジニアは、`setTimeout` を使って作業を分割（チャンキング）し、UIレンダリングに隙間を作る方法を知っていなければなりません。

# 🚀 4. プロミス API マスター：最強の4人衆

実際の現場（**ANA** の航空券予約システムなど）では、単一の API だけを叩くことは稀です。

### 4.1 Promise.all([p1, p2, p3])
-   **挙動**: すべての成功を待ちます。一つでも失敗すれば、即座にすべてが失敗します（Fail-fast）。
-   **用途**: ユーザー情報と財布の残高を同時に取得し、支払い能力があるか確認する場合。

### 4.2 Promise.allSettled([p1, p2, p3])
-   **挙動**: 成功・失敗に関わらず、すべての終了を待ちます。
-   **用途**: ダッシュボードのウィジェットをロードする場合。一つのウィジェットがエラーになっても、他のウィジェットを壊してはいけません。

### 4.3 Promise.race([p1, p2, p3])
-   **挙動**: 最も早く終わったものの結果を採用します（成功・失敗問わず）。
-   **用途**: **リクエストタイムアウトパターン**。APIリクエストと `setTimeout` を競わせ、タイムアウトが勝ったら「タイムアウト」と報告します。

### 4.4 Promise.any([p1, p2, p3])
-   **挙動**: 最初に **成功** した結果を返します。すべてが失敗したときのみエラーになります。
-   **用途**: 複数のバックアップサーバーからデータを取得する場合。最も速く有効なデータを返したサーバーを採用します。

# 🛡️ 5. 高度なエラーハンドリング：防御的戦略

### 5.1 グローバルエラーキャッチ
`window.addEventListener('unhandledrejection')` を使用して、忘れ去られた Promise エラーを監視システム（SentryやCloudWatchなど）にログ出力します。

### 5.2 「セーフ・ラッパー」パターン
ネストした `try/catch` を避けるために、ラッパーを使用します：
```javascript
const to = (promise) => promise.then(data => [null, data]).catch(err => [err, null]);
const [err, user] = await to(getUser(id));
if (err) return handleError(err);
```

# 🏎️ 6. レースコンディション：実行順序の逆転

ユーザーが検索ボタンを連打している場面を想像してください。リクエスト1が先に送信されましたが、リクエスト2よりも後に届きました。何も対策をしていないと、UIにはリクエスト1（古い結果）が表示されてしまいます（誤り！）。

**解決策：AbortController**
```javascript
let controller = new AbortController();
async function search(query) {
    controller.abort(); // 以前のリクエストをキャンセル
    controller = new AbortController();
    try {
        const res = await fetch(`/api/search?q=${query}`, { signal: controller.signal });
        // ... 結果の処理
    } catch (err) {
        if (err.name === 'AbortError') console.log('以前のリクエストはキャンセルされました');
    }
}
```

# 😱 7. ASYNC/AWAIT：エレガンスの極致

`async/await` は完全に新しい仕組みではありません。Promise と Generator（ジェネレータ）の上に構築された **構文糖衣 (Syntactic Sugar)** です。非同期コードを、同期的な逐次処理コードのように見せることができます。

### 7.1 Async/Await の実行フロー
JS が `await` キーワードに遭遇すると、その async 関数の実行を「一時停止」し、残りのコードをマイクロタスクキューにプッシュします。その間、コールスタックは解放され、他の作業ができるようになります。

# 🎯 10. 試験ロジック：マスターの知恵

**Q1: Rejected された Promise に対して `.catch()` を使わないとどうなりますか？**
*回答*: `Unhandled Promise Rejection` という警告が発生します。Node.js の最新バージョンでは、プロセスがクラッシュすることもあります。

**Q2: `await` は `async` 関数の外でも使えますか？**
*回答*: **Top-level await** (ES Modules) または特定の REPL 環境でのみ可能です。それ以外では構文エラーになります。

**Q3: 逐次 (Sequential) と並列 (Parallel)：いつどちらを使うべきですか？**
-   **逐次**: タスクBにタスクAの結果が必要な場合。
-   **並列**: 各タスクが独立している場合。`Promise.all()` を使用します。これにより、日本の SIer プロジェクトでもページ遅延を 2秒から 500ミリ秒に短縮できる可能性があります。

**Q4: `Promise.all()` で、一部が失敗しても全体を壊さないようにするには？**
*回答*: `Promise.all()` に渡す配列内の各 promise 自体に `.catch()` を付けておきます。

**Q5: なぜ日本の銀行システムでは速度よりも安定性が重視されるのですか？**
*回答*: 金融取引において「未ハンドリングの拒絶」は致命的な不整合を生むからです。最悪のケースをすべて想定して処理する「遅いが堅牢なシステム」が、常に好まれます。
